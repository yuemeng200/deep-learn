# 第5章：记忆与持久化

> 上一章我们理解了 Agent 如何通过技能和工具扩展能力。本章我们看另一个维度的扩展——**时间维度**：Agent 如何跨会话记住用户。记忆系统是「将不确定性封装在确定性框架中」在数据层面的体现：LLM 的记忆是不可靠的（上下文窗口有限、会话结束就遗忘），但持久化存储 + LLM 辅助提取的框架是确定的。

---

## 5.1 记忆系统架构

### 核心问题

没有记忆的 Agent 每次对话都从零开始——不知道你的偏好、不记得之前的讨论、不了解你的工作背景。有了记忆，Agent 就像「认识了你很久的助手」。

### 数据流

```
用户与 Agent 对话
    ↓
MemoryMiddleware（#14）→ 将对话加入更新队列
    ↓
更新队列（debounce 30s）→ 合并同一线程的多次更新
    ↓
后台线程 → 调用 LLM 提取事实
    ↓
LLM 分析对话 → 结构化 JSON 输出
    ↓
原子写入 memory.json（临时文件 + rename）
    ↓
下次对话 → DynamicContextMiddleware 注入记忆到提示词
```

## 5.2 记忆数据结构

每个用户的记忆存储在独立文件中：

```
backend/.deer-flow/
  └── users/
      └── {user_id}/
          ├── memory.json        ← 全局记忆
          └── agents/
              └── {agent_name}/
                  └── memory.json  ← 自定义 Agent 专属记忆
```

### memory.json 的结构

```json
{
  "version": "1.0",
  "lastUpdated": "2026-05-14T10:00:00Z",

  "user": {
    "workContext":     {"summary": "全栈开发者，主要用 TypeScript 和 Python", "updatedAt": "..."},
    "personalContext":  {"summary": "对 AI Agent 系统感兴趣", "updatedAt": "..."},
    "topOfMind":       {"summary": "正在研究 DeerFlow 框架", "updatedAt": "..."}
  },

  "history": {
    "recentMonths":      {"summary": "...", "updatedAt": "..."},
    "earlierContext":     {"summary": "...", "updatedAt": "..."},
    "longTermBackground": {"summary": "...", "updatedAt": "..."}
  },

  "facts": [
    {
      "id": "fact_abc123",
      "content": "偏好使用 ZhipuAI 的模型",
      "category": "preference",
      "confidence": 0.9,
      "createdAt": "2026-05-14T10:00:00Z",
      "source": "thread_xxx"
    }
  ]
}
```

**三层结构的设计意图**：
- **user/history**：LLM 生成的综合摘要，提供全局视角
- **facts**：具体的、可验证的事实条目，提供精确细节

## 5.3 事实提取算法

这是记忆系统最精妙的部分——用 LLM 从对话中提取结构化事实：

### 第一步：消息预处理

```python
# 1. 剥离文件上传事件（临时性信息，不值得记忆）
# 2. 只保留用户消息 + AI 最终回复（丢弃工具调用中间过程）
# 3. 检测修正信号（"不对"、"搞错了"）
# 4. 检测强化信号（"很好"、"正是如此"）
```

### 第二步：LLM 提取

```
输入给 LLM：
  - 当前记忆状态（user + history + facts）
  - 预处理后的对话消息
  - 详细的提取指南（什么该记、什么不该记）

LLM 输出：
  - user 各字段的更新
  - history 各字段的更新
  - 新增的 facts 列表
  - 需要删除/修改的 facts ID
```

### 第三步：后处理

```python
# 1. 解析 LLM 的 JSON 输出
# 2. 合并更新到现有记忆
# 3. 去重（基于内容，忽略空白差异）
# 4. 强制上限（最多 100 条 facts，按 confidence 排序截断）
# 5. 原子写入文件
```

### 事实分类

| 分类 | 含义 | 示例 |
|------|------|------|
| `preference` | 用户偏好 | "喜欢用 TypeScript" |
| `knowledge` | 用户具备的知识 | "熟悉 LangGraph" |
| `context` | 当前工作上下文 | "正在开发一个 Agent 项目" |
| `behavior` | 行为模式 | "习惯先看代码再问问题" |
| `goal` | 目标意图 | "想成为 DeerFlow 核心贡献者" |
| `correction` | 修正信息 | "之前的答案有误，应该是..." |

## 5.4 更新队列：Debounce 机制

记忆更新不是每次对话都触发，而是通过**防抖队列**：

```
对话 A 结束 → 加入队列 → 开始 30s 倒计时
对话 B 结束 → 加入队列 → 重置 30s 倒计时（合并 A + B）
  ... 30s 内没有新对话 ...
    ↓
批量处理队列中的所有对话
```

**为什么需要 debounce？**
- **性能**：每次对话都调 LLM 做事实提取开销太大
- **质量**：多条消息一起分析，比单条分析更准确
- **去重**：30s 内的多次更新合并，避免重复提取同一事实

## 5.5 记忆注入：让 Agent 「记住」

`DynamicContextMiddleware`（#9）在每次 Agent 执行前将记忆注入系统提示词：

```
1. 读取 memory.json
2. 按 confidence 排序 facts
3. 用 tiktoken 计算 token 数
4. 在 max_injection_tokens（默认 2000）预算内，尽可能多地注入
5. 拼接到系统提示词的「用户记忆」区域
```

**Token 预算机制**很重要——记忆不能无限膨胀，否则会挤占工具调用和推理的空间。

## 5.6 用户隔离

DeerFlow 实现了严格的用户级隔离：

```python
# 无认证模式：所有用户共享 "default" ID
user_id = "default"

# 有认证模式：从 access_token 解析 user_id
user_id = get_effective_user_id(runtime_context)
```

每个用户的数据完全隔离：
- 独立的 memory.json
- 独立的线程目录
- 独立的沙箱工作空间
- 独立的 checkpoint 数据

## 5.7 Checkpoint：对话状态持久化

除了用户记忆，DeerFlow 还通过 Checkpoint 机制持久化**对话状态**：

```yaml
# config.yaml
checkpointer:
  type: sqlite                    # 内存 / SQLite / PostgreSQL
  connection_string: checkpoints.db
```

| 类型 | 适用场景 | 特点 |
|------|---------|------|
| `memory` | 开发测试 | 进程退出即丢失 |
| `sqlite` | 单机部署 | 文件持久化，简单可靠 |
| `postgres` | 生产集群 | 支持多进程共享 |

Checkpoint 保存的是 `ThreadState` 的完整快照——包括消息历史、工具调用结果、artifacts 列表等。这确保了「关闭浏览器再打开，对话继续」。

## 5.8 实战：为研究助手添加「记住偏好」能力

在研究助手技能的基础上，我们可以利用记忆系统让 Agent 记住用户的研究偏好：

当用户第一次使用研究助手时：
- Agent 会自动提取「用户关注 AI 框架对比」这类偏好
- 下次用户问「帮我调研 XX」，Agent 会基于偏好调整搜索策略和报告格式

不需要写额外代码——记忆系统是全局的，所有技能自动受益。

## 思考题

**题 1**：记忆系统使用 LLM 来提取事实（用 LLM 分析对话 → 输出结构化事实），而不是用正则或 NER 等传统方法。这种选择有什么优势和代价？在什么情况下 LLM 提取可能会「出错」？

> **参考答案**：优势：1）**语义理解**——能理解「我不喜欢 Python」是偏好而非知识，传统方法很难做这种分类；2）**灵活性**——不需要预定义提取规则，能处理任意格式的对话；3）**上下文推理**——能从多轮对话中推断隐含偏好。代价：1）**成本**——每次记忆更新都要调一次 LLM；2）**不确定性**——LLM 可能提取出「幻觉事实」（对话中没说过但 LLM 推断出来的）或遗漏重要信息；3）**延迟**——debounce 后的后台处理仍有延迟，不是实时更新。LLM 提取出错的典型场景：用户说反话/讽刺时（LLM 可能按字面理解）、对话涉及假设性场景时（LLM 可能把假设当事实）、长对话中前后矛盾时（LLM 可能取前面或后面的版本）。

**题 2**：记忆注入有 2000 token 的预算限制。如果用户的记忆已经积累了很多内容（超过 2000 token），系统按 confidence 排序截断。这种策略在什么情况下可能丢失重要信息？你会如何改进？

> **参考答案**：按 confidence 排序可能丢失重要信息的场景：1）**新近但低 confidence**——用户刚提到的重要偏好可能 confidence 还不高（只提过一次），被旧的、高 confidence 但不再相关的信息挤掉；2）**上下文相关但整体低 confidence**——当前对话主题相关的事实可能 confidence 一般，但与本次对话高度相关。改进方案：1）**时间衰减 + confidence**——综合评分中加入时间因素，近期事实加分；2）**语义相关性**——根据当前对话内容，用 embedding 检索最相关的记忆，而非纯按 confidence 排序；3）**分层预算**——user 层、history 层、facts 层各分配固定预算，确保每层都有代表性信息。

**题 3**：当前记忆系统是「全局的」——所有技能共享同一份用户记忆。如果要让不同技能拥有独立的记忆空间（比如研究助手记研究偏好，代码助手记编码风格），你会如何修改架构？

> **参考答案**：DeerFlow 其实已经有了基础设施——自定义 Agent 支持 `agents/{agent_name}/memory.json` 的独立记忆文件。要扩展到技能级别：1）**技能级记忆文件**——在 memory 路径下增加 `skills/{skill_name}/memory.json`，每个技能独立存储；2）**注入时按技能过滤**——DynamicContextMiddleware 注入记忆时，除了全局记忆，还注入当前匹配技能的专属记忆；3）**提取时标记来源**——LLM 提取事实时要求标注属于哪个技能（或全局），然后路由到对应的记忆文件。权衡在于**碎片化 vs 专注度**——独立记忆空间更专注但信息不共享，全局记忆更统一但可能混入不相关信息。合理的折中是：全局记忆 + 技能增强记忆（双层结构）。
