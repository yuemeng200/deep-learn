> 前八章我们从架构全景走到每一个核心子系统，包括前后端通信的深入解析。本章是整门课程的「整合与输出」——将所有知识汇聚成一个真实的贡献。这正是课程核心本质的最终落地：你将用「确定性框架」的方式（代码规范、测试流程、PR 模板）将你的「不确定性创意」（新功能或改进）封装成一个可靠的贡献。

## 9.1 开发环境确认

在开始贡献之前，确保开发环境完整：

```bash
# 检查工具链
make check

# 安装所有依赖 + pre-commit hooks
make install

# 验证本地运行
make dev
# 访问 http://localhost:2026，确认功能正常
```

### Pre-commit Hooks

安装后，每次 `git commit` 会自动运行：
- **后端**：`ruff` 格式化 + lint
- **前端**：ESLint + Prettier

如果 commit 被拒绝，说明代码格式不符合规范，修复后重新 commit 即可。

## 9.2 代码规范

### 后端（Python）

| 工具 | 命令 | 用途 |
|------|------|------|
| ruff | `cd backend && make format` | 格式化 + 自动修复 lint 问题 |
| ruff | `cd backend && make lint` | 仅检查，不修改 |
| pytest | `cd backend && make test` | 运行测试 |

代码风格：
- 双引号
- 空格缩进
- 行长度上限 240 字符
- 必须使用 type hints

### 前端（TypeScript/React）

| 工具 | 命令 | 用途 |
|------|------|------|
| ESLint | `cd frontend && pnpm check` | lint + 类型检查 |
| Prettier | `cd frontend && pnpm format:write` | 格式化 |
| Vitest | `cd frontend && pnpm test` | 单元测试 |
| Playwright | `cd frontend && pnpm test:e2e` | E2E 测试 |

导入顺序（强制）：
```
builtin → external → internal → parent → sibling
(按字母排序)
```

### 关键架构约束

**Harness/App 边界**是最重要的架构规则：

```
✅ 允许：
  app/gateway/ → import deerflow.harness.*
  tests/ → import deerflow.*

❌ 禁止：
  deerflow.harness/ → import app.gateway.*
```

harness 是可发布的独立包，不能依赖应用层。这个约束在 CI 中通过 `test_harness_boundary.py` 测试强制执行。

## 9.3 贡献流程

### 标准流程

```
1. Fork + Clone（如果还没有）
2. 创建功能分支
   git checkout -b feature/your-feature-name

3. 编写代码 + 测试
4. 格式化代码
   cd backend && make format
   cd frontend && pnpm format:write

5. 运行测试
   cd backend && make test
   cd frontend && pnpm test

6. 提交（遵循 Conventional Commits）
   git commit -m "feat: 添加 XX 功能"
   git commit -m "fix: 修复 YY 问题"
   git commit -m "docs: 更新 ZZ 文档"

7. 推送 + 创建 PR
   git push origin feature/your-feature-name
   gh pr create --title "feat: ..." --body "..."
```

### Commit 消息格式

```
<type>(<scope>): <description>

类型：
  feat:     新功能
  fix:      修复 bug
  docs:     文档变更
  style:    格式调整（不影响逻辑）
  refactor: 重构（不是新功能也不是修 bug）
  test:     添加或修改测试
  chore:    构建工具或辅助工具变更
```

### PR 要求

1. **标题**：简明扼要，说明做了什么
2. **描述**：为什么做、怎么做的、如何测试
3. **测试**：必须包含相关测试
4. **文档**：用户可见的变更需要更新 README.md
5. **CI 通过**：所有自动化测试必须通过

## 9.5 实战：完成研究助手技能的完整集成

将第 4 章创建的研究助手技能完善为可提交的贡献：

### Step 1：完善技能定义

```markdown
# skills/custom/research-assistant/SKILL.md

---
name: research-assistant
description: "多源研究助手：将复杂研究问题分解为子问题，并行搜索多个信息源，综合生成结构化研究报告"
---

# 多源研究助手

## 触发条件
当用户的请求涉及以下场景时激活此技能：
- 需要调研某个主题或技术
- 需要对比多个方案
- 需要收集和综合多方面信息

## 执行流程

### 第一步：问题分解
分析用户的研究问题，将其拆解为 2-5 个独立的子问题。
每个子问题应该：
- 可以独立搜索和回答
- 覆盖原问题的不同维度
- 合在一起能完整回答原问题

将分解结果展示给用户，确认后继续。

### 第二步：并行搜索
使用 task 工具创建并行子 Agent（最多 3 个），每个子 Agent 负责：
1. 使用 web_search 搜索相关信息
2. 使用 web_fetch 抓取关键页面的详细内容
3. 整理发现，输出结构化的研究结果

### 第三步：综合报告
汇总所有子 Agent 的结果，生成包含以下部分的结构化报告：
- **摘要**（100 字以内）
- **背景**（为什么值得研究这个主题）
- **各维度的发现**（每个子问题一个章节）
- **关键结论**（3-5 条核心洞察）
- **建议**（基于发现的行动建议）
- **信息来源**（所有引用的 URL）

### 第四步：保存报告
将最终报告写入 /mnt/user-data/outputs/research-report.md，
并使用 present_files 工具展示给用户。

## 注意事项
- 如果研究问题很简单（只需一次搜索就能回答），不需要分解
- 保持客观，呈现多方观点而非单一结论
- 标注信息的不确定性和时效性
```

### Step 2：添加测试

```python
# tests/test_research_skill.py
import pytest
from deerflow.skills.parser import parse_skill_file
from deerflow.skills.validation import validate_skill

def test_research_skill_metadata():
    """测试技能元数据是否正确"""
    skill = parse_skill_file("skills/custom/research-assistant/SKILL.md")
    assert skill.name == "research-assistant"
    assert "研究" in skill.description
    assert skill.description  # 非空
    assert len(skill.description) <= 1024

def test_research_skill_content():
    """测试技能内容包含必要章节"""
    skill = parse_skill_file("skills/custom/research-assistant/SKILL.md")
    assert "问题分解" in skill.content
    assert "并行搜索" in skill.content
    assert "综合报告" in skill.content

def test_research_skill_validation():
    """测试技能通过验证"""
    skill = parse_skill_file("skills/custom/research-assistant/SKILL.md")
    errors = validate_skill(skill)
    assert len(errors) == 0, f"Validation errors: {errors}"
```

### Step 3：提交 PR

```bash

git checkout -b feature/research-assistant-skill

# 复制技能到公共目录（如果要提交给社区）

# 格式化 + 测试

# 提交

git add tests/test_research_skill.py

# 推送 + 创建 PR
git push origin feature/research-assistant-skill
gh pr create --title "feat(skills): add research-assistant skill" --body "$(cat <<'EOF'

and synthesizes a structured report.

## Test plan
- [x] Unit tests for skill metadata validation
- [x] Manual test: trigger skill with research query, verify parallel sub-agent execution

EOF
)"
```

## 思考题

**题 1**：DeerFlow 的 Harness/App 边界规则（harness 不能 import app）通过 CI 测试强制执行。但有些贡献可能需要同时在 harness 和 app 层修改。你会如何组织这样的 PR？

> **参考答案**：关键原则是**保持依赖方向**——app 依赖 harness，harness 不依赖 app。组织方式：1）**扩展点在 harness**——在 harness 中定义新的抽象接口或钩子（如新的中间件类型、新的事件类型），不引入任何 app 层代码；2）**实现在 app**——在 app/gateway 中实现具体的业务逻辑，引用 harness 的新接口；3）**同 PR 双层修改**——可以在同一个 PR 中同时修改两层，只要 harness 的修改不依赖 app 的修改即可。如果确实需要双向通信，使用**事件/回调模式**——harness 定义事件接口，app 注册具体的处理器。

**题 2**：你发现了一个已有的社区工具（如 `deerflow.community.tavily`）的一个 bug。修复这个 bug 的最小改动是什么？如何确保你的修复不会影响其他使用这个工具的用户？

> **参考答案**：最小改动：1）在 `community/tavily/tools.py` 中定位 bug 代码；2）只修改有问题的逻辑，不重构；3）添加一个回归测试覆盖这个 bug 场景。确保不影响其他用户：1）**只改实现不改接口**——函数签名和返回格式不变；2）**跑全量测试**——`make test` 确保没有破坏其他测试；3）**考虑配置兼容性**——如果 bug 修复改变了某个默认行为，确保 config.yaml 中有回退选项；4）**PR 描述中说明影响范围**——让 reviewer 知道这个修改的影响面。

**题 3**：假设你要为 DeerFlow 添加一个全新的子系统（比如「定时任务调度」——让 Agent 定期执行某些技能）。你会如何规划这个贡献？需要修改哪些目录？需要新增哪些文件？

> **参考答案**：规划步骤：1）**harness 层**——在 `deerflow/scheduler/` 下新建调度器模块（抽象接口 + 默认实现），定义调度配置 schema、任务执行器接口；2）**app 层**——在 `app/gateway/routers/` 下添加调度管理 API（CRUD 定时任务），在 `app/gateway/services.py` 中添加调度服务；3）**配置**——在 config.yaml 中添加 `scheduler:` 配置节；4）**集成**——通过中间件或 hook 在 Agent 启动/停止时注册/注销定时任务；5）**前端**——在 workspace 中添加定时任务管理 UI；6）**测试**——单元测试调度逻辑 + E2E 测试完整流程。这是一个大型贡献，建议拆成多个 PR：第一个 PR 做 harness 层的接口定义，后续 PR 逐步添加实现和集成。
