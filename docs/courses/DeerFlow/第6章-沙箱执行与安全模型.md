# 第6章：沙箱执行与安全模型

> 前几章我们理解了 Agent 的智能层（编排、技能、记忆）。本章我们看 Agent 的「执行力」——沙箱系统。这是「将不确定性封装在确定性框架中」在安全层面的终极体现：LLM 可能生成任意代码，但沙箱确保这段代码**只能在受控环境中执行**，无法突破预设的安全边界。

---

## 6.1 为什么需要沙箱？

DeerFlow 的 Agent 能执行 bash 命令、读写文件——这是它的强大之处，也是危险之处。

没有沙箱的风险：
- Agent 误操作 `rm -rf /` 删除系统文件
- 恶意提示注入诱导 Agent 执行危险命令
- Agent 访问不该访问的敏感文件（如 `.env`、`id_rsa`）
- 子 Agent 的并行执行导致资源争抢

**沙箱的本质**：为 Agent 的行为划定一个「安全围栏」——在围栏内可以自由操作，但无法越界。

## 6.2 沙箱架构：三层选择

DeerFlow 提供三种沙箱模式，通过 `config.yaml` 的 `sandbox.use` 配置：

```
┌──────────────────────────────────────────────┐
│           Sandbox Provider（抽象层）            │
│  acquire_sandbox() / release_sandbox()        │
└──────────┬───────────┬────────────┬───────────┘
           │           │            │
     ┌─────┴─────┐ ┌───┴────┐ ┌────┴──────┐
     │   Local    │ │  AIO   │ │   K8s     │
     │  Sandbox   │ │ Docker │ │ Provisioner│
     │  (开发)    │ │ (生产) │ │ (集群)     │
     └───────────┘ └────────┘ └─────────────┘
```

### LocalSandbox（本地模式）

```yaml
sandbox:
  use: deerflow.sandbox.local:LocalSandboxProvider
  allow_host_bash: false  # 默认禁止 bash
```

- 直接在宿主机执行命令
- 通过**虚拟路径映射**限制访问范围
- **不是真正的隔离**——依赖路径校验而非 OS 级隔离
- 适合本地开发和可信环境

### AioSandbox（容器模式）

```yaml
sandbox:
  use: deerflow.community.aio_sandbox:AioSandboxProvider
  image: enterprise-public-cn-beijing.cr.volces.com/vefaas-public/all-in-one-sandbox:latest
  replicas: 3
```

- 在 Docker 容器中执行（macOS 优先使用 Apple Container）
- **真正的 OS 级隔离**
- 温池（Warm Pool）机制避免冷启动
- 适合生产环境

### K8s Provisioner（集群模式）

```yaml
sandbox:
  use: deerflow.community.aio_sandbox:AioSandboxProvider
  provisioner_url: http://provisioner:8002
```

- 每个线程获得独立的 K8s Pod
- 最强的隔离性和可扩展性
- 适合大规模生产部署

## 6.3 虚拟路径系统：核心安全机制

这是沙箱最精妙的设计——Agent 看到的路径和真实路径是**不同的**。

### Agent 视角（虚拟路径）

```
/mnt/user-data/           ← 用户数据根目录
  ├── workspace/          ← 工作空间
  ├── uploads/            ← 上传文件
  └── outputs/            ← 输出产物
/mnt/skills/              ← 技能文件（只读）
/mnt/acp-workspace/       ← ACP 工作空间（只读）
```

### 真实路径（宿主机）

```
backend/.deer-flow/users/{user_id}/threads/{thread_id}/user-data/
deer-flow/skills/
backend/.deer-flow/users/{user_id}/threads/{thread_id}/acp-workspace/
```

### 路径转换

```python
# Agent 说「读 /mnt/user-data/workspace/main.py」
# 沙箱翻译为「读 .deer-flow/users/{uid}/threads/{tid}/user-data/workspace/main.py」
# 然后把结果中的真实路径替换回虚拟路径

def _resolve_path(self, virtual_path: str) -> str:
    """虚拟路径 → 真实路径"""
    for mount in self.mounts:
        if virtual_path.startswith(mount.container_path):
            return virtual_path.replace(mount.container_path, mount.host_path)
    raise PermissionError(f"路径不在允许范围内: {virtual_path}")

def _reverse_resolve_path(self, real_path: str) -> str:
    """真实路径 → 虚拟路径（用于输出脱敏）"""
    # 确保返回给 Agent 的路径始终是虚拟路径
    # 防止宿主机路径泄露
```

### 自定义挂载

可以在 config.yaml 中添加额外的挂载点：

```yaml
sandbox:
  mounts:
    - host_path: /home/user/my-project
      container_path: /mnt/my-project
      read_only: true     # 只读挂载
```

## 6.4 安全防护层

### 第一层：路径校验

```python
def _reject_path_traversal(path: str):
    """拒绝 .. 路径穿越"""
    if ".." in pathlib.Path(path).parts:
        raise PermissionError("路径穿越被阻止")

def validate_local_tool_path(path: str, allowed_prefixes: list[str]):
    """验证路径是否在允许的前缀下"""
    real = os.path.realpath(path)
    if not any(real.startswith(prefix) for prefix in allowed_prefixes):
        raise PermissionError("路径不在允许范围内")
```

### 第二层：命令审计

`SandboxAuditMiddleware`（#7）记录所有 bash 命令执行：

```
[审计日志] thread_id=xxx, command="cat /mnt/user-data/workspace/config.yaml"
[审计日志] thread_id=xxx, command="pip install requests"
[警告] 检测到潜在危险命令: thread_id=xxx, command="rm -rf ..."
```

### 第三层：输出脱敏

所有返回给 Agent 的结果中，真实路径被替换为虚拟路径：

```python
# 工具返回: "File created at /home/user/.deer-flow/users/.../main.py"
# 脱敏后:   "File created at /mnt/user-data/workspace/main.py"
```

Agent 永远不知道宿主机的真实路径结构。

### 第四层：输出截断

```yaml
sandbox:
  bash_output_max_chars: 20000     # bash 输出最大字符数
  read_file_output_max_chars: 50000  # 文件读取最大字符数
```

- bash 使用**中间截断**（保留头部 + 尾部），因为错误信息可能在任意位置
- read_file 使用**头部截断**，因为代码文件的上下文通常在前面

## 6.5 AIO Sandbox 的温池机制

容器模式的性能优化——避免每次工具调用都等待容器启动：

```
首次使用:
  创建容器 → 启动 → 等待就绪（最多 60s）→ 执行命令
                    ↓
              放入温池（保持运行）
后续使用:
  从温池取出 → 直接执行命令（零延迟）
                    ↓
              放回温池
                    ↓
  空闲 10 分钟后 → 自动销毁
```

### 确定性容器 ID

```python
# 基于 thread_id 生成确定性的容器 ID
container_id = f"deer-flow-sandbox-{sha256(thread_id)[:12]}"
```

这确保同一个线程始终使用同一个容器——文件操作的结果在多次工具调用之间保持一致。

### 跨进程发现

使用文件锁机制防止多个 Gateway 进程创建重复容器：

```
进程 A 检查容器 → 不存在 → 创建
进程 B 检查容器 → 发现进程 A 已创建 → 复用
```

## 6.6 沙箱工具集

所有在沙箱中执行的工具：

| 工具 | 功能 | 安全考虑 |
|------|------|---------|
| `bash` | 执行 shell 命令 | 路径翻译 + 命令审计 |
| `ls` | 列出目录（树形，2 层） | 只显示虚拟路径 |
| `read_file` | 读取文件内容 | 路径校验 + 大小截断 |
| `write_file` | 写入/追加文件 | 路径校验 + 目录自动创建 |
| `str_replace` | 字符串替换 | 路径校验 |
| `glob` | 按模式查找文件 | 路径校验 + 结果数量限制 |
| `grep` | 搜索文件内容 | 路径校验 + 结果数量限制 |

## 思考题

**题 1**：LocalSandbox 依赖路径校验而非 OS 级隔离。如果 Agent 通过 bash 工具执行 `ln -s /etc/passwd /mnt/user-data/workspace/passwd_link`，然后 `read_file /mnt/user-data/workspace/passwd_link`，会怎样？如何防护？

> **参考答案**：这是一个经典的符号链接攻击。如果 LocalSandbox 没有对符号链接做解析检查，`read_file` 会跟随 symlink 读取到 `/etc/passwd`。防护手段：1）**解析后校验**——在 `_resolve_path()` 中使用 `os.path.realpath()` 而非 `os.path.abspath()`，realpath 会解析所有 symlink 后再校验路径前缀；2）**禁止 symlink 创建**——在 bash 命令审计中检测 `ln -s` 并阻止指向允许范围外的目标；3）**使用 Docker 沙箱**——容器模式下文件系统天然隔离，symlink 无法逃逸到宿主机。DeerFlow 的实际实现采用了方案 1，在路径校验时使用 realpath。

**题 2**：温池机制保持了容器的「热」状态以避免冷启动，但这意味着一个空闲的 DeerFlow 实例也在持续消耗 Docker 容器资源。在资源受限的环境（如小团队服务器）中，你会如何调整温池策略？

> **参考答案**：几个可调参数：1）**缩短空闲超时**——从 10 分钟降到 2-3 分钟，更快回收资源；2）**降低副本上限**——从 3 降到 1-2，减少同时保持的容器数；3）**按需启动而非温池**——完全关闭温池，每次使用时创建容器，接受 10-30s 的冷启动延迟换取零空闲开销；4）**分级策略**——频繁使用的线程保持温池，低频线程用完即销毁，通过访问频率统计自动调整。最优解取决于具体场景的「延迟敏感度 vs 资源预算」权衡。

**题 3**：DeerFlow 的沙箱工具返回给 Agent 的路径是虚拟路径，但 bash 命令的 stdout 输出中可能包含真实路径（如编译错误信息 `/home/user/.deer-flow/.../error.log`）。当前的脱敏机制能完全覆盖这种情况吗？如果不够，你会如何增强？

> **参考答案**：当前的脱敏机制可能不完全覆盖——bash 的 stdout/stderr 内容千变万化，编译器、包管理器等工具可能以各种格式输出路径。增强方案：1）**正则替换**——在 bash 输出中用正则匹配所有可能的宿主机路径前缀并替换为虚拟路径；2）**环境变量注入**——在沙箱环境中设置 `HOME=/mnt/user-data`、`PWD=/mnt/user-data/workspace` 等环境变量，让子进程自然输出虚拟路径；3）**容器模式下的自然解决**——在 Docker 沙箱中，容器内的路径本身就是虚拟路径，不需要脱敏。这是 Docker 模式比本地模式更安全的另一个原因。
