# 第4章：技能与工具系统

> 前两章我们理解了 Agent 的「大脑」（状态机编排）和「手脚」（子 Agent 并行）。本章我们看 DeerFlow 如何让 Agent 掌握「技能」——可复用的、结构化的工作流定义。技能系统是「将不确定性封装在确定性框架中」的另一个维度：不是控制 LLM 的流转，而是控制 LLM 的**行为边界**。

---

## 4.1 技能（Skills）：用 Markdown 定义 Agent 能力

### 技能是什么？

技能是**预设的工作流模板**——用自然语言描述一套操作流程，让 Agent 在特定场景下遵循特定的行为模式。

DeerFlow 内置了 23+ 个技能，都定义在 [skills/public/](skills/public/) 目录下。

### 技能定义格式

每个技能是一个 Markdown 文件，包含 YAML frontmatter + 正文：

```markdown
---
name: data-analysis
description: "分析 Excel/CSV 数据文件，支持 SQL 查询和统计摘要"
license: "MIT"
allowed-tools: ["bash", "read_file", "write_file"]
---

# 数据分析技能

## 使用场景
当用户需要分析表格数据时，按以下流程执行：

1. 确认数据文件路径和格式
2. 使用 DuckDB 加载数据
3. ...

## 输出格式
请将分析结果以 Markdown 表格形式呈现...
```

### Frontmatter 字段

| 字段 | 必填 | 说明 |
|------|------|------|
| `name` | 是 | 小写字母 + 数字 + 连字符，最长 64 字符 |
| `description` | 是 | 最长 1024 字符，描述技能用途 |
| `license` | 否 | 许可证信息 |
| `allowed-tools` | 否 | 该技能允许使用的工具白名单 |

### 技能加载管线

```
skills/public/ 目录扫描
    ↓
发现 SKILL.md 文件
    ↓
解析 YAML frontmatter（parser.py）
    ↓
验证字段格式（validation.py）
    ↓
安全扫描内容（security_scanner.py）
    ↓
合并启用状态（extensions_config.json）
    ↓
返回 Skill 对象列表
```

### 技能如何被 Agent 使用

技能不是作为工具注入的，而是**作为系统提示词的一部分**：

```python
# prompt.py 中的 get_skills_prompt_section()
# 将所有启用的技能描述注入到系统提示词中
# Agent 根据用户请求匹配最相关的技能
```

这意味着 Agent **看到技能描述后会自主决定是否使用**——不是硬编码的触发条件，而是 LLM 理解后自然匹配。

### 安全防护

技能系统有多层安全检查：
- **ZIP 提取防护**：防止路径穿越攻击（`../../../etc/passwd`）
- **符号链接检测**：跳过可疑的 symlink
- **大小限制**：512MB 上限防止 ZIP 炸弹
- **内容扫描**：检测提示注入和恶意代码模式

## 4.2 工具（Tools）：Agent 的操作接口

### 工具 vs 技能

| 维度 | 技能（Skills） | 工具（Tools） |
|------|---------------|--------------|
| 本质 | 自然语言工作流模板 | 可执行的代码函数 |
| 定义方式 | Markdown 文件 | Python 函数 + config.yaml |
| 触发方式 | LLM 自主匹配 | LLM 显式调用 |
| 灵活性 | 高（自由文本） | 低（结构化输入/输出） |

### 工具加载管线

`get_available_tools()` 按以下优先级组装工具：

```
1. config.yaml 中定义的工具
   ↓ resolve_variable() 动态加载
2. 内置工具（present_files, ask_clarification, view_image, ...）
   ↓
3. MCP 工具（从 extensions_config.json 中的 MCP 服务器加载）
   ↓ 延迟加载 + 缓存
4. 子 Agent 工具（task，如果启用）
   ↓
5. 社区工具（deerflow.community/ 下的扩展）
```

### config.yaml 中的工具定义

```yaml
tools:
  - name: web_search
    group: web                                          # 工具分组
    use: deerflow.community.ddg_search.tools:web_search_tool  # 实现类路径
    max_results: 5                                      # 工具参数

  - name: read_file
    group: file:read
    use: deerflow.sandbox.tools:read_file_tool

  - name: bash
    group: bash
    use: deerflow.sandbox.tools:bash_tool
```

`use` 字段使用与模型配置相同的 `package.module:variable` 模式——DeerFlow 的统一解析协议。

### 工具分组与权限

工具通过 `group` 字段分组，这为权限控制提供了基础：

| 分组 | 包含的工具 | 典型权限 |
|------|-----------|---------|
| `web` | web_search, web_fetch, image_search | 通常允许 |
| `file:read` | ls, read_file, glob, grep | 通常允许 |
| `file:write` | write_file, str_replace | 可能受限 |
| `bash` | bash | 需要显式授权 |

## 4.3 MCP 协议集成：无限扩展工具

### 什么是 MCP？

MCP（Model Context Protocol）是一个开放协议，让 Agent 能够连接外部工具服务器。你可以把它理解为「Agent 的 USB 接口」——标准化了工具的插拔方式。

### 配置方式

[extensions_config.json](extensions_config.json) 中定义 MCP 服务器：

```json
{
  "mcpServers": {
    "my-server": {
      "enabled": true,
      "type": "stdio",
      "command": "node",
      "args": ["server.js"],
      "env": {"API_KEY": "value"}
    }
  }
}
```

### 支持的传输类型

| 类型 | 场景 | 说明 |
|------|------|------|
| `stdio` | 本地进程 | 启动子进程，通过 stdin/stdout 通信 |
| `sse` | 远程服务 | Server-Sent Events 长连接 |
| `http` | 远程服务 | HTTP 请求/响应 |

### 延迟加载与缓存

MCP 工具采用**延迟加载**策略：

```python
# 首次使用时才连接 MCP 服务器
# 缓存工具列表，避免重复连接
# 监听配置文件变更（mtime），自动刷新
```

### Tool Search：解决工具过多的问题

当 MCP 服务器暴露大量工具时，全部注入提示词会浪费上下文。DeerFlow 提供了 `tool_search` 机制：

```yaml
tool_search:
  enabled: true  # 启用后，MCP 工具不直接注入
                  # 而是通过 tool_search 工具按需发现
```

这就像给 Agent 一个「工具目录」而非「整箱工具」——需要什么再取什么。

## 4.4 社区工具生态

[community/](backend/packages/harness/deerflow/community/) 目录下有多个即插即用的工具扩展：

| 工具 | 功能 | 配置方式 |
|------|------|---------|
| `ddg_search` | DuckDuckGo 搜索（免 API Key） | 默认启用 |
| `tavily` | Tavily AI 搜索 | 需 API Key |
| `jina_ai` | Jina AI 网页抓取 | 默认启用 |
| `firecrawl` | Firecrawl 网页抓取 | 需 API Key |
| `image_search` | 图片搜索 | 默认启用 |
| `infoquest` | BytePlus 搜索引擎 | 需 API Key |
| `aio_sandbox` | Docker 沙箱 | config.yaml 配置 |

添加新工具只需要：1）在 `community/` 下编写工具函数；2）在 `config.yaml` 中注册。零侵入核心代码。

## 4.5 实战：为研究助手创建第一个技能

让我们开始实战项目的第一步——创建研究助手技能的骨架：

在 `skills/custom/` 目录下创建 `research-assistant/SKILL.md`：

```markdown
---
name: research-assistant
description: "多源研究助手：将复杂研究问题分解为子问题，并行搜索多个信息源，综合生成结构化研究报告"
---

# 多源研究助手

## 触发条件
当用户的请求涉及以下场景时激活此技能：
- 需要调研某个主题或技术
- 需要对比多个方案
- 需要收集和综合多方面信息

## 执行流程

### 第一步：问题分解
分析用户的研究问题，将其拆解为 2-5 个独立的子问题。
每个子问题应该：
- 可以独立搜索和回答
- 覆盖原问题的不同维度
- 合在一起能完整回答原问题

### 第二步：并行搜索
使用 task 工具创建并行子 Agent，每个子 Agent 负责一个子问题。
每个子 Agent 应使用 web_search 和 web_fetch 工具收集信息。

### 第三步：综合报告
汇总所有子 Agent 的结果，生成结构化报告：
- 摘要（100 字以内）
- 各维度的发现
- 关键结论
- 信息来源列表
```

这个技能骨架展示了技能系统的核心价值：**用自然语言定义复杂工作流，Agent 自动理解和执行**。

## 思考题

**题 1**：技能是通过系统提示词注入而非硬编码触发的。这意味着 Agent 可能「不使用」某个明明匹配的技能，或者「误用」一个不相关的技能。这种设计的取舍是什么？有没有更好的方案？

> **参考答案**：取舍的核心是**灵活性 vs 确定性**。提示词注入的优势：Agent 可以根据上下文灵活决定是否使用、如何使用技能——用户说「简单查一下 X」时可能不需要完整的研究流程。劣势：LLM 不 100% 可靠，可能遗漏或误匹配。更精确的方案包括：1）**意图分类器**——在 Lead Agent 前加一个轻量级分类模型，先确定意图再匹配技能；2）**结构化触发规则**——在 frontmatter 中定义正则或关键词匹配规则；3）**Few-shot 示例**——在提示词中加入技能使用的示例对话，提高匹配准确率。DeerFlow 选择纯提示词方案是因为简单且够用——对于大部分场景，现代 LLM 的技能匹配准确率已经足够高。

**题 2**：MCP 工具的延迟加载（首次使用时才连接）与启动时全量加载各有什么优劣？在什么场景下你会建议改为启动时加载？

> **参考答案**：延迟加载的优势：1）**启动速度快**——不等待 MCP 服务器连接；2）**容错性好**——某个 MCP 服务器挂掉不影响整体启动；3）**资源节约**——不用的工具不占资源。劣势：1）**首次调用延迟高**——用户第一次用到某个工具时需要等待连接建立；2）**运行时失败**——连接问题在用户使用时才暴露。建议改为启动时加载的场景：1）**生产环境**——启动时的健康检查可以在用户使用前发现问题；2）**工具数量少且确定使用**——延迟加载的复杂度不值得；3）**对延迟敏感的应用**——首次调用的额外延迟不可接受。

**题 3**：如果让你设计一个「工具权限系统」——不同用户/场景可以使用不同工具集——你会如何扩展 DeerFlow 的 `tool_groups` 配置？

> **参考答案**：当前 `tool_groups` 是全局的静态分组。扩展方向：1）**角色-权限映射**——在 config.yaml 中定义角色（admin/user/guest），每个角色允许的工具组不同；2）**线程级覆盖**——创建线程时可以指定本次会话可用的工具集（类似 `context` 中的 `thinking_enabled`）；3）**GuardrailMiddleware 集成**——现有的 Guardrail 中间件已经支持工具授权，扩展它读取角色权限配置即可。关键设计原则是**默认最小权限**——新用户默认只能用最基础的工具，按需授权更多。实现上可以利用已有的 `configurable` 运行时配置机制，把权限信息通过 context 传入中间件。
