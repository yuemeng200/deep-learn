# 第1章：全景认知与本地运行

> DeerFlow 的核心哲学是「将不确定性封装在确定性框架中」——LLM 的输出不可预测，但 Agent 的状态机流转是确定的、工具调用协议是确定的、沙箱隔离边界是确定的。本章我们将从全局视角看到这个哲学如何体现在整个架构中。

---

## 1.1 架构心智模型

把 DeerFlow 想象成一家**软件公司**：

```
用户（客户）
  ↓ 发出需求
前端（前台接待）
  ↓ 转发需求（SSE 长连接）
Nginx 反向代理（公司总机，端口 2026）
  ↓ 分发
┌─────────────────────────────────────────┐
│ FastAPI Gateway（项目经理）               │
│  - 接收请求，创建 Run 记录                │
│  - 管理线程（Thread）和运行（Run）         │
│  - 暴露 REST API + SSE 流                │
└──────────────┬──────────────────────────┘
               ↓ 调度
┌─────────────────────────────────────────┐
│ Lead Agent（技术主管）                    │
│  - LangGraph 状态机驱动                   │
│  - 18 个中间件组成处理管道                 │
│  - 选择模型、加载工具、注入记忆            │
│  - 决定是否分解为子任务                    │
└──────────────┬──────────────────────────┘
               ↓ 分派任务
┌──────────┐  ┌──────────┐  ┌──────────┐
│ 子 Agent A │  │ 子 Agent B │  │ 子 Agent C │  ← 最多 3 个并行
│ （开发人员）│  │ （开发人员）│  │ （开发人员）│
└─────┬─────┘  └─────┬─────┘  └─────┬─────┘
      ↓              ↓              ↓
┌─────────────────────────────────────────┐
│ 沙箱环境（安全实验室）                     │
│  - 本地文件系统 / Docker 容器 / K8s Pod   │
│  - 执行代码、读写文件、运行命令            │
└─────────────────────────────────────────┘
```

关键洞察：**Lead Agent 是唯一的入口，所有功能都通过它编排**。这确保了每条路径都经过中间件管道——记忆、安全审计、错误处理一个不落。

## 1.2 请求生命周期：一个用户消息的完整旅程

当用户在前端输入 "帮我研究 2026 年 AI Agent 框架的发展趋势"，以下事件按序发生：

**Phase 1：前端 → 后端**
1. 前端 `useThreadStream` hook 通过 LangGraph SDK 发起 SSE 连接
2. 请求经 Nginx（端口 2026）转发到 FastAPI Gateway
3. Gateway 的 `start_run()` 创建一个 `RunRecord`，分配唯一 run_id

**Phase 2：Agent 构建**
4. `resolve_agent_factory()` 找到注册的 `deerflow.agents:make_lead_agent`
5. `make_lead_agent()` 构建 LangGraph 状态图：
   - 加载配置中的模型（如 GLM-4.7）
   - 通过 `get_available_tools()` 收集所有工具（web_search、bash、file ops、MCP 工具等）
   - 生成系统提示词（注入技能描述、用户记忆）
   - 按序组装 18 个中间件

**Phase 3：Agent 执行**
6. `agent.astream()` 以流式模式执行 LangGraph 状态机
7. 请求依次穿过中间件管道：
   - `ThreadDataMiddleware` → 创建线程工作目录
   - `SandboxMiddleware` → 获取沙箱环境
   - `MemoryMiddleware` → 注入用户历史记忆
   - `SummarizationMiddleware` → 如果上下文过长则压缩
   - ... 其余中间件处理各自关注点
8. Lead Agent 决定行动：
   - 直接回答 → 生成消息
   - 需要搜索 → 调用 `web_search` 工具
   - 任务复杂 → 创建子 Agent 并行处理
   - 需要执行代码 → 在沙箱中运行

**Phase 4：结果返回**
9. `StreamBridge` 将事件流推送到 SSE 连接
10. 前端实时渲染：消息气泡、工具调用状态、中间结果、最终回答

这条链路上的**确定性**体现在：状态机节点是预定义的、中间件顺序是固定的、工具调用协议是标准化的。LLM 只在「决策点」发挥作用——选择哪个工具、生成什么内容。

## 1.3 核心目录结构解读

```
deer-flow/
├── config.yaml              # ⭐ 全局配置中心（模型、工具、沙箱、记忆...）
├── extensions_config.json   # MCP 服务器和技能配置
├── Makefile                 # 统一开发命令入口
│
├── backend/
│   ├── packages/harness/    # ⭐ 核心 Agent 框架（deerflow-harness 包）
│   │   └── deerflow/
│   │       ├── agents/      #    Lead Agent + 中间件
│   │       ├── subagents/   #    子 Agent 管理
│   │       ├── tools/       #    内置工具注册
│   │       ├── skills/      #    技能系统
│   │       ├── memory/      #    记忆系统
│   │       ├── sandbox/     #    沙箱执行
│   │       ├── models/      #    LLM 模型适配
│   │       ├── mcp/         #    MCP 协议集成
│   │       └── community/   #    社区工具（Tavily、Jina 等）
│   │
│   └── app/gateway/         # FastAPI 网关应用
│       ├── app.py           #    应用入口 & 生命周期
│       ├── routers/         #    API 路由（threads、models、memory...）
│       └── services.py      #    业务逻辑层
│
├── frontend/
│   ├── src/app/             # Next.js App Router 页面
│   ├── src/components/      # React 组件
│   ├── src/core/            # 业务逻辑（API 客户端、hooks、类型）
│   └── src/styles/          # 样式
│
├── skills/
│   └── public/              # 内置技能（Markdown 定义）
│
└── docker/                  # Docker / Nginx 配置
```

**重要区分**：`packages/harness/` 是**框架**（可被其他项目复用），`app/gateway/` 是**应用**（DeerFlow 自己的业务实现）。贡献核心代码主要改 harness，贡献功能特性主要改 gateway 或 skills。

## 1.4 本地运行

### 前置条件
- Python 3.12+
- Node.js 22+
- pnpm（`npm install -g pnpm`）
- uv（Python 包管理器，`curl -LsSf https://astral.sh/uv/install.sh | sh`）

### 步骤

```bash
# 1. 克隆仓库（如果还没有）
git clone https://github.com/bytedance/deer-flow.git && cd deer-flow

# 2. 一键安装所有依赖
make install

# 3. 配置 LLM 模型（编辑 config.yaml）
# 至少需要一个模型配置，填入 API Key
# 默认已配置 ZhipuAI GLM-4.7，需要设置环境变量：
export ZHIPU_API_KEY="your-api-key"

# 4. 启动开发模式（前端 + 后端 + Nginx）
make dev

# 5. 访问 http://localhost:2026
```

### 验证清单
- [ ] 前端页面加载成功（localhost:2026）
- [ ] 能发送消息并收到流式响应
- [ ] 工具调用正常（如 web_search）
- [ ] 沙箱执行正常（如让 Agent 创建文件）

### 常用开发命令

| 命令 | 用途 |
|------|------|
| `make dev` | 启动开发模式（热重载） |
| `make stop` | 停止所有服务 |
| `make doctor` | 检查配置和依赖 |
| `make check` | 检查必要工具是否安装 |

## 1.5 配置要点速览

`config.yaml` 是 DeerFlow 的**神经中枢**，几个关键区域：

```yaml
# 模型配置 — 决定用哪个 LLM
models:
  - name: glm-4.7
    use: langchain_openai:ChatOpenAI  # LangChain 类路径
    model: glm-5.1
    api_key: $ZHIPU_API_KEY           # 环境变量引用

# 沙箱配置 — 决定代码在哪里执行
sandbox:
  use: deerflow.sandbox.local:LocalSandboxProvider  # 本地模式
  # use: deerflow.community.aio_sandbox:AioSandboxProvider  # Docker 模式

# 记忆配置 — 决定是否跨会话记住用户
memory:
  enabled: true
  storage_path: memory.json

# 技能配置 — 决定 Agent 会什么
skills:
  container_path: /mnt/skills
```

注意 `use` 字段的模式：`package.module:ClassName`。这是 DeerFlow 的**统一解析协议**——模型、工具、沙箱提供者都通过这种方式指定实现类，实现了高度可插拔。

## 思考题

**题 1**：DeerFlow 选择「单一 Lead Agent 作为唯一入口，所有请求都经过 18 个中间件」的架构，而不是「每个功能独立暴露为一个 API 端点」的微服务架构。这种设计有什么优势和代价？

> **参考答案**：优势是**一致性和可观测性**——每条路径都经过记忆注入、安全审计、错误处理，不会出现「某个端点忘了加认证」的问题。中间件管道也便于横向扩展能力（加一个中间件就全局生效）。代价是**耦合度**——所有中间件共享同一个请求上下文，中间件之间的执行顺序可能产生隐式依赖。此外，中间件链过长会影响单次请求的延迟。这是一个经典的「管道/过滤器」架构 vs 微服务架构的权衡，DeerFlow 的选择反映了「Agent 系统中一致性和可控性比独立部署更重要」的设计判断。

**题 2**：`config.yaml` 中的 `use: langchain_openai:ChatOpenAI` 使用了动态类解析（从字符串加载 Python 类）。这种模式在框架设计中很常见（Django 的 `MIDDLEWARE`、LangChain 的 `tool`），但它引入了什么风险？DeerFlow 可能如何缓解？

> **参考答案**：主要风险是**运行时错误前置到配置阶段**——拼写错误的类路径在启动时才会暴露，而不是导入时。此外还有**安全性**风险——如果配置文件可被外部修改，可能加载恶意代码。缓解手段包括：启动时的 schema 验证（`make doctor` 命令）、类路径白名单机制、以及将配置解析限制在已知包范围内。这也是「约定优于配置」与「显式优于隐式」之间的工程权衡——DeerFlow 选择了显式配置换取灵活性。

**题 3**：如果你要让 DeerFlow 支持一个全新的 LLM 提供商（比如某国产模型），你需要修改哪些文件？不需要修改哪些文件？

> **参考答案**：只需要修改 **`config.yaml`**——添加一个新的 `models` 条目，设置 `use` 为对应的 LangChain Chat 类（如已存在）或自定义适配器类路径。不需要修改任何 Agent 代码、中间件代码或前端代码。这正是 DeerFlow 架构的核心优势之一：**模型是可替换的组件，Agent 编排逻辑与具体 LLM 解耦**。如果新提供商需要特殊处理（如 thinking 模式），可能需要新增一个 `Patched*` 适配器类（参考 `deerflow/models/patched_openai.py`），但这也是在模型层局部修改，不影响上层架构。
