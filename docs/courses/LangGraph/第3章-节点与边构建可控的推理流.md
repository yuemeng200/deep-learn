# 第3章：节点与边——构建可控的推理流

## 回扣本质

前两章我们有了图的骨架（StateGraph）和血液（State）。本章要做的是**画出真正的流程图**——定义每个节点做什么、节点之间如何连接、在什么条件下走哪条路。这是 LangGraph "显式控制流"理念的直接落地：你画出来的图，就是 Agent 实际走的路。

---

## 节点：做一件事，做好一件事

### 节点的本质

节点就是一个 Python 函数，签名固定：

```python
def node_name(state: YourState) -> dict:
    # 读取 state 中需要的信息
    # 执行逻辑（调用 LLM、调用工具、做计算...）
    # 返回要更新的字段
    return {"field_to_update": new_value}
```

### 节点粒度的设计哲学

一个关键的工程决策：**一个节点应该多大？**

```
❌ 太粗：一个节点干了"规划+搜索+分析"三件事
   → 无法在中间插入条件判断、人工审核、checkpoint

❌ 太细：每次 LLM 调用都是一个节点
   → 图变得巨大且难以理解，过度工程化

✅ 合适：一个节点 = 一个"业务动作"
   → 规划是一个节点，搜索是一个节点，分析是一个节点
   → 每个节点完成后，系统可以做决策：继续？换路？暂停？
```

**判断标准：在这个节点完成之后，系统是否可能需要做一个"分支决策"？** 如果是，那这里就应该是一个节点边界。

### 节点的三种模式

```python
# 模式一：LLM 节点——调用大模型
def planner(state: ResearchState) -> dict:
    response = llm.invoke(f"为以下主题制定研究计划：{state['topic']}")
    return {"plan": parse_plan(response.content)}

# 模式二：工具节点——调用外部服务
def searcher(state: ResearchState) -> dict:
    results = []
    for query in state["search_queries"]:
        results.extend(search_api.search(query))
    return {"sources": results}

# 模式三：逻辑节点——纯计算/判断（不调 LLM）
def increment_counter(state: ResearchState) -> dict:
    return {"iteration_count": state["iteration_count"] + 1}
```

生产环境中，**将 LLM 调用和工具调用分离到不同节点**是一个重要的最佳实践。原因：
- LLM 节点可能需要重试（模型超时）
- 工具节点可能需要人工审批（敏感操作）
- 分开后可以独立监控各节点的延迟和成功率

## 边：连接节点的三种方式

### 方式一：普通边（无条件流转）

```python
graph.add_edge("planner", "searcher")  # planner 完成后，一定去 searcher
```

适用于：流程中没有分支的线性步骤。

### 方式二：条件边（动态路由）

这是 LangGraph 最强大的能力之一——**根据 State 决定下一步去哪**。

```python
def route_after_analysis(state: ResearchState) -> str:
    """根据质量评分决定下一步"""
    if state["quality_score"] >= 7:
        return "reporter"
    if state["iteration_count"] >= 3:
        return "reporter"      # 超过最大重试次数，强制结束
    return "searcher"              # 质量不够，继续搜索

graph.add_conditional_edges(
    "analyzer",                    # 从哪个节点出发
    route_after_analysis,          # 路由函数
    {                              # 路由映射：返回值 → 目标节点
        "reporter": "reporter",
        "searcher": "searcher",
    }
)
```

路由函数的设计要点：
- 接收完整 State，返回一个字符串（目标节点名）
- 必须是**确定性的**——相同的 State 应该返回相同的结果
- 不要在路由函数中修改 State（它不是节点，不能写状态）

### 方式三：START 和 END

```python
graph.add_edge(START, "planner")     # 图的入口
graph.add_edge("reporter", END)      # 图的出口
```

`END` 也可以作为条件边的目标：

```python
def should_end(state: ResearchState) -> str:
    if state["report"]:
        return END
    return "continue_research"
```

## 动手：构建研究助手的核心流程

现在用真实的 LLM 调用来实现"规划 → 搜索 → 分析"的三节点流程：

```python
from typing import TypedDict, Annotated
from operator import add
from langgraph.graph import StateGraph, START, END
from langchain_openai import ChatOpenAI
from langchain_core.messages import HumanMessage, SystemMessage

llm = ChatOpenAI(model="gpt-4o-mini", temperature=0)


# ===== State 定义 =====
class ResearchState(TypedDict):
    topic: str
    plan: list[str]
    search_queries: list[str]
    sources: Annotated[list[dict], add]
    analysis: str
    quality_score: int
    iteration_count: int
    report: str


# ===== 节点实现 =====
def planner(state: ResearchState) -> dict:
    """规划节点：根据主题生成研究计划"""
    response = llm.invoke([
        SystemMessage(content="你是一个研究规划专家。根据用户的研究主题，生成3-5个具体的研究步骤。每个步骤一行，不要编号。"),
        HumanMessage(content=f"研究主题：{state['topic']}")
    ])
    plan = [step.strip() for step in response.content.strip().split("\n") if step.strip()]
    queries_response = llm.invoke([
        SystemMessage(content="根据研究计划，生成2-3个搜索引擎查询词。每个一行，不要编号。"),
        HumanMessage(content=f"研究计划：{chr(10).join(plan)}")
    ])
    queries = [q.strip() for q in queries_response.content.strip().split("\n") if q.strip()]
    return {
        "plan": plan,
        "search_queries": queries,
        "iteration_count": 0,
    }


def searcher(state: ResearchState) -> dict:
    """搜索节点：模拟搜索（生产中替换为真实搜索 API）"""
    results = []
    for query in state["search_queries"]:
        response = llm.invoke([
            SystemMessage(content="模拟搜索引擎，为给定查询生成2条相关结果。每条包含标题和摘要，用'---'分隔。"),
            HumanMessage(content=f"搜索：{query}")
        ])
        results.append({
            "query": query,
            "content": response.content,
        })
    return {"sources": results}


def analyzer(state: ResearchState) -> dict:
    """分析节点：综合搜索结果进行分析，并自我评分"""
    sources_text = "\n\n".join([
        f"[查询: {s['query']}]\n{s['content']}" for s in state["sources"]
    ])
    analysis_response = llm.invoke([
        SystemMessage(content="你是研究分析师。根据搜索结果，围绕研究主题进行综合分析。"),
        HumanMessage(content=f"主题：{state['topic']}\n\n搜索结果：\n{sources_text}")
    ])
    score_response = llm.invoke([
        SystemMessage(content="评估以下分析的质量和完整性，给出1-10的评分。只输出数字。"),
        HumanMessage(content=analysis_response.content)
    ])
    try:
        score = int(score_response.content.strip())
    except ValueError:
        score = 5
    return {
        "analysis": analysis_response.content,
        "quality_score": score,
        "iteration_count": state["iteration_count"] + 1,
    }


def reporter(state: ResearchState) -> dict:
    """报告节点：生成最终报告"""
    response = llm.invoke([
        SystemMessage(content="根据研究分析，撰写一份结构化的研究报告。包含：概述、关键发现、结论。"),
        HumanMessage(content=f"主题：{state['topic']}\n\n分析：{state['analysis']}")
    ])
    return {"report": response.content}


# ===== 路由函数 =====
def route_after_analysis(state: ResearchState) -> str:
    """核心路由逻辑"""
    if state["quality_score"] >= 7:
        return "reporter"
    if state["iteration_count"] >= 3:
        return "reporter"
    return "searcher"


# ===== 构建图 =====
graph_builder = StateGraph(ResearchState)

graph_builder.add_node("planner", planner)
graph_builder.add_node("searcher", searcher)
graph_builder.add_node("analyzer", analyzer)
graph_builder.add_node("reporter", reporter)

graph_builder.add_edge(START, "planner")
graph_builder.add_edge("planner", "searcher")
graph_builder.add_edge("searcher", "analyzer")
graph_builder.add_conditional_edges("analyzer", route_after_analysis)
graph_builder.add_edge("reporter", END)

graph = graph_builder.compile()

result = graph.invoke({"topic": "LangGraph 在生产环境中的最佳实践"})
print(result["report"])
```

### 图的拓扑结构

```
START → planner → searcher → analyzer ─┐
                     ↑                  │
                     │    质量 < 7      │
                     │    且次数 < 3    │
                     └──────────────────┘
                                        │
                          质量 >= 7     │
                          或次数 >= 3   │
                                        ▼
                                    reporter → END
```

## 条件边的进阶模式

### 模式一：多路分发

```python
def route_by_topic_type(state: ResearchState) -> str:
    """根据主题类型选择不同的搜索策略"""
    if "代码" in state["topic"] or "编程" in state["topic"]:
        return "code_searcher"
    elif "论文" in state["topic"] or "学术" in state["topic"]:
        return "academic_searcher"
    else:
        return "web_searcher"

graph.add_conditional_edges(
    "planner",
    route_by_topic_type,
    {
        "code_searcher": "code_searcher",
        "academic_searcher": "academic_searcher",
        "web_searcher": "web_searcher",
    }
)
```

### 模式二：省略映射字典

当路由函数的返回值和节点名一致时，可以省略映射：

```python
# 这两种写法等价：
graph.add_conditional_edges("analyzer", route_after_analysis, {
    "reporter": "reporter",
    "searcher": "searcher",
})

graph.add_conditional_edges("analyzer", route_after_analysis)
# ← 框架自动将返回值作为目标节点名
```

### 模式三：路由到 END

```python
from langgraph.graph import END

def should_finish(state: ResearchState) -> str:
    if state["report"]:
        return END
    return "continue"

graph.add_conditional_edges("check_done", should_finish, {
    END: END,
    "continue": "next_step",
})
```

## 节点设计的工程准则

### 准则一：节点应该是幂等的

同一个 State 输入，节点应该产出一致的结果（或者至少不会破坏系统）。这对于错误恢复至关重要。

```python
# ❌ 非幂等：每次执行都往外部系统写数据
def bad_searcher(state):
    db.insert({"query": state["query"], "time": now()})
    return {"sources": [...]}

# ✅ 幂等：搜索本身是幂等的
def good_searcher(state):
    results = search_api.search(state["query"])
    return {"sources": results}
```

### 准则二：节点之间通过 State 通信，而非闭包

```python
# ❌ 通过闭包共享可变状态
shared_results = []

def searcher(state):
    shared_results.append(search(...))
    return {}

# ✅ 所有通信走 State
def searcher(state):
    results = search(...)
    return {"sources": results}
```

### 准则三：错误处理在节点内完成

```python
def searcher(state: ResearchState) -> dict:
    try:
        results = search_api.search(state["search_queries"])
        return {"sources": results}
    except SearchAPIError:
        return {"sources": [{"query": "FAILED", "content": "搜索服务暂不可用"}]}
```

## 章末思考题

**题目一：节点粒度的权衡**

在我们的实现中，`analyzer` 节点同时做了两件事：分析搜索结果 + 自我评分。如果把它拆成 `analyzer` 和 `scorer` 两个节点，有什么好处和坏处？你会怎么决策？

> **参考答案**：**好处**：①可以独立重试——如果评分 LLM 调用失败，不需要重新执行整个分析；②可以在分析和评分之间插入人工审核；③观测性更好——能分别监控两个步骤的延迟。**坏处**：①图变复杂了，多了一个节点和一条边；②如果这两步之间永远不需要做决策或干预，拆分就是过度工程。**决策标准**：如果评分逻辑未来可能换成非 LLM 方案（如规则引擎），或者你需要 A/B 测试不同的评分策略，就值得拆分。否则保持合并更简洁。

**题目二：条件边的确定性**

路由函数为什么必须是确定性的（相同 State → 相同结果）？如果你在路由函数里调用 LLM 来"决定下一步去哪"，会引入什么问题？

> **参考答案**：三个问题：①**可重放性丧失**——从 checkpoint 恢复后，同一个 State 可能走不同的路径；②**调试困难**——你无法通过查看 State 来确定 Agent 会走哪条路；③**测试困难**——无法写确定性的单元测试。正确做法是：让 LLM 的决策结果写入 State（比如 `next_action` 字段），然后路由函数只读取这个字段做确定性路由。**把"决策"放在节点里，把"执行决策"放在条件边里。**

**题目三：如何处理"条件边所有分支都不匹配"的情况？**

假设你的路由函数遇到了一个意料之外的 State 值（比如 `quality_score` 是 None），而你没有处理这个 case。LangGraph 会怎么做？你应该如何防御？

> **参考答案**：LangGraph 会抛出异常——路由函数返回的字符串不在条件边的映射中时，图执行会崩溃。防御策略：①**设置默认分支**——路由函数的最后一个 `return` 应该是兜底的安全路径；②**在节点中保证字段有效性**——analyzer 节点保证 `quality_score` 一定是 int；③**State 初始化时给默认值**。核心思想：**路由函数必须是全函数（total function）——对任何可能的输入都有确定的输出。**
