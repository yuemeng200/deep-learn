# 第2章：从文字到数字——Tokenization 与 Embedding

## 回扣本质

上一章我们看到了 LLM 工作的全景图。本章深入第一个环节：模型连"文字"都不认识，它只认数字。**如何把人类语言转化为可计算的形式，同时尽可能保留语义信息**——这是一切的起点，也是"下一个词预测器"能工作的前提。

## 正文

### 一、Tokenization：为什么不直接按字/词切？

你可能会想：中文按字切，英文按空格切，不就行了？实际没这么简单。

**按字切的问题：**
- 序列太长。"人工智能的未来发展方向"按字切是 10 个 token。序列越长，计算量越大（Attention 的计算量与序列长度的平方成正比）
- 单个字缺少语义。"人"、"工"单独看没什么意义

**按词切的问题：**
- 词表爆炸。英语单词量轻松上百万，加上各种变形（running, ran, runs）更是无穷无尽
- 遇到没见过的词（OOV, Out-of-Vocabulary）就傻了

**实际方案：子词切分（Subword Tokenization）**

核心思想：**高频词保留完整，低频词拆成更小的片段**。

比如 BPE（Byte Pair Encoding）算法：
- "understanding" → ["under", "stand", "ing"]
- "cat" → ["cat"]（高频，保留完整）
- "tokenization" → ["token", "ization"]

这是一个**效率和覆盖面的折衷**：
- 常见词作为整体，效率高
- 罕见词拆开，用已有片段拼，永远不会遇到"不认识的词"
- 词表大小可控（通常 3-10 万）

### 二、Tokenization 对实践的影响

这不是纯理论——它直接影响你用 LLM 的效果：

**1. Token ≠ 字/词**

"ChatGPT" 可能被切成 ["Chat", "G", "PT"]，也就是 3 个 token。这意味着：
- API 按 token 计费，不是按字数
- 上下文窗口 "128K tokens" 不等于 128K 个字

**2. 中文通常比英文"贵"**

一个汉字经常占 1-2 个 token，而英文一个常见词也大概 1 个 token。同样的信息量，中文消耗的 token 更多。

**3. 模型对 token 边界敏感**

- 让 GPT 数"strawberry 里有几个 r"——它可能答错，因为"strawberry"被切成了 ["straw", "berry"]，模型看不到单个字母
- 代码中的变量名可能被切碎，影响理解

### 三、Embedding：从编号到语义空间

Tokenization 之后，每个 token 是一个整数编号（比如"猫"=3471）。但编号本身不含语义——3471 和 3472 在数值上相邻，但对应的词可能毫无关系。

**Embedding 做的事**：维护一个巨大的查找表（矩阵），每个 token 编号对应一行，这一行就是它的向量表示。

```
Token "猫" → 编号 3471 → 查表 → [0.23, -0.87, 0.45, ..., 0.12]  (几千维)
Token "狗" → 编号 8832 → 查表 → [0.21, -0.82, 0.51, ..., 0.09]  (相近！)
Token "经济" → 编号 1056 → 查表 → [-0.65, 0.33, -0.28, ..., 0.77]  (很不同)
```

**为什么向量能表达语义？**

因为训练。模型在训练过程中发现："猫"和"狗"经常出现在相似的上下文中（"喂___"、"带___散步"、"可爱的___"），于是它们的向量被梯度下降逐渐推到相近的位置。

这不是人为设定的，而是**从数据中自动学出来的**。

### 四、位置编码：弥补"顺序"信息

向量解决了"这个词是什么意思"，但还有一个问题：**词的顺序**。

"狗咬人"和"人咬狗"，token 完全一样，只是顺序不同。但 Embedding 查表时不考虑位置——编号 3471 不管在句首还是句尾，查出来的向量一样。

**解决方案**：在 embedding 向量上叠加一个"位置信号"，让模型知道每个 token 处于序列的第几个位置。

```
最终输入向量 = token_embedding + position_encoding
```

位置编码的具体实现有很多种（固定的正弦函数、可学习的向量、RoPE 等），但核心目的一样：**让相同的词在不同位置有不同的表示。**

> **扩展：RoPE（旋转位置编码）**
> 现代 LLM（LLaMA、GPT-4 等）普遍使用 RoPE。它的巧妙之处在于：不直接编码"绝对位置"，而是编码"两个 token 之间的相对距离"。这让模型更容易泛化到训练时没见过的长度——这也是"长上下文窗口"技术的基础之一。

### 五、与实战项目的关联

回到客服场景：
- 用户输入"我的订单号是 SF20240315X87654321，一周了还没到"——这个长订单号大概率被切成很多碎片 token，模型可能无法精确"记住"它。这就是为什么实际系统中，结构化信息（订单号、日期）通常不让 LLM 处理，而是用代码提取后查数据库
- 中文客服 vs 英文客服，同样的上下文窗口能容纳的对话轮数不同，因为中文 token 效率更低

## 思考题

**Q1：为什么大多数 LLM 不擅长做精确的字符级操作（比如数字母、倒写单词）？**

参考答案：因为 tokenization 在字符级别之上工作。模型看到的不是单个字母，而是子词片段。"strawberry" 被切成 ["straw","berry"] 后，模型无法直接"看到"里面有几个 r。它只能基于记忆和推理间接判断，所以经常出错。这也是为什么一些场景需要让模型"逐字拼写"来强制字符级处理。

**Q2：如果两个完全不同含义的词（如英文 "bank" 的河岸/银行含义），它们的 embedding 向量是相同的还是不同的？**

参考答案：**在 embedding 层是相同的**——因为 embedding 只看 token 本身，不看上下文。"bank" 不管什么含义，查表查出的是同一个向量。消歧发生在后面的 Transformer 层：通过 Attention 看到上下文（"river bank" vs "bank account"），同一个初始向量会被加工成完全不同的表示。这正是第 3 章要讲的内容。

**Q3：为什么 LLM 公司对自己的 tokenizer 都非常在意，经常针对特定语言优化？**

参考答案：因为 tokenization 效率直接影响成本和能力。如果中文 tokenizer 效率低（每个字需要 2-3 个 token），那么相同的上下文窗口能装的中文内容更少，API 调用成本更高，模型"思考"的空间也更小。优化 tokenizer 让目标语言用更少的 token 表达同样的信息，是提升性价比的关键手段。
