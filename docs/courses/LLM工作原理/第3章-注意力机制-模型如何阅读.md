# 第3章：注意力机制——模型如何"阅读"

## 回扣本质

上一章我们把文字变成了向量，但每个向量只知道"自己是谁"，不知道上下文。本章解决的核心问题是：**模型如何让每个词"看到"序列中其他相关的词，从而理解语境？** 这是"下一个词预测器"能做出准确预测的关键——预测下一个词，必须先理解前文说了什么。

## 正文

### 一、为什么需要 Attention？

考虑这句话："小明把书还给了图书馆，因为**它**已经过期了。"

"它"指的是什么？是"书"。人类秒懂，但对模型来说，需要一个机制让"它"这个 token 能够"回头看"前面的所有词，找到最相关的那个。

在 Attention 出现之前，RNN（循环神经网络）是逐词处理的——像从左到右念一遍，越早的词记忆越模糊。Attention 的突破在于：**允许每个词直接与序列中任意其他词建立联系**，无论距离多远。

### 二、Attention 的直觉：提问-匹配-汇总

把 Attention 理解为一个**信息检索**过程：

1. **每个词发出一个"提问"（Query）**："我需要什么信息来补充自己的理解？"
2. **每个词提供一个"标签"（Key）**："我能提供什么信息？"
3. **每个词准备一个"内容"（Value）**："如果你需要我，这是我的详细信息。"

然后：
- 用 Query 和所有 Key 做匹配（点积），得到"相关性得分"
- 得分高的词，它的 Value 会被更多地采纳
- 最终每个词得到一个"综合了相关上下文信息"的新向量

**类比**：你在图书馆找资料。你心中有个问题（Query），每本书封面有摘要（Key），你扫一遍所有书的摘要，挑出最相关的几本，仔细读它们的内容（Value），最终整合出你的答案。

### 三、Q、K、V 从哪来？

```
Q = X · W_Q    （同一个输入，左乘不同的权重矩阵）
K = X · W_K
V = X · W_V
```

**X** 是上一层的输出向量（或第一层时的 embedding）。**W_Q、W_K、W_V** 是训练学出来的权重矩阵。

**为什么要三个不同的矩阵，而不是直接用 X 自己？**

因为"我需要什么"和"我能提供什么"是两种不同的角色。一个词作为"提问者"和作为"被查阅者"时，应该呈现不同的侧面。用三个矩阵让模型能灵活学习这种角色分离。

### 四、注意力得分：谁和谁相关？

```
注意力得分 = softmax(Q · K^T / √d)
```

直觉：
- **Q · K^T（点积）**：衡量"我的提问"和"你的标签"有多匹配。向量方向越一致，点积越大
- **÷ √d（缩放）**：防止维度太高时点积数值太大，导致 softmax 后概率过于集中（一个词独占所有注意力）
- **softmax**：把得分归一化为概率分布。所有得分加起来 = 1，表示"注意力的分配比例"

结果是每个词对其他所有词有一个 0-1 之间的注意力权重。

### 五、Multi-Head Attention：同时关注多种关系

一个注意力头只能学一种"关注模式"。但语言中的关系是多种多样的：

- 句法关系（主语-动词）
- 指代关系（代词-被指物）
- 语义关系（形容词-名词）
- 位置关系（相邻词对）

**解决方案：Multi-Head Attention**——并行运行多个独立的 Attention（每个叫一个"头"），每个头有自己的 W_Q、W_K、W_V，学习不同的关注模式。最后把所有头的结果拼接起来。

```
head_1 = Attention(X·W_Q1, X·W_K1, X·W_V1)    // 可能学会关注主语
head_2 = Attention(X·W_Q2, X·W_K2, X·W_V2)    // 可能学会关注近距离词
...
output = Concat(head_1, head_2, ..., head_n) · W_O
```

典型的 LLM 有 32-128 个注意力头。

### 六、因果遮罩：为什么模型只能"往前看"

LLM 在生成时，第 5 个词还没生成时，不应该看到第 6、7、8 个词（它们还不存在）。所以训练时使用**因果遮罩（Causal Mask）**：强制每个位置只能 attend 到它之前（含自身）的位置。

```
位置 1：只能看 [1]
位置 2：只能看 [1, 2]
位置 3：只能看 [1, 2, 3]
...
```

这就是"decoder-only"架构的核心约束，也是为什么 GPT 系列叫"Generative Pre-trained Transformer"——它是为**生成**（从左到右）而设计的。

> **扩展：Encoder vs Decoder**
> BERT 这类模型没有因果遮罩——每个词可以同时看前后文（双向），适合理解任务（分类、抽取）。GPT 只能看前文（单向），适合生成任务。这就是为什么 BERT 擅长做 NLU（理解），GPT 擅长做 NLG（生成）。

### 七、与实战项目的关联

回到客服场景：
- **上下文窗口限制**的本质：Attention 需要与所有前文 token 计算关联，序列越长，计算量（和显存）越大。这就是为什么上下文窗口有上限——不是存储不下，而是算不过来
- **RAG 的核心逻辑**：用户问"订单什么时候到"，你把订单信息拼进 prompt，Attention 机制自然会让模型在回答时"注意到"这些检索来的信息

## 思考题

**Q1：为什么 Attention 的计算量与序列长度的平方成正比？这对实际使用有什么影响？**

参考答案：因为每个 token 的 Query 都要和所有 token 的 Key 做点积。n 个 token，就是 n×n 次计算。这意味着输入从 1K 变到 10K token，计算量变为 100 倍。实际影响：长对话越来越慢越来越贵；超长文档一次放不下；KV Cache 等优化技术因此成为工程核心。

**Q2：如果让你设计客服系统，对话已经进行了 50 轮，但上下文窗口装不下了。你会怎么处理？为什么？**

参考答案：几种策略各有权衡——① 滑动窗口：只保留最近 N 轮，简单但丢失早期上下文 ② 摘要压缩：用 LLM 把早期对话总结成几句话放在开头，保留关键信息但可能丢细节 ③ 关键信息提取：把早期对话中的实体（订单号、问题描述）提取为结构化数据放在 system prompt，兼顾效率和信息保留。实际系统通常组合使用。

**Q3：为什么"把相关信息放在 prompt 开头或结尾"比放在中间效果更好（Lost in the Middle 现象）？**

参考答案：虽然 Attention 理论上可以关注任意位置，但实际训练中，模型对靠近"当前生成位置"和"序列开头"的内容注意力更强（因为训练数据中重要信息往往出现在这些位置）。中间位置的信息更容易被"淹没"。这对 RAG 系统设计有直接指导意义：检索到的关键信息应该放在 prompt 的显眼位置。
