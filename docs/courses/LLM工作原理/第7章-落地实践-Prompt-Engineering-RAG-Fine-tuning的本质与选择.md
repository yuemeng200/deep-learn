# 第7章：落地实践——Prompt Engineering / RAG / Fine-tuning 的本质与选择

## 回扣本质

前六章我们建立了对 LLM 完整工作原理的理解。本章回到核心目标：**在实际工作中，如何选择正确的方式让 LLM 为你所用？** Prompt Engineering、RAG、Fine-tuning 本质上是在不同层面解决同一个问题——"如何让一个通用的下一个词预测器，在你的特定场景中表现好"。

## 正文

### 一、三种方式的本质区别

| 方式 | 本质 | 改变了什么 | 类比 |
|------|------|-----------|------|
| **Prompt Engineering** | 改变输入 | 模型不变，通过更好的前文引导更好的续写 | 给一个人更清晰的指令 |
| **RAG** | 补充信息 | 模型不变，把外部知识拼进输入 | 给一个人参考资料 |
| **Fine-tuning** | 改变模型 | 修改模型权重，改变它的知识或行为 | 培训一个人 |

三者不是互斥的，通常组合使用。从左到右，成本递增、门槛递增、效果上限也递增。

### 二、Prompt Engineering：改变输入

**原理回顾**：LLM 是自回归模型，前文决定续写方向。

**核心技巧和"为什么有效"：**

1. **System Prompt**：利用角色上下文引导生成
2. **Few-shot Examples**：利用 in-context learning
3. **Chain-of-Thought**：给模型打草稿的空间
4. **结构化输出指令**：利用模型对格式的遵循能力

**边界**：无法注入新知识、受上下文窗口限制、可靠性有限。

### 三、RAG（检索增强生成）：补充信息

**流程：**
```
用户提问 → [检索相关文档] → [把文档拼进 prompt] → [模型基于文档生成回答]
```

**为什么有效**：Attention 让模型能"看到"检索结果，相当于"开卷考试"。

**优势**：知识可实时更新、可溯源、成本低
**局限**：检索质量是瓶颈、受上下文窗口限制、无法改变模型行为

### 四、Fine-tuning：改变模型

**什么时候需要**：
- 需要特定风格/格式
- 需要特定推理模式
- 需要极致响应速度
- 需要模型"内化"知识

**方式对比**：

| 方式 | 改了什么 | 数据量 | 成本 |
|------|---------|--------|------|
| 全量 fine-tuning | 所有参数 | 万级 | 高 |
| LoRA | 低秩补丁 | 千级 | 中 |
| Adapter | 插入小型网络 | 千级 | 中 |

**风险**：灾难性遗忘、过拟合、破坏对齐

### 五、决策框架

```
├─ 模型知识够用，只需更好引导？ → Prompt Engineering
├─ 需要最新/私有知识？ → RAG
├─ 需要改变行为模式？ → Fine-tuning
└─ 以上都需要？ → 组合使用
```

### 六、客服场景完整方案

```
┌─────────────────────────────────────────────┐
│              System Prompt                    │
│  (角色设定 + 输出格式 + 安全约束)            │
├─────────────────────────────────────────────┤
│    用户问题 + RAG 检索结果                    │
│  (订单信息 + 相关FAQ + 产品知识)             │
├─────────────────────────────────────────────┤
│         Fine-tuned Chat Model               │
│  (在客服对话数据上做 LoRA fine-tuning)       │
├─────────────────────────────────────────────┤
│           输出 + 后处理                       │
│  (格式校验 + 安全过滤 + 日志记录)            │
└─────────────────────────────────────────────┘
```

**决策理由**：RAG 解决知识时效性、LoRA 教客服风格、Prompt 做精细控制、7B-14B 模型保性价比。

> **扩展：何时 Prompt Engineering 就够了？**
> 通用知识 + 简单格式/风格 + 不需要极高一致性 → 直接 prompt 就行。先试最简单的方案，不够了再加复杂度。

## 思考题

**Q1：一家公司说"我们要用 fine-tuning 让模型学会我们的产品知识"。这个决策可能有什么问题？**

参考答案：① 产品知识经常更新，每次都要重新 fine-tune ② Fine-tuning 可能导致幻觉 ③ 无法溯源。更好的替代：用 RAG 做知识检索，fine-tuning 只教"怎么利用检索结果回答"（行为模式），而非"记住所有信息"（知识注入）。

**Q2：RAG 系统中，"检索"这一步失败了会怎样？如何降低这个风险？**

参考答案：模型会基于自身知识回答或幻觉。降低风险：① 多路召回（关键词 + 向量 + 重排序） ② 相似度阈值——低于阈值时回答"我需要更多信息" ③ 优化文档切分粒度 ④ query 改写。

**Q3：基于本课程所学，如果给你一个新的 LLM 应用场景，你会按什么顺序尝试？**

参考答案：渐进式，从简单到复杂：① Prompt engineering（zero-shot → few-shot → CoT） ② 加 RAG ③ LoRA fine-tuning ④ 全量 fine-tuning。逻辑：成本递增，先穷尽低成本方案。
