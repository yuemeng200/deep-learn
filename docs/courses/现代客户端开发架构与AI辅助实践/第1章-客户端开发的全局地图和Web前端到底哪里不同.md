# 第 1 章：客户端开发的全局地图，和 Web 前端到底哪里不同

客户端开发的核心不是“换一种语言写界面”，而是在用户设备这个受限、异构、强交互的环境中，组织业务状态、平台能力、网络数据、界面渲染、生命周期、性能和稳定性。

如果你未来主要依赖 AI Coding 做客户端业务迭代，第一件事不是记住更多 API，而是先知道一个需求会穿过哪些系统边界。只有边界清楚，你才能判断 AI 生成的代码是不是放错层、漏掉生命周期、误解平台能力，或者只是在“能跑”的表面上成立。

## 1. 客户端不是“前端的另一种形态”

Web 前端开发者进入客户端时，最容易带着一个默认假设：

> App 页面和 Web 页面差不多，都是拿数据、管状态、渲染 UI、响应用户交互。

这个判断有一半是对的。现代客户端 UI 的确越来越像前端：SwiftUI、Jetpack Compose、React Native、Flutter 都强调声明式 UI、状态驱动、组件化、响应式更新。你过去积累的组件拆分、状态建模、数据流、异步请求、工程协作经验都能迁移。

但另一半差异非常关键：Web 前端运行在浏览器里，而移动客户端运行在操作系统里。

浏览器替你屏蔽了大量平台细节。它提供 DOM、CSS、JS runtime、网络栈、缓存模型、安全沙箱、跨平台渲染能力和统一事件模型。你面对的是浏览器 API，而不是直接面对 iOS 或 Android。

移动客户端则更靠近系统：

- App 会被系统启动、挂起、恢复、杀死。
- 页面会随着导航、后台切换、权限弹窗、横竖屏、内存压力而变化。
- 网络可能断开、超时、弱网、被系统限制后台访问。
- 权限、通知、相册、相机、定位、蓝牙、文件、支付都由系统控制。
- 崩溃、卡顿、内存泄漏、包体、启动耗时会直接影响用户体验。
- 发布链路受应用商店、签名、证书、审核、灰度、版本兼容影响。

所以，Web 和客户端不是“哪个更复杂”的关系，而是复杂度所在的位置不同。

Web 的复杂度更多集中在浏览器、前端框架、构建系统、服务端接口、缓存与多端适配。客户端的复杂度更多来自操作系统、设备能力、生命周期、资源限制、原生 SDK、发布链路和长期运行质量。

## 2. 一张客户端技术地图

可以先把现代客户端体系分成五层：

```text
业务体验层
  页面、交互、业务流程、埋点、错误提示、用户反馈

UI 与状态层
  SwiftUI / UIKit
  Jetpack Compose / Android View
  React Native
  Flutter
  状态管理、导航、表单、列表、动画

业务与数据层
  ViewModel / Store / Use Case / Repository
  网络请求、鉴权、缓存、本地存储、离线、同步

平台能力层
  相机、相册、定位、通知、支付、蓝牙、文件、分享、后台任务
  iOS / Android SDK
  原生模块、插件、Platform Channels

系统与工程层
  生命周期、线程、内存、包体、构建、签名、发布、监控、崩溃、性能
```

这张地图的重点不是层数，而是提醒你：一个看起来很小的业务需求，往往不是只改 UI。

比如“用户点击按钮上传头像”，在 Web 里你可能会想到：

1. 文件选择。
2. 预览图片。
3. 上传接口。
4. 更新用户信息。
5. 展示成功或失败状态。

在客户端里，同一个需求还会牵涉：

1. 相册或相机权限。
2. iOS 和 Android 的权限差异。
3. 图片裁剪、压缩、EXIF 方向。
4. 上传过程中的弱网、后台切换和重试。
5. 本地缓存头像与服务端头像的一致性。
6. 页面返回后是否取消请求。
7. 上传失败后是否保留本地草稿。
8. 埋点、错误码、崩溃监控。
9. 如果页面是 React Native 或 Flutter，是否需要调用原生能力。

这就是客户端开发的本质差异：业务需求经常会穿过 UI、状态、网络、权限、平台能力、生命周期和工程质量多个边界。

## 3. Web、iOS、Android、React Native、Flutter 分别抽象了什么

你可以把这些技术路线理解为不同的“抽象层选择”。

### Web 前端

Web 的核心抽象是浏览器。

浏览器统一了渲染、事件、网络、安全、存储和跨平台能力。React、Vue、Svelte 等框架是在浏览器之上组织 UI 和状态。你写的大多数代码不关心用户是 macOS、Windows、iOS 还是 Android，只关心浏览器是否支持相关能力。

Web 的优势是分发成本低、跨平台强、迭代快、生态成熟。限制是对系统能力的控制较弱，性能和体验受到浏览器环境约束，深度原生能力通常不如 App。

### iOS 原生

iOS 的核心抽象是 Apple 平台。

你面对的是 Swift、SwiftUI、UIKit、Foundation、系统权限、安全沙箱、App 生命周期、Xcode 工程、签名和 App Store 发布。SwiftUI 提供声明式 UI，UIKit 仍然大量存在于成熟工程和复杂场景中。

iOS 原生的优势是系统能力完整、体验一致、性能上限高、平台规范清晰。代价是平台绑定强，工程和发布链路有 Apple 生态特有的约束。

### Android 原生

Android 的核心抽象是开放设备生态上的应用模型。

你面对的是 Kotlin/Java、Activity、Fragment、Jetpack Compose、ViewModel、Gradle、权限、后台限制、设备兼容和 Google Play 或其他应用市场发布。Android 的设备形态和系统版本更分散，因此兼容性、构建配置和平台差异更突出。

Android 原生的优势是系统能力完整、生态开放、工程可组合性强。代价是碎片化、兼容性和构建复杂度更高。

### React Native

React Native 的核心抽象是用 React 心智协调 JavaScript 和原生 UI。

它不是“WebView 套壳”。RN 的界面最终会映射到原生视图体系，业务逻辑大多运行在 JS 侧，平台能力通过原生模块或新架构能力连接。它适合让有 React 经验的团队复用一部分 UI、状态和业务逻辑，同时保留访问原生能力的通道。

RN 的关键边界在 JS runtime 和 Native runtime 之间。性能问题、调试问题、原生能力接入问题，很多都发生在这个边界附近。

### Flutter

Flutter 的核心抽象是自带渲染体系的跨端 UI runtime。

Flutter 使用 Dart 编写，UI 由 Widget Tree 描述，框架通过自己的渲染管线绘制界面，而不是主要依赖系统原生 UI 组件。它通过 Engine、Skia/Impeller、Platform Channels 和插件体系接入平台能力。

Flutter 的优势是跨端一致性强、UI 表现可控、渲染模型统一。代价是它更像一套独立客户端技术栈，团队需要接受 Dart、Flutter 工程体系和与原生平台的桥接方式。

## 4. 从 Web 迁移到客户端，哪些经验能复用

你已有的前端和后端经验并不会浪费。很多能力可以直接迁移。

### 可以高度复用的能力

组件化思维可以迁移。无论 SwiftUI、Compose、RN 还是 Flutter，都需要拆分界面结构、识别复用单元、控制组件输入输出。

状态建模可以迁移。加载中、成功、失败、空状态、提交中、局部错误、乐观更新，这些状态在客户端同样存在。

异步和数据流经验可以迁移。网络请求、缓存、并发、取消、重试、错误处理，本质上都是异步系统设计。

工程协作经验可以迁移。模块边界、代码 review、CI、测试、环境配置、接口契约、日志和监控，客户端也需要。

产品体验判断可以迁移。用户路径、反馈时机、错误文案、加载体验、表单验证、权限引导，都不是某个端独有的问题。

### 需要重新建立的能力

生命周期需要重新理解。Web 页面也有生命周期，但 App 的生命周期更强：启动、前台、后台、恢复、被系统杀死、页面栈切换、内存压力都会影响代码行为。

权限模型需要重新理解。浏览器权限通常由标准 API 暴露，移动端权限更细、更平台化，而且用户拒绝后可能需要跳转系统设置。

线程和性能需要重新理解。主线程阻塞会造成卡顿，图片、列表、动画、序列化、桥接通信、数据库读写都可能影响体验。

发布和版本需要重新理解。Web 可以快速回滚和灰度，App 的发布受商店审核、用户升级率、旧版本兼容、热修复策略影响。

平台能力需要重新理解。相机、定位、通知、支付、蓝牙、后台任务不是普通 SDK 调用，它们往往伴随权限、系统策略和平台差异。

## 5. AI Coding 下最重要的不是“会不会写”，而是“知不知道问什么”

如果 AI 能帮你生成 SwiftUI、Kotlin、React Native 或 Flutter 代码，那么人的价值会更集中在三件事上。

第一，提供正确上下文。

你需要告诉 AI 当前工程使用的是 SwiftUI 还是 UIKit，是 Compose 还是 XML View，是 RN 新架构还是旧架构，是 Flutter 独立 App 还是混合接入，是 MVVM、Redux、MVI 还是自研架构。缺少这些上下文，AI 很容易写出局部正确、整体不合适的代码。

第二，判断代码放在哪一层。

AI 经常会把网络请求写进 UI，把权限检查散落在页面里，把缓存和业务状态混在一起，把平台差异藏在条件分支里。你需要能判断：这个逻辑应该属于 View、ViewModel、Repository、Use Case、原生模块，还是平台适配层。

第三，审查平台风险。

客户端代码“能编译”不等于“能上线”。你需要检查它是否处理了权限拒绝、页面销毁、请求取消、后台切换、弱网、线程切换、错误提示、埋点、崩溃风险和旧版本兼容。

因此，本课程后续不会把目标设为“手写所有 API”。更实际的目标是：你能读懂现有客户端代码的组织方式，能给 AI 足够准确的上下文，能审查它生成的实现是否符合客户端工程约束。

## 6. 轻量验证：一个需求的影响面扫描

拿一个常见需求做验证：

> 在个人资料页新增“修改头像”功能，支持从相册选择图片，裁剪后上传，上传成功后刷新头像。

如果你只用 Web 前端直觉看，它可能是一个页面交互需求。但从客户端地图看，它至少涉及：

| 层级 | 需要考虑的问题 |
| --- | --- |
| UI 与状态层 | 选择中、裁剪中、上传中、成功、失败、取消、重试如何展示 |
| 平台能力层 | 相册权限、相机权限、系统图片选择器、裁剪能力、权限拒绝后的引导 |
| 数据与网络层 | 图片压缩、上传接口、鉴权、超时、重试、服务端返回头像 URL |
| 本地存储层 | 是否缓存新头像，旧头像何时失效，失败后是否保留本地选择 |
| 生命周期层 | 上传中切后台、页面返回、App 被杀死后怎么办 |
| 跨端边界 | RN/Flutter 页面是否已有图片选择插件，是否需要补原生模块 |
| 质量层 | 大图内存风险、上传失败率、错误日志、埋点、崩溃监控 |

这张表就是你和 AI 协作时可以使用的第一种上下文模板。你不一定要一开始就实现所有边界，但你必须知道哪些边界存在。业务迭代的质量，很多时候取决于你有没有意识到这些边界，而不是你是否记住某个 API 名称。

## 7. 本章小结

这一章建立了客户端开发的第一张地图：

- Web 前端运行在浏览器抽象之上，移动客户端运行在操作系统之上。
- iOS、Android、React Native、Flutter 的区别不只是语言或框架，而是运行时、渲染模型、平台能力和工程边界不同。
- 客户端业务需求经常穿过 UI、状态、网络、缓存、权限、平台能力、生命周期和质量多个层级。
- 前端经验可以大量迁移，但生命周期、权限、线程、性能、发布和平台能力需要重新建立心智模型。
- AI Coding 可以加速实现，但你仍然需要负责上下文、分层判断和平台风险审查。

后续章节会沿着这张地图继续展开。第 2 章会先进入 iOS 和 Android 的平台模型：在理解 SwiftUI、Compose、RN、Flutter 之前，先理解操作系统怎样管理一个 App。

## 思考题

### 题 1：为什么说移动客户端的复杂度更多来自“运行环境”，而不只是语言或 UI 框架？

参考答案：

因为移动客户端直接运行在操作系统管理的 App 环境中。它不仅要渲染 UI，还要处理生命周期、权限、后台限制、设备能力、线程、内存、崩溃、发布、版本兼容和系统策略。Swift、Kotlin、Dart 或 JavaScript 只是表达逻辑的语言，真正影响架构判断的是这些系统边界。

### 题 2：React Native 和 Flutter 都是跨端方案，它们的抽象方式有什么根本差异？

参考答案：

React Native 更像是用 React 和 JavaScript 组织业务逻辑，再协调原生 UI 与原生能力；它的关键边界在 JS runtime 和 Native runtime 之间。Flutter 更像是提供一套自带渲染体系的跨端 UI runtime，用 Dart 和 Widget Tree 描述界面，通过 Engine 和渲染管线自己绘制 UI，再通过 Platform Channels 接入平台能力。前者更贴近 React 和原生协作，后者更强调跨端一致性和自有渲染体系。

### 题 3：如果你让 AI 帮你实现“修改头像”，除了功能描述，你还应该补充哪些上下文？

参考答案：

至少应该补充：当前页面属于 iOS、Android、React Native 还是 Flutter；项目使用的 UI 和状态架构；是否已有图片选择、裁剪、上传、权限处理模块；网络层和鉴权方式；头像缓存策略；页面生命周期中是否需要取消上传；失败时的交互规范；是否需要埋点、日志和监控；是否有平台差异或旧版本兼容要求。这些上下文能显著减少 AI 写出“局部能跑但不符合工程”的代码。
