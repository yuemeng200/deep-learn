# 第 4 章：业务功能如何穿过客户端分层

客户端开发的核心不是把某个按钮和某个接口接起来，而是让一个业务意图在 UI、状态、领域逻辑、数据、平台能力和质量体系之间正确流动。

第 3 章我们讨论了页面 UI 如何由状态驱动。这一章继续往业务深处走：一个用户点击到底会穿过哪些层？为什么成熟客户端工程不会把所有逻辑都写在页面组件里？

## 1. 业务功能不是“页面 + 接口”

从 Web 前端经验出发，很容易把一个客户端需求理解成：

```text
画页面
  -> 绑定点击事件
  -> 调接口
  -> 更新 UI
```

这个模型适合描述最小 demo，但不足以描述真实 App。

真实业务迭代通常会同时涉及：

- UI 展示和交互状态。
- 页面级状态和异步流程。
- 表单校验和业务规则。
- 网络请求、鉴权和错误码。
- 本地缓存和离线状态。
- 权限、相册、定位、支付等平台能力。
- 埋点、日志、崩溃和性能监控。
- 多端一致性和旧版本兼容。

所以更准确的业务链路是：

```text
用户意图
  -> UI 事件
  -> 页面状态 / ViewModel / Store
  -> 业务规则 / Use Case
  -> Repository / Service
  -> 网络 / 本地存储 / 平台能力
  -> 结果归一化
  -> 状态更新
  -> UI 反馈
  -> 埋点 / 日志 / 监控
```

这里的每一层都不是为了“显得架构复杂”，而是为了让变化有边界。

## 2. 为什么要分层：变化来源不同

一个页面里看似都叫“代码”，但它们变化的原因不同。

UI 会因为视觉、交互、设计规范变化而变化。

状态会因为用户流程、异步阶段、错误场景变化而变化。

业务规则会因为产品策略变化而变化。

网络层会因为接口协议、鉴权、错误码、重试策略变化而变化。

本地数据会因为缓存策略、离线能力、数据迁移变化而变化。

平台能力会因为 iOS/Android 权限、SDK、系统版本变化而变化。

埋点和日志会因为增长、分析、排障需求变化而变化。

如果这些都混在 UI 组件里，一个小需求会变成高风险修改。分层的真实目的就是让不同变化被限制在合适位置。

## 3. 一张业务链路分层图

可以先用这张图理解客户端常见分层：

```text
Presentation / UI
  View / Component / Widget / Composable
  负责展示 state，接收 user event

Presentation State
  ViewModel / Store / State Holder / Bloc
  负责页面状态、异步阶段、用户事件编排

Domain / Use Case
  业务规则、流程编排、权限前置判断、跨数据源组合
  不关心具体 UI 长什么样

Data / Repository
  网络请求、本地缓存、数据库、DTO 转换、数据源选择

Platform / Infrastructure
  相机、相册、定位、支付、通知、文件、系统 SDK
  HTTP client、database、analytics、logger

Quality / Observability
  埋点、日志、崩溃、性能、错误归因、灰度开关
```

这不是唯一分法，也不是所有项目都严格这么命名。iOS 项目可能叫 ViewModel、Service、Manager；Android 项目可能叫 ViewModel、UseCase、Repository；RN 项目可能叫 store、hook、service；Flutter 项目可能叫 Bloc、Notifier、Repository。

名字会变，但职责不应该乱。

## 4. 用“修改用户资料”走一遍链路

假设需求是：

> 用户在个人资料页修改昵称和简介，点击保存后提交到服务端，成功后刷新页面，失败时展示错误。

### UI 层

UI 层负责：

- 展示头像、昵称、简介。
- 展示输入框、保存按钮、错误文案。
- 根据状态决定按钮是否可点。
- 用户点击保存时发出 `saveTapped` 事件。

UI 层不应该直接决定：

- 接口 URL 是什么。
- 鉴权 token 怎么取。
- 错误码如何映射业务文案。
- 保存成功后缓存如何更新。
- 埋点字段如何组装。

### 状态层

状态层负责：

- 保存当前表单内容。
- 判断表单是否 dirty。
- 处理保存中的 loading。
- 接收保存结果。
- 把服务端字段错误映射到页面状态。
- 控制一次性提示，比如 Toast 或 Snackbar。

状态层的核心职责是让页面“每个时刻是什么状态”变得明确。

### 领域逻辑层

领域逻辑层负责：

- 昵称是否为空。
- 昵称长度和字符规则。
- 简介是否超长。
- 当前用户是否允许修改资料。
- 是否需要先检查登录态。
- 是否需要和其他数据一起提交。

有些项目不会显式写 Use Case，但这些规则仍然存在。问题只是它们散落在 UI、接口层，还是被集中管理。

### 数据层

数据层负责：

- 调用更新资料接口。
- 把 UI 表单转换成接口请求结构。
- 把服务端响应转换成客户端模型。
- 更新本地用户缓存。
- 处理接口错误、网络错误、鉴权错误。

数据层的价值是隔离接口协议变化。服务端字段从 `nickname` 改成 `display_name`，不应该导致 UI 组件大面积修改。

### 质量层

质量层负责：

- 保存按钮点击埋点。
- 保存成功或失败埋点。
- 接口失败日志。
- 异常错误上报。
- 保存耗时统计。

这部分经常被初学者忽略，但真实业务里很重要。功能上线后，团队需要知道用户是否点击、是否失败、失败在哪里、是否影响体验。

## 5. 再看“进入详情页”：导航也是业务链路

进入详情页看起来更简单：

```text
点击列表项 -> 打开详情页
```

但真实链路至少包括：

- 列表项是否有完整 ID。
- 是否需要登录后才能进入。
- 是否需要先检查本地缓存。
- 详情页参数怎么传。
- deep link 是否也能进入同一详情页。
- 页面打开埋点在哪里上报。
- 详情页加载失败后怎么返回或重试。
- RN/Flutter 页面是否由原生容器打开。

导航不是 UI 小事，而是业务流程的一部分。尤其在客户端，页面可能从多个入口进入：

- 列表点击。
- Push 通知。
- Deep link。
- 分享链接。
- 搜索结果。
- 第三方 SDK 回调。
- App 冷启动恢复。

如果你只按“从列表进详情”写代码，其他入口很容易坏。

## 6. 再看“提交订单”：业务流程会跨越更多边界

提交订单比修改资料复杂，因为它经常涉及强业务规则、支付、库存、风控和状态一致性。

一个简化链路可能是：

```text
点击提交
  -> 校验地址、库存、优惠券、支付方式
  -> 创建订单
  -> 拉起支付 SDK
  -> App 跳转到第三方或系统支付
  -> 支付回调
  -> 查询订单状态
  -> 展示成功或失败
  -> 上报埋点和日志
```

这里至少有几个架构判断：

- 校验哪些在本地做，哪些必须由服务端做。
- 支付 SDK 是原生接入，还是 RN/Flutter 插件接入。
- 支付跳出 App 后，回调如何恢复页面状态。
- 支付结果以 SDK 回调为准，还是以服务端订单查询为准。
- 如果用户中途杀掉 App，下次打开如何恢复订单状态。
- 埋点如何区分“点击提交”“创建订单成功”“支付成功”“支付失败”“用户取消”。

这类需求最能体现客户端分层价值。如果所有逻辑写在页面里，后续排查会非常痛苦。

## 7. MVC、MVVM、MVI、Clean Architecture 到底在解决什么

你会在客户端里看到很多架构名词。不要先把它们当成宗教，先看它们解决的问题。

### MVC

MVC 试图把数据、界面和控制逻辑分开。

在很多客户端历史项目里，Controller 容易膨胀，因为它既处理 UI，又处理事件、网络、导航和业务逻辑。这就是常说的 Massive View Controller 问题。

### MVVM

MVVM 的重点是引入 ViewModel，让 View 绑定或订阅 ViewModel 暴露的状态。

它适合声明式 UI 和状态驱动模型。View 负责展示，ViewModel 负责状态和事件编排，Repository 负责数据来源。

### MVI

MVI 更强调单向数据流：

```text
Intent / Event -> Reducer / Processor -> State -> View
```

它的优势是状态变化路径清晰，适合复杂页面和可测试性要求较高的场景。代价是样板代码和抽象成本可能更高。

### Clean Architecture

Clean Architecture 更关注依赖方向：

```text
UI -> Use Case -> Domain -> Repository Interface -> Data Implementation
```

核心原则是业务规则不应该依赖 UI 框架、网络库或数据库实现。它适合复杂业务和长期演进项目，但对简单页面可能显得过重。

### 现实判断

真实项目往往不是纯粹 MVC、MVVM、MVI 或 Clean Architecture，而是混合形态。你需要看的不是名字，而是：

- UI 是否承担了太多职责。
- 状态是否有单一事实来源。
- 业务规则是否散落在页面里。
- 数据层是否隔离了接口和缓存细节。
- 副作用是否可控。
- 测试和排查是否容易。

## 8. 现有 App 功能阅读 checklist

当你进入一个已有客户端项目，要修改某个功能，可以按下面顺序阅读。

### 入口

- 这个页面从哪些地方进入？
- 是否支持 deep link、通知、分享、第三方回调？
- iOS、Android、RN、Flutter 的入口是否一致？

### UI 与状态

- 页面状态在哪里定义？
- loading、error、empty、success、submitting 状态是否明确？
- 表单状态和服务端数据状态是否混在一起？
- 一次性事件，比如 Toast、跳转、弹窗，如何处理？

### 事件链路

- 用户点击后事件传到哪里？
- View 是否直接调接口？
- 是否经过 ViewModel、Store、Use Case？
- 是否有重复点击、防抖、取消、重试？

### 业务规则

- 校验逻辑在哪里？
- 规则是否和服务端保持一致？
- 是否有权限、登录态、会员态、地区、实验开关等前置条件？

### 数据层

- 请求结构和响应结构在哪里定义？
- 是否有 Repository 或 Service 隔离接口？
- 是否有本地缓存或数据库？
- 接口失败、鉴权失败、业务错误码如何处理？

### 平台能力

- 是否涉及相机、相册、定位、通知、支付、文件、分享？
- 权限请求在哪里？
- iOS 和 Android 是否有差异？
- RN/Flutter 是否通过插件或原生模块接入？

### 质量与观测

- 是否有埋点？
- 是否有错误日志？
- 是否有性能指标？
- 失败后团队能不能知道失败率和原因？

这个 checklist 的目标不是让你慢，而是让你少踩坑。业务迭代最怕只看到当前页面，却没有看到它背后的入口、状态、数据和平台边界。

## 9. AI Coding 下的业务链路提示模板

当你让 AI 修改已有客户端功能时，可以这样组织上下文：

```text
需求：
  在个人资料页增加保存昵称和简介的能力。

技术栈：
  SwiftUI / UIKit / Jetpack Compose / React Native / Flutter

当前架构：
  View 只渲染 state。
  ViewModel/Store 处理 user event。
  Repository 负责用户资料接口和缓存。
  AnalyticsService 负责埋点。

业务链路：
  saveTapped
    -> validate form
    -> update UI state to submitting
    -> call UpdateProfileUseCase
    -> UserRepository.updateProfile
    -> update local profile cache
    -> emit success or field errors
    -> track save result

约束：
  不要在 View 中直接调用 HTTP client。
  不要把服务端 DTO 直接暴露给 UI。
  保存中禁止重复提交。
  页面离开时处理未完成任务。
  失败时保留用户输入。

验收：
  成功保存后刷新本地资料。
  字段错误展示在对应输入框。
  网络错误展示全局错误并允许重试。
  重复点击不会提交多次。
  有成功/失败埋点。
```

这个模板会迫使 AI 沿着业务链路生成代码，而不是只在页面里拼一个能跑的实现。

## 10. 轻量验证：给“修改用户资料”画链路

可以用下面这张表做一次推演：

| 层级 | 修改用户资料需要做什么 | 常见错误 |
| --- | --- | --- |
| UI | 展示表单、保存按钮、错误文案 | 保存中仍可重复点击 |
| 状态 | 管理 dirty、submitting、field errors | loading 和 error 状态互相覆盖 |
| 业务规则 | 校验昵称、简介、登录态 | 只依赖前端校验或校验散落各处 |
| 数据层 | 调接口、转模型、更新缓存 | UI 直接依赖服务端 DTO |
| 本地存储 | 更新本地用户资料缓存 | 保存成功但返回页面仍显示旧数据 |
| 错误处理 | 区分字段错误、网络错误、鉴权错误 | 所有错误都显示“保存失败” |
| 平台/生命周期 | 页面离开、App 后台、请求取消 | 页面销毁后仍更新状态 |
| 观测 | 成功率、失败原因、耗时 | 上线后不知道哪里失败 |

这就是业务链路分层的实际用法：不是为了背架构名词，而是为了在做需求前看清影响面。

## 11. 本章小结

这一章建立了客户端业务功能的分层模型：

- 一个业务功能不是“页面 + 接口”，而是一条穿过 UI、状态、业务规则、数据、平台能力和质量体系的链路。
- 分层的目的不是制造复杂度，而是隔离不同变化来源。
- MVC、MVVM、MVI、Clean Architecture 的共同目标，都是减少 UI 过载，让状态、业务规则和数据访问更可控。
- 阅读现有 App 功能时，要从入口、UI 状态、事件链路、业务规则、数据层、平台能力和观测体系一起看。
- AI Coding 做业务迭代时，最好提供完整业务链路和架构约束，而不是只描述页面长什么样。

第 5 章会继续深入数据层：为什么客户端经常要处理缓存、一致性、弱网和本地状态，而不能只等后端返回。

## 思考题

### 题 1：为什么把网络请求直接写在 View 里通常不是好选择？

参考答案：

因为 View 的主要职责应该是展示状态和接收用户事件。网络请求涉及鉴权、错误处理、重试、缓存、模型转换和生命周期管理。如果直接写在 View 里，UI 会承担过多职责，后续接口变化、缓存策略变化、错误处理变化都会影响页面组件，也更难测试和复用。

### 题 2：MVVM 和 MVI 的共同点是什么？差异在哪里？

参考答案：

共同点是它们都试图让 UI 通过状态驱动，并把业务状态和事件处理从 View 中抽离出来。MVVM 通常强调 View 绑定或订阅 ViewModel 暴露的状态；MVI 更强调单向数据流，通过 Intent/Event 进入处理器或 Reducer，再生成新的 State。MVI 的状态变化路径更明确，但抽象和样板成本通常更高。

### 题 3：进入一个已有 App 修改功能时，为什么要先看入口和导航，而不是直接找当前页面文件？

参考答案：

因为客户端页面可能从多个入口进入，包括列表点击、通知、deep link、分享、搜索、第三方回调或冷启动恢复。不同入口可能传递不同参数，也可能触发不同埋点和权限逻辑。如果只看当前页面文件，很容易漏掉入口参数、导航恢复、跨端容器和业务前置条件，导致只修好了一个路径，其他路径仍然出错。
