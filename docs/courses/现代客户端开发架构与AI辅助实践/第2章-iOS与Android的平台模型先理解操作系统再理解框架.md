# 第 2 章：iOS 与 Android 的平台模型，先理解操作系统再理解框架

客户端开发的核心不是“换一种 UI 框架写页面”，而是在操作系统管理的 App 容器里组织业务、状态、权限、资源和用户体验。

第 1 章我们建立了客户端全局地图。这一章继续往下走：在理解 SwiftUI、UIKit、Jetpack Compose、React Native、Flutter 之前，先理解 iOS 和 Android 怎样管理一个 App。因为很多客户端问题不是框架问题，而是平台模型问题。

## 1. 为什么要先理解平台模型

从前端视角看，一个页面的主要关系通常是：

```text
用户操作 -> 状态变化 -> 组件重新渲染 -> 请求服务端 -> 更新 UI
```

这条链路在客户端也成立，但它不是完整图景。移动 App 还会被系统持续干预：

```text
系统启动 App
系统创建页面
用户授权或拒绝权限
系统切换前后台
系统回收内存
系统限制后台任务
系统派发通知
系统恢复页面状态
系统终止进程
应用商店分发新版本
```

因此，客户端业务代码始终运行在两个力量之间：

1. 业务自己想做什么：展示页面、提交表单、上传图片、播放视频、发送通知。
2. 系统允许你怎么做：什么时候能运行、能访问哪些资源、能占用多少内存、能不能在后台继续、权限是否被用户授予。

这就是为什么很多客户端问题看起来像“代码没写对”，本质却是“没有尊重平台模型”。

比如：

- 页面返回了，异步请求还在回调，导致状态更新到已销毁页面。
- 用户拒绝相册权限后，代码仍然尝试打开图片选择器。
- App 进入后台后上传被系统中断，但 UI 仍然显示上传中。
- Android 低版本或厂商系统上权限行为不同，某个功能只在部分设备失败。
- iOS 审核拒绝某个权限描述，因为用途说明不清楚。

这些问题都不是语法问题。它们来自 App 和操作系统之间的契约。

## 2. iOS 与 Android 的共同模型

iOS 和 Android 在设计哲学上差异明显，但从 App 开发者视角看，它们共享一组基础概念。

### App 是被系统托管的进程

移动 App 不是一个永远自主运行的程序。它的进程由系统启动、调度、挂起、恢复和终止。

用户点击图标、点开通知、从分享面板进入、从其他 App 跳转、系统恢复上次任务，这些都可能成为 App 的入口。你的代码不能假设“用户总是从首页开始，一路顺序点击到当前页面”。

### 页面不是孤立对象，而在导航栈或任务栈中

客户端页面通常存在于某种导航结构里。iOS 有 Navigation Stack、Tab、Modal、Scene 等概念；Android 有 Activity、Fragment、Navigation Component、Task、Back Stack 等概念。

业务页面的生命周期会受到导航影响：进入、离开、返回、重新出现、被销毁、被重建。一个页面不只是“渲染一次”，而是在系统和导航共同管理下持续变化。

### 权限是用户和系统共同控制的资源访问开关

相机、相册、定位、通知、蓝牙、麦克风、通讯录等能力都不是普通函数调用。它们需要声明用途，运行时请求授权，并处理用户拒绝、仅本次允许、有限访问、永久拒绝、系统设置关闭等状态。

### 本地数据处在沙箱中

移动 App 通常运行在自己的沙箱里。它可以访问自己的文件、数据库、缓存、Keychain/Keystore 等安全存储，但不能随意读写其他 App 的数据。

这个模型带来安全性，也带来数据迁移、缓存清理、备份、卸载、登录态保存等工程问题。

### 后台运行受到严格限制

移动系统要保护电量、性能和隐私，所以不会让所有 App 无限制后台运行。后台上传、定位、音乐播放、通知推送、定时任务都需要符合系统规则。

如果一个业务需求依赖“App 在后台持续工作”，必须先判断平台是否允许，而不是直接写一个循环或定时器。

## 3. iOS 平台模型：强控制、一致性和生态闭环

iOS 的核心特点是 Apple 对硬件、系统、开发工具、分发渠道和体验规范有很强控制力。

这带来几个开发上的结果。

### 应用生命周期更集中

现代 iOS App 通常围绕 App、Scene、ViewController 或 SwiftUI App 生命周期组织。

可以粗略理解为：

```text
App 启动
  -> 创建 Scene 或主窗口
  -> 显示根视图
  -> 用户导航到不同页面
  -> App 进入后台
  -> App 回到前台
  -> 系统可能挂起或终止进程
```

SwiftUI 让很多生命周期细节变得更声明式，但系统生命周期并没有消失。你仍然需要理解 App 什么时候进入后台、什么时候恢复、什么时候保存状态、什么时候取消任务。

### UIKit 仍然是重要地基

SwiftUI 是现代 iOS UI 的重要方向，但 UIKit 并没有消失。大量成熟工程、复杂页面、导航、列表、原生 SDK、混合接入都可能仍然涉及 UIKit。

对于业务迭代者来说，关键不是站队 SwiftUI 或 UIKit，而是知道：

- SwiftUI 更强调声明式、状态驱动和组合。
- UIKit 更强调对象、控制器、委托、命令式更新。
- 真实工程里经常两者共存。
- React Native 和 Flutter 接入 iOS 时，最终也会和 UIKit、ViewController、原生模块发生关系。

### 权限和隐私描述非常重要

iOS 对隐私权限要求严格。很多权限不仅要在运行时请求，还要在配置文件中说明用途。用途说明不清楚，可能导致审核风险或用户拒绝率升高。

对于 AI Coding 来说，这是一个高频风险点。AI 可能会写出请求相册或定位的代码，但不会自动知道你的 `Info.plist` 是否声明了用途，也不会自动设计权限拒绝后的产品路径。

### 发布链路受 App Store 影响

iOS 的发布通常经过证书、签名、Provisioning Profile、TestFlight、App Store Review、灰度发布等链路。

这意味着客户端迭代不能完全按 Web 的节奏思考。Web 可以分钟级回滚，App 可能受审核、用户升级率和旧版本兼容影响。一个接口字段或本地数据结构的变更，需要考虑老版本 App 是否仍在运行。

## 4. Android 平台模型：开放生态、设备差异和组件化应用模型

Android 的核心特点是开放生态和设备多样性。它支持多厂商、多系统版本、多屏幕、多应用市场，也因此更强调兼容性和组件化。

### Activity 是重要入口，但不是整个架构

Android 早期开发常以 Activity 和 Fragment 为中心。现代 Android 工程会更多使用 Jetpack、ViewModel、Lifecycle、Navigation、Compose 等能力，但 Activity 仍然是系统认识你的重要组件之一。

可以粗略理解为：

```text
系统启动 Activity
  -> Activity 创建 UI
  -> 页面进入前台
  -> 用户跳转或返回
  -> Activity 暂停、停止、销毁
  -> 系统可能因配置变化重建 Activity
```

Android 的一个重要特点是配置变化。比如横竖屏切换、语言变化、深色模式变化，都可能导致 Activity 重建。业务状态如果只存在页面对象里，就可能丢失。

### Jetpack 是现代 Android 的工程底座

Jetpack 不是一个单一框架，而是一组帮助你处理生命周期、状态、导航、数据库、后台任务、分页、权限等问题的库和架构组件。

常见心智模型是：

- Activity/Fragment/Compose 负责 UI 容器和界面展示。
- ViewModel 保存 UI 相关状态，并跨配置变化存活。
- Flow/LiveData 负责响应式数据流。
- Repository 负责协调网络、本地存储和数据源。
- WorkManager 负责可靠后台任务。
- Room 负责本地数据库。

你不需要一开始背所有 API，但要知道这些组件大多是在帮你对抗 Android 平台复杂度。

### Android 权限和兼容性更碎片化

Android 权限模型随系统版本持续演进。相册、通知、定位、蓝牙、后台定位、文件访问等权限在不同版本上行为可能不同。

此外，厂商系统可能对后台任务、通知、自启动、省电策略做额外限制。一个功能在模拟器或某个品牌手机上正常，不代表所有设备都正常。

这也是为什么 Android 业务迭代经常需要更明确的设备矩阵、系统版本范围和兼容策略。

### Gradle 和构建配置是平台理解的一部分

Android 工程中，Gradle 不只是“安装依赖的工具”。它管理模块、构建变体、签名、资源、插件、编译参数、渠道包和多环境配置。

前端开发者经常低估 Android 构建系统的重要性。很多问题并不出在业务代码，而出在依赖版本、插件版本、SDK 版本、混淆规则、资源冲突、构建变体或签名配置上。

## 5. iOS 与 Android 平台模型对照表

下面这张表用于建立宏观判断，不追求覆盖所有细节。

| 维度 | iOS | Android | 对业务迭代的影响 |
| --- | --- | --- | --- |
| 生态控制 | Apple 强控制，硬件和系统更集中 | 开放生态，多厂商多版本 | Android 更需要设备和版本兼容意识 |
| UI 主线 | SwiftUI 正在成为主线，UIKit 仍大量存在 | Jetpack Compose 增长中，View/Fragment 仍大量存在 | 真实工程经常新旧 UI 体系共存 |
| 生命周期 | App/Scene/ViewController/SwiftUI 生命周期 | Activity/Fragment/Lifecycle/Task/Back Stack | 异步任务、状态保存、页面返回都要尊重生命周期 |
| 权限 | 隐私声明严格，审核敏感 | 版本差异和厂商差异更明显 | 权限拒绝、降级路径和配置声明都要检查 |
| 后台任务 | 控制严格，后台能力类型明确 | 有 WorkManager、Service 等机制，但受系统和厂商限制 | 后台上传、定位、推送不能按 Web 定时器心智设计 |
| 存储 | 沙箱、Keychain、文件、数据库、UserDefaults | 沙箱、Keystore、文件、Room/SQLite、SharedPreferences/DataStore | 登录态、缓存、离线数据需要区分安全性和生命周期 |
| 构建工具 | Xcode、Swift Package Manager、CocoaPods、签名证书 | Gradle、Android Gradle Plugin、Maven 依赖、签名 | 依赖和构建配置会直接影响交付风险 |
| 发布 | App Store/TestFlight/审核 | Google Play/多应用市场/渠道包 | 版本兼容、灰度、审核和回滚策略不同 |
| 跨端接入 | RN/Flutter 通过原生容器、模块、插件接入 | RN/Flutter 通过 Activity、模块、插件接入 | 跨端页面也不能绕开原生平台模型 |

这张表的价值在于：当你做一个业务功能时，不要只问“代码怎么写”，还要问“这个功能触碰了平台模型的哪些部分”。

## 6. 常见业务需求的平台影响面

下面用几个常见需求做平台影响面扫描。

### 需求一：新增定位能力

你需要考虑：

- iOS 和 Android 的定位权限文案、授权时机、拒绝后路径。
- 是否需要精确定位，还是粗略定位就够。
- 是否需要后台定位，如果需要，平台是否允许，用户是否理解。
- 定位失败、超时、系统定位关闭时如何展示。
- 是否有隐私合规和埋点要求。
- RN/Flutter 页面是否已有统一定位模块，还是要补原生能力。

如果只让 AI 写“获取当前位置”，它很可能忽略授权时机、后台限制和拒绝后的体验。

### 需求二：通知提醒

你需要考虑：

- iOS 和 Android 通知权限差异。
- 通知是本地通知还是远程推送。
- 点击通知后进入哪个页面，是否需要携带参数。
- App 冷启动、后台、前台时通知行为是否一致。
- 用户关闭通知权限后是否有替代提醒。
- 服务端推送 token 如何注册、刷新、失效。

通知不是一个 UI 功能，而是系统、服务端、权限、路由和用户体验共同组成的能力。

### 需求三：上传文件或图片

你需要考虑：

- 文件来源：相册、相机、文件系统、分享入口。
- 权限和系统选择器。
- 图片压缩、视频转码、文件大小限制。
- 上传中切后台或页面返回。
- 弱网、重试、取消、断点续传。
- 上传成功后的缓存更新和 UI 刷新。
- 大文件导致的内存和耗电风险。

这类需求非常适合用第 1 章的影响面表来审查 AI 方案。

### 需求四：接入支付或登录 SDK

你需要考虑：

- iOS 和 Android SDK 接入方式不同。
- URL Scheme、Universal Links、App Links、回调跳转。
- 签名、包名、Bundle ID、证书配置。
- App 被第三方拉起后如何恢复业务状态。
- SDK 版本、隐私合规、审核风险。
- RN/Flutter 是否已有桥接插件，插件是否维护良好。

这类需求最容易让 Web 开发者低估平台配置的重要性。很多 bug 不在页面代码里，而在工程配置、签名、回调和平台限制里。

## 7. AI Coding 下的平台上下文模板

当你让 AI 修改客户端功能时，可以先提供这类上下文：

```text
当前平台：
  iOS / Android / React Native / Flutter / 混合页面

工程形态：
  SwiftUI / UIKit / Compose / XML View / RN 新架构 / Flutter 独立 App / Flutter 混合接入

页面位置：
  入口页面 / Tab 页面 / 二级页面 / Modal / 原生容器中的跨端页面

生命周期要求：
  页面离开后是否取消任务
  App 进入后台后是否继续
  是否需要恢复上次状态

平台能力：
  是否涉及相机、相册、定位、通知、蓝牙、文件、支付、分享

权限策略：
  何时请求权限
  用户拒绝后怎么处理
  是否需要系统配置声明

数据与状态：
  是否需要缓存
  是否需要离线
  是否涉及登录态
  是否要处理弱网和重试

质量要求：
  是否需要埋点
  是否需要错误日志
  是否有崩溃或性能风险
  是否有旧版本兼容要求
```

这个模板的作用不是让每个需求都变复杂，而是让你先知道哪些问题必须被排除。成熟开发者和初学者的差别，很多时候不是写代码速度，而是能否提前识别“不该漏掉的边界”。

## 8. 本章小结

这一章建立了 iOS 与 Android 的平台模型：

- App 是被操作系统托管的进程，不是完全自主运行的网页脚本。
- 页面运行在导航栈、任务栈和生命周期之中，异步任务和状态必须尊重这些边界。
- 权限、存储、后台任务、通知、发布和系统服务都是平台契约，不是普通 API 调用。
- iOS 的特点是强控制、一致性和生态闭环；Android 的特点是开放生态、设备差异和组件化应用模型。
- React Native 和 Flutter 虽然是跨端方案，但最终仍然要接入 iOS 和 Android 的平台模型。
- AI Coding 做客户端开发时，必须补充平台上下文，否则很容易生成“局部正确、平台错误”的实现。

第 3 章会进入 UI 架构层：为什么 SwiftUI、Jetpack Compose、React Native 和 Flutter 都在走声明式 UI，但它们仍然不能被简单理解为“移动端 React”。

## 思考题

### 题 1：为什么“页面返回后请求还在执行”在客户端里是一个平台模型问题，而不只是异步代码问题？

参考答案：

因为客户端页面有明确的生命周期。页面离开、销毁、被系统重建或 App 进入后台时，异步任务可能仍然回调。如果代码没有感知生命周期，就可能更新已销毁页面、泄漏资源、展示错误状态或造成崩溃。所以它不仅是 Promise、Callback、Coroutine、Task 的问题，也是页面和系统生命周期边界的问题。

### 题 2：iOS 和 Android 在权限处理上有什么共同点和差异？

参考答案：

共同点是权限都不是普通函数调用，都需要声明、请求、处理用户授权或拒绝，并设计降级路径。差异是 iOS 对隐私描述和审核更敏感，权限用途说明很重要；Android 的权限行为更受系统版本和厂商差异影响，同一类权限在不同版本上可能有不同规则。因此业务迭代时要同时检查配置声明、授权时机、拒绝路径和平台兼容性。

### 题 3：为什么 React Native 或 Flutter 页面仍然需要理解 iOS/Android 平台模型？

参考答案：

因为跨端框架只抽象了一部分 UI 和业务逻辑，不能消除底层平台。相机、相册、定位、通知、支付、文件、后台任务、权限、发布、崩溃和性能最终仍然受 iOS 和 Android 管理。RN 需要通过原生模块或新架构能力接入平台，Flutter 需要通过插件和 Platform Channels 接入平台。如果不了解平台模型，就很难判断跨端代码什么时候必须回到原生边界。
