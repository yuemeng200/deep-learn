# 第 7 章：客户端工程化、质量与性能，业务迭代为什么不能只看功能跑通

客户端开发的核心不是让功能在自己手机上跑通，而是让它在真实用户的设备、网络、系统版本和长期使用中稳定、流畅、可观测、可回滚。

前面几章讲了平台、UI、业务链路、数据和跨端。第 7 章讨论更贴近上线后的问题：崩溃、卡顿、包体、启动、耗电、兼容性、监控和发布。

## 1. 为什么客户端质量更像长期工程

Web 出问题时，团队通常可以快速发布修复，用户刷新页面后就能拿到新版本。

客户端不一样：

- 用户不一定立刻升级。
- 旧版本可能长期存在。
- App Store 或应用市场审核会带来延迟。
- 崩溃发生在用户设备上，不一定容易复现。
- 设备型号、系统版本、厂商 ROM、网络环境差异很大。
- 包体、启动、内存和耗电会直接影响留存。

所以客户端质量不是上线前最后测一下，而是从架构、工程、监控和发布流程里持续约束。

## 2. 构建系统和模块化

客户端工程通常比 Web 页面更重。iOS 有 Xcode、Swift Package Manager、CocoaPods、签名、证书；Android 有 Gradle、Android Gradle Plugin、构建变体、签名、混淆；RN/Flutter 又叠加 JS/Dart 包管理、原生工程和跨端构建。

模块化的目标是：

- 降低编译和构建成本。
- 控制业务模块依赖方向。
- 隔离基础能力和业务页面。
- 支持多人协作。
- 支持按模块测试和发布。

常见模块划分：

```text
App Shell
  启动、导航、登录态、全局配置

Feature Modules
  用户、订单、消息、设置、活动页

Core Modules
  网络、缓存、数据库、日志、埋点、权限、路由

Platform Adapters
  相机、定位、支付、通知、文件、分享

Cross-platform Modules
  RN bundle、Flutter module、共享业务页面
```

业务迭代时要尊重模块边界。把一个订单页面直接依赖支付 SDK、网络实现、数据库实现和埋点实现，会让后续修改非常困难。

## 3. 测试：客户端不是只有手工点点

客户端测试通常可以分层：

| 类型 | 目标 | 例子 |
| --- | --- | --- |
| 单元测试 | 验证纯逻辑 | 表单校验、状态 reducer、Use Case |
| 集成测试 | 验证模块协作 | Repository + fake API + cache |
| UI 测试 | 验证关键流程 | 登录、下单、资料保存 |
| 快照/截图测试 | 验证 UI 回归 | 组件视觉变化 |
| 手工测试 | 覆盖复杂设备和体验 | 权限、通知、支付、弱网 |
| 灰度验证 | 真实用户小范围观察 | 崩溃率、失败率、性能 |

AI Coding 时代，测试更重要。因为 AI 可以快速生成代码，也可能快速生成隐藏 bug。你要让 AI 同时生成测试思路，而不是只生成实现。

## 4. 可观测性：上线后要知道发生了什么

客户端可观测性至少包括：

- 崩溃：crash-free rate、崩溃堆栈、影响版本、设备分布。
- 错误：接口失败、业务错误码、SDK 错误、权限拒绝。
- 性能：启动耗时、页面打开耗时、列表卡顿、帧率、内存。
- 用户行为：点击、曝光、转化、取消、失败路径。
- 日志：关键链路的上下文，但要注意隐私脱敏。
- 版本：App 版本、系统版本、设备型号、网络环境、实验分组。

没有可观测性，客户端问题会变成“用户说有问题，但我们不知道在哪里”。

## 5. 性能：卡顿、启动、内存、包体

客户端性能通常要关注几个核心指标。

### 启动性能

启动慢会直接影响用户打开 App 的第一感受。常见原因：

- 启动时做太多同步初始化。
- 过早初始化重型 SDK。
- 主线程阻塞。
- 资源加载过多。
- 跨端引擎初始化时机不合理。

### 页面性能

页面打开慢、列表滚动卡、动画掉帧常见原因：

- 主线程做重计算。
- 图片过大或解码不当。
- 列表没有虚拟化或复用。
- 状态更新范围过大。
- RN JS 线程繁忙或桥接频繁。
- Flutter rebuild 范围过大或平台视图混合开销高。

### 内存

内存问题常见于：

- 大图处理。
- 视频和音频资源。
- 页面对象未释放。
- 监听器、闭包、回调持有对象。
- 缓存无限增长。

### 包体

包体影响下载、安装、启动和低端设备体验。常见来源：

- 图片、字体、音视频资源。
- 多架构二进制。
- 重型 SDK。
- 未裁剪的跨端 bundle。
- 调试符号或无用资源。

性能优化的原则是先测量，再定位，再优化。不要靠猜。

## 6. 发布、灰度和回滚

客户端发布比 Web 更慢，所以需要更谨慎：

- 版本号和构建号管理。
- iOS TestFlight / App Store Review。
- Android 多渠道和应用市场。
- 灰度发布。
- 远程配置和 feature flag。
- 服务端兼容旧版本。
- 强制升级或提示升级。
- 热修复或动态化能力的边界。

一个服务端接口变更，要问：

- 老版本 App 是否还在用旧字段？
- 新版本是否能兼容旧服务端响应？
- 如果新版本出 bug，能否通过配置关闭功能？
- 用户升级不及时怎么办？

客户端工程里，发布策略也是架构的一部分。

## 7. 业务需求上线前风险检查表

| 风险维度 | 检查问题 |
| --- | --- |
| 生命周期 | 页面离开、App 后台、进程恢复是否处理 |
| 权限 | 用户拒绝、系统关闭、版本差异是否处理 |
| 网络 | 超时、弱网、重复提交、取消、重试是否处理 |
| 数据 | 缓存更新、多页面一致性、旧版本兼容是否处理 |
| 性能 | 列表、大图、动画、主线程、跨端桥接是否有风险 |
| 崩溃 | 空值、类型转换、SDK 回调、平台差异是否有保护 |
| 埋点 | 成功、失败、取消、耗时是否能观测 |
| 发布 | 灰度、开关、回滚、审核、渠道是否考虑 |
| 测试 | 单元、集成、UI、设备矩阵、弱网是否覆盖 |

这个表可以作为 AI 生成代码后的审查清单。

## 8. AI Coding 下的质量提示模板

```text
请实现该客户端功能，同时满足以下质量要求：

生命周期：
  页面离开后取消非必要请求。
  App 后台切换不导致状态错乱。

错误处理：
  区分网络错误、业务错误、鉴权错误、权限拒绝。
  用户输入失败后不丢失。

性能：
  不在主线程做重计算。
  图片需要压缩或限制尺寸。
  列表使用虚拟化/复用机制。

观测：
  上报点击、成功、失败、取消和耗时。
  错误日志带 trace id，但不记录敏感信息。

测试：
  给出单元测试和关键手工测试用例。
  覆盖弱网、重复点击、页面返回、权限拒绝。
```

## 9. 轻量验证：头像上传上线前检查

| 检查项 | 要点 |
| --- | --- |
| 权限 | 相册/相机拒绝后有降级路径 |
| 图片处理 | 大图压缩，避免内存峰值过高 |
| 上传 | 超时、重试、取消、重复点击 |
| 生命周期 | 页面离开或 App 后台策略明确 |
| 缓存 | 上传成功后更新本地头像缓存 |
| 埋点 | 选择、裁剪、上传成功/失败都有事件 |
| 监控 | 上传失败率和错误原因可查 |
| 兼容 | iOS/Android 权限和文件 URI 差异已处理 |
| 跨端 | RN/Flutter 插件或原生模块行为一致 |

这就是“功能跑通”和“可以上线”的差距。

## 10. 本章小结

- 客户端质量是长期工程，受设备、系统、网络、发布和用户升级率影响。
- 模块化、测试、监控、性能和发布策略都属于客户端架构的一部分。
- 性能问题要围绕启动、页面、内存、包体、跨端运行时具体定位。
- 可观测性决定上线后能不能排查问题。
- AI Coding 生成实现后，必须用生命周期、错误处理、性能、观测和测试清单审查。

第 8 章会把全部内容收束到 AI Coding 时代的客户端开发方法。

## 思考题

### 题 1：为什么客户端发布策略也是架构问题？

参考答案：

因为客户端版本不能像 Web 一样立即覆盖所有用户。旧版本会长期存在，审核和应用市场会带来延迟，接口和本地数据结构都要考虑兼容。灰度、开关、回滚和服务端兼容会直接影响功能设计。

### 题 2：为什么“功能跑通”不等于“可以上线”？

参考答案：

功能跑通只证明理想路径可用，但上线还要面对弱网、权限拒绝、页面离开、设备差异、旧版本、崩溃、性能和监控。没有覆盖这些场景，真实用户环境中很容易出问题。

### 题 3：AI Coding 为什么会放大质量审查的重要性？

参考答案：

AI 能快速生成大量代码，但它可能忽略平台生命周期、错误边界、性能和观测要求。开发者需要用清单和测试约束生成结果，否则代码增长速度会超过质量控制能力。
