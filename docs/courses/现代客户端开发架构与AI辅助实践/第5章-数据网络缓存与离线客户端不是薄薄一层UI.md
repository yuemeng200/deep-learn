# 第 5 章：数据、网络、缓存与离线，客户端不是薄薄一层 UI

客户端开发的核心不是把接口数据显示出来，而是在不稳定网络、有限设备资源和多版本 App 共存的现实里，维护用户可感知的数据体验。

前面几章我们已经建立了 UI、状态和业务链路的分层。这一章进入数据层：为什么客户端经常要处理缓存、一致性、弱网和本地状态，而不能只等后端返回。

## 1. 客户端数据的第一原则：用户面对的是体验，不是接口

从服务端视角看，数据请求通常是：

```text
client request -> server response
```

但从客户端用户视角看，问题是：

```text
我现在看到的数据可靠吗？
操作有没有成功？
失败了能不能恢复？
网络差时还能不能继续？
返回上一页后状态是不是一致？
```

所以客户端数据层不只是 HTTP client。它还要处理：

- 鉴权和 token 刷新。
- 请求取消和重试。
- 分页、预加载和并发控制。
- 本地缓存和缓存失效。
- 离线草稿和同步。
- 乐观更新和回滚。
- 服务端错误码到 UI 文案的映射。
- 多页面共享数据的一致性。

很多 App 体验问题不是“接口慢”，而是客户端没有设计好接口慢、失败、重复、取消、离线时的行为。

## 2. 数据状态不等于页面状态

第 3 章我们讲过页面状态，比如 loading、loaded、failed。数据状态更底层，描述的是数据从哪里来、是否可信、是否过期、是否正在同步。

可以粗略分成几类：

| 数据类型 | 例子 | 主要问题 |
| --- | --- | --- |
| 服务端权威数据 | 订单状态、余额、库存 | 客户端不能随意相信本地结果 |
| 客户端临时数据 | 表单输入、草稿、筛选条件 | 需要保存和恢复 |
| 缓存数据 | 用户资料、列表第一页、图片 | 何时可用，何时失效 |
| 派生数据 | 本地计算的展示字段、分组结果 | 源数据变化后如何更新 |
| 乐观数据 | 点赞后先本地 +1 | 失败后如何回滚 |
| 平台数据 | 定位、相册文件、通知 token | 权限和系统状态会影响可用性 |

页面状态回答“界面此刻怎么展示”。数据状态回答“这些数据从哪里来、是否还能用、何时需要同步”。

如果这两个概念混在一起，页面会很难维护。比如列表页面既有“首次加载中”，又有“已有缓存但后台刷新中”，这两种 UI 不应该一样。

## 3. 网络层：不只是封装 fetch 或 URLSession

一个成熟网络层通常要处理这些问题：

```text
Request 构建
  base URL、path、query、body、headers

鉴权
  access token、refresh token、登录失效

协议转换
  DTO -> Domain Model
  Domain Model -> Request DTO

错误归一
  HTTP error、业务错误码、网络超时、解析失败

重试与取消
  超时重试、幂等请求重试、页面离开取消

观测
  请求耗时、失败率、trace id、日志脱敏
```

前端开发者熟悉 HTTP，但客户端网络层还要额外考虑页面生命周期和 App 生命周期。页面离开后是否取消请求？App 进入后台后上传是否继续？弱网下是否重试？重复点击会不会发出多个提交？

AI Coding 很容易生成“调用接口并 setState”的代码，但这通常只是最薄的一层实现。

## 4. 缓存：不是为了偷懒，而是为了体验和可用性

客户端缓存有很多层：

- 内存缓存：页面间快速复用，进程结束后消失。
- 磁盘缓存：图片、接口响应、文件，App 重启后仍可用。
- 数据库缓存：结构化数据、本地索引、离线能力。
- 安全存储：token、凭据、敏感配置。
- 框架缓存：图片库、HTTP cache、Query cache、Repository cache。

缓存策略的核心问题不是“要不要缓存”，而是：

```text
缓存什么？
缓存多久？
谁负责失效？
用户操作后如何更新？
服务端数据变化后如何同步？
缓存脏了会造成什么后果？
```

例如用户资料可以先展示本地缓存，再后台刷新；但账户余额、库存、支付状态就不能长期依赖本地缓存。不同业务数据的权威性不同，缓存策略也不同。

## 5. 弱网和离线：客户端必须替用户面对现实世界

移动网络不是稳定局域网。用户可能在地铁、电梯、地下车库、海外漫游、低电量模式、后台切换中使用 App。

弱网下常见问题：

- 请求超时。
- 图片加载失败。
- 分页重复或漏数据。
- 上传中断。
- 表单提交成功但响应丢失。
- 用户重复点击导致重复提交。
- 前端显示失败，但服务端其实已处理成功。

离线能力不一定意味着完整离线 App。它可以是分层的：

| 能力级别 | 含义 | 例子 |
| --- | --- | --- |
| 无离线 | 没网直接不可用 | 支付、强实时交易 |
| 读缓存 | 没网时展示旧数据 | 用户资料、历史列表 |
| 离线草稿 | 允许先保存本地 | 编辑文章、填写表单 |
| 延迟同步 | 联网后自动提交 | 待办、笔记、打卡 |
| 冲突合并 | 多端修改后解决冲突 | 协作文档、复杂表单 |

大多数业务不需要做到最高级，但必须明确自己属于哪一级。

## 6. 乐观更新：体验和一致性的交换

乐观更新是指：用户操作后客户端先更新 UI，再等待服务端确认。

例如点赞：

```text
用户点击点赞
  -> 本地点亮按钮，数量 +1
  -> 后台请求服务端
  -> 成功则保持
  -> 失败则回滚或提示重试
```

乐观更新适合低风险、可回滚、用户期望即时反馈的操作。它不适合强一致、强交易、不可逆的操作。

判断一个操作能否乐观更新，可以问：

- 失败后能否回滚？
- 重复提交是否安全？
- 服务端最终结果是否可能和客户端不同？
- 用户是否能接受短暂不一致？
- 多端同步是否会造成混乱？

AI 生成乐观更新代码时，很容易只写“先改 UI”，忘记失败回滚、重复点击、请求取消和多页面缓存同步。

## 7. 数据层分层：Repository 的真实作用

Repository 不是为了套架构名词，而是为了隐藏数据来源。

一个 `UserRepository` 可以同时协调：

- 远程用户资料接口。
- 本地用户缓存。
- token 或登录态。
- 数据模型转换。
- 缓存失效策略。
- 错误归一。

对上层来说，它只暴露业务语义：

```text
getCurrentUser()
updateProfile(form)
refreshUser()
observeUser()
```

而不是暴露：

```text
GET /api/v3/user/profile
POST /api/v3/user/update
read sqlite table users
write shared preferences
```

这能减少 UI 和接口协议的耦合。服务端字段变化、本地缓存策略变化、接口拆分合并，都不应该让 UI 大面积改动。

## 8. 轻量验证：弱网下的资料保存

以“保存个人资料”为例，设计一个数据策略：

| 场景 | 推荐处理 |
| --- | --- |
| 首次进入页面 | 先读缓存，没有缓存再展示 loading 请求远程 |
| 用户编辑表单 | 表单状态只存在页面或草稿层，不立即覆盖服务端缓存 |
| 点击保存 | 禁止重复提交，状态进入 submitting |
| 网络超时 | 保留用户输入，展示可重试错误 |
| 服务端字段错误 | 映射到对应输入框，不清空表单 |
| 保存成功 | 更新本地用户缓存，通知其他页面刷新 |
| 页面离开 | 如果有未保存修改，提示或保存草稿 |
| App 后台 | 根据业务决定继续、取消或保存草稿 |

这个表比“调一个 updateProfile 接口”更接近真实客户端开发。

## 9. AI Coding 下的数据层提示模板

```text
需求：
  实现用户资料保存，支持缓存、错误处理和弱网重试。

架构约束：
  UI 不直接调用 HTTP client。
  ViewModel 调用 UserRepository。
  Repository 负责远程接口、本地缓存、模型转换和错误归一。

数据策略：
  页面进入时先读缓存，再后台刷新。
  保存中禁止重复提交。
  保存失败保留表单输入。
  保存成功更新本地用户缓存，并通知依赖用户资料的页面。
  字段错误映射到具体字段，网络错误展示全局错误。

生命周期：
  页面离开时取消非必要请求。
  如果存在未保存修改，提示用户。

验收：
  无网、超时、401、字段错误、服务端 500 都有明确 UI。
  不出现保存成功后其他页面仍显示旧资料。
```

## 10. 本章小结

- 客户端数据层要处理网络、缓存、离线、错误、鉴权、生命周期和一致性。
- 页面状态和数据状态不是一回事，前者关心 UI 展示，后者关心数据来源和可信度。
- 缓存不是简单存一份数据，而是围绕失效、同步、权威性和用户体验做权衡。
- 弱网和离线能力需要分级设计，不是所有业务都要完整离线。
- Repository 的价值是隔离数据来源和协议细节，让 UI 面向业务语义。
- AI Coding 写数据层时，要明确缓存策略、错误归一、生命周期和一致性要求。

第 6 章会进入跨端技术路线：React Native、Flutter 与原生混合接入到底分别在复用什么，又牺牲了什么。

## 思考题

### 题 1：为什么“有缓存”不等于“体验一定好”？

参考答案：

因为缓存还涉及可信度、失效策略、同步机制和业务风险。错误的缓存可能展示过期数据，保存成功后不刷新可能造成多页面不一致，强交易数据如果依赖本地缓存可能误导用户。所以缓存要和业务权威性一起设计。

### 题 2：哪些操作适合乐观更新，哪些不适合？

参考答案：

适合低风险、可回滚、用户期望即时反馈的操作，比如点赞、收藏、开关偏好。不适合强一致、不可逆、涉及金钱或库存的操作，比如支付、转账、提交订单。关键判断是失败能否回滚、重复提交是否安全、短暂不一致是否可接受。

### 题 3：Repository 层对 AI Coding 有什么帮助？

参考答案：

Repository 给 AI 一个清晰边界：UI 和 ViewModel 不需要知道接口细节、本地缓存细节和 DTO 转换细节。这样生成代码更容易符合工程分层，也更容易在接口变化、缓存策略变化时局部修改。
