# 第 8 章：AI Coding 时代的客户端开发方法

AI Coding 时代，客户端开发者的核心能力会从“逐行写出所有代码”转向“描述正确上下文、约束架构边界、审查平台风险、设计验证路径”。

前面七章已经覆盖平台、UI、业务链路、数据、跨端和质量。这一章把它们收束成一套实际工作方法：如何在已有 App 中借助 AI 完成功能迭代，同时不丢掉客户端工程判断。

## 1. AI 能加速什么，不能替你判断什么

AI 很擅长：

- 根据已有模式补代码。
- 生成 UI 骨架和状态模型。
- 写 Repository、DTO、测试样例。
- 补充错误处理分支。
- 根据上下文解释旧代码。
- 对比 iOS/Android/RN/Flutter 实现差异。

AI 不稳定的地方：

- 它可能误判项目真实架构。
- 它可能忽略平台生命周期。
- 它可能调用不存在或过时的 API。
- 它可能把逻辑放错层。
- 它可能忽略权限、弱网、旧版本兼容。
- 它可能生成局部正确但难维护的实现。

所以你的任务不是和 AI 比谁更会写语法，而是成为“上下文提供者、架构约束者、风险审查者、验证设计者”。

## 2. 接手一个客户端需求的标准流程

可以把工作流拆成七步。

```text
1. 定义需求边界
2. 阅读现有入口和架构
3. 画业务链路
4. 设计状态模型和数据策略
5. 给 AI 明确实现约束
6. 审查生成代码
7. 设计验证和上线风险检查
```

### 第一步：定义需求边界

先问清楚：

- 需求属于 iOS、Android、RN、Flutter 还是混合链路？
- 是新增页面、修改现有页面，还是接入平台能力？
- 是否涉及权限、支付、通知、定位、文件、相机？
- 是否需要兼容旧版本？
- 是否有埋点、灰度、AB 实验要求？

### 第二步：阅读现有入口和架构

不要直接让 AI 写新代码。先让它帮助你阅读：

- 页面从哪里进入。
- 当前页面状态在哪里定义。
- 网络请求通过哪个 Repository 或 Service。
- 路由、埋点、错误处理在哪里。
- 是否已有类似功能可以参考。

### 第三步：画业务链路

把需求写成链路：

```text
user event
  -> state change
  -> validation
  -> use case
  -> repository
  -> cache / network / platform
  -> result
  -> state update
  -> UI feedback
  -> analytics / logging
```

这一步能显著提高 AI 输出质量。

### 第四步：设计状态模型和数据策略

明确：

- loading、success、empty、error。
- submitting、submitted、failed。
- 权限授权、拒绝、永久拒绝。
- 缓存优先还是网络优先。
- 失败后是否保留用户输入。
- 是否需要乐观更新或草稿。

### 第五步：给 AI 明确实现约束

不要只说“帮我实现”。要说：

- 不要在 View 里直接调接口。
- 使用现有 ViewModel/Store。
- 复用现有 Repository。
- 错误类型要归一。
- 页面离开时取消任务。
- 加埋点但不要记录敏感信息。
- 按项目已有风格写测试。

### 第六步：审查生成代码

重点看：

- 是否放错层。
- 是否破坏现有架构风格。
- 是否遗漏生命周期。
- 是否处理权限拒绝和弱网。
- 是否重复提交或重复请求。
- 是否暴露敏感日志。
- 是否影响其他入口。

### 第七步：设计验证和上线风险检查

最后确认：

- 主路径可用。
- 失败路径可用。
- 页面返回、后台、权限拒绝、弱网可用。
- iOS/Android 行为一致或差异明确。
- 埋点和日志能帮助排查。
- 有灰度或开关时已接入。

## 3. 给 AI 的上下文要分层

一个高质量 prompt 通常包含这几层：

```text
目标：
  要实现什么业务结果

技术栈：
  iOS / Android / RN / Flutter / 混合

现有架构：
  View / ViewModel / Repository / Use Case / Service 的职责

业务链路：
  从用户事件到服务端结果再到 UI 反馈

状态模型：
  页面状态、表单状态、权限状态、上传状态

数据策略：
  缓存、重试、错误归一、同步、乐观更新

平台约束：
  生命周期、权限、后台、原生模块、插件

质量要求：
  埋点、日志、测试、性能、兼容性

输出要求：
  修改哪些文件、不要改哪些文件、需要补哪些测试
```

这比一句“帮我加个功能”更像真实工程协作。

## 4. 代码审查 checklist

AI 写完代码后，按这张表看：

| 维度 | 审查问题 |
| --- | --- |
| 架构 | 是否遵守 View / State / Repository 分层 |
| 状态 | 是否存在非法状态组合 |
| 生命周期 | 页面离开、后台、重建是否处理 |
| 权限 | 拒绝、永久拒绝、配置声明是否处理 |
| 数据 | 缓存、错误、重试、取消、一致性是否处理 |
| 平台 | iOS/Android 差异是否明确 |
| 跨端 | RN/Flutter 原生边界是否清楚 |
| 质量 | 埋点、日志、崩溃、性能是否考虑 |
| 测试 | 主路径和失败路径是否覆盖 |
| 风格 | 是否符合项目已有命名和模式 |

这张表会比“代码看起来对不对”更可靠。

## 5. 与客户端同事沟通的方式

你不需要一开始就比资深 iOS/Android 同事更懂平台细节，但你需要能提出正确问题。

好的问题是：

- 这个页面现在的状态来源在哪里？
- 这个功能是否已有 Repository 或 Use Case？
- 权限拒绝后的产品路径是什么？
- 这个跨端页面调用原生能力的入口在哪里？
- 这个请求页面离开后应该取消还是继续？
- 这个数据保存成功后哪些页面需要刷新？
- 这个 SDK 接入有没有审核或隐私风险？
- 这个功能能否通过远程配置关闭？

这些问题能让你快速进入团队语境，也能避免 AI 生成方案偏离现有工程。

## 6. 轻量验证：一次 AI 辅助开发任务

假设需求是：

> 在 RN 个人资料页新增头像上传，iOS 和 Android 都支持相册选择、裁剪、上传、失败重试。

你可以这样拆：

```text
平台：
  RN 页面，底层需要 iOS/Android 图片选择和裁剪能力。

入口：
  个人资料页点击头像。

状态：
  idle / requestingPermission / pickingImage / cropping / uploading(progress) / failed

数据：
  上传成功后更新 UserRepository 本地缓存，并通知资料页刷新。

平台能力：
  优先复用已有 image picker module。
  如果没有，评估第三方库或原生模块。

生命周期：
  页面离开时取消上传或保留后台上传，按产品决策。

质量：
  埋点：点击头像、授权拒绝、上传成功、上传失败。
  日志：上传失败原因，不记录图片内容。

验收：
  权限拒绝、取消选择、裁剪取消、弱网上传失败、重复点击都正常。
```

这个拆法能让 AI 在正确边界内工作，也能让你和原生同事讨论哪些部分需要他们支持。

## 7. 本课程的最终工作模板

以后遇到客户端需求，可以直接套用：

```text
1. 这个需求属于哪个端和哪个技术栈？
2. 它有哪些入口？
3. 它触碰哪些平台能力？
4. 页面状态模型是什么？
5. 数据从哪里来，缓存怎么处理？
6. 用户事件如何穿过 ViewModel/Store/UseCase/Repository？
7. 异常、弱网、权限拒绝、页面离开怎么处理？
8. iOS/Android/RN/Flutter 的边界在哪里？
9. 需要哪些埋点、日志、性能指标？
10. 如何测试和灰度？
```

你不必每次写长文档，但脑子里要过这十个问题。

## 8. 本章小结

- AI Coding 会把客户端开发者的价值推向上下文、架构、风险和验证。
- 接手需求时先读现有架构，再画业务链路，不要直接让 AI 写孤立代码。
- Prompt 要分层：目标、技术栈、架构、状态、数据、平台、质量、输出要求。
- 审查 AI 代码时重点看分层、生命周期、权限、数据一致性、平台差异和测试。
- 与客户端同事沟通时，要围绕平台边界和业务链路提问。

这门课到这里完成主体章节。你现在拥有的不是某个 API 清单，而是一套客户端业务迭代的判断框架。

## 思考题

### 题 1：AI Coding 时代，为什么开发者仍然需要理解客户端架构？

参考答案：

因为 AI 可以生成代码，但它需要正确上下文和边界。客户端开发涉及平台生命周期、权限、缓存、跨端桥接、性能、发布和监控，AI 很容易生成局部可用但工程不合适的实现。开发者需要判断代码是否放在正确层、是否处理平台风险、是否符合现有架构。

### 题 2：一个高质量客户端 prompt 应该包含哪些信息？

参考答案：

应包含业务目标、技术栈、现有架构、业务链路、状态模型、数据策略、平台约束、质量要求、测试验收和输出范围。这样 AI 才能按真实工程边界生成代码。

### 题 3：为什么要先让 AI 帮你读现有代码，而不是直接生成新实现？

参考答案：

因为已有 App 通常有自己的架构、命名、基础服务、路由、网络层、缓存和埋点体系。直接生成新实现容易破坏一致性或重复造轮子。先读现有代码能让 AI 复用项目模式，减少偏离工程风格的风险。
