# 第3章：嵌套结构与复杂配置

## 回扣本质

真实项目的配置从来不是扁平的——你需要多个数据库实例、多个中间件、各自带有不同参数。TOML 的 **`[nested.table]`** 和 **`[[array of tables]]`** 语法，让这些复杂结构在保持人类可读的同时，依然能精确映射到 Go 的嵌套 struct 和 slice。这正是"对人类友好"在复杂场景下的延伸。

---

## 3.1 嵌套表：点号语法 vs 分层声明

TOML 提供两种方式表达嵌套：

### 方式一：分层 `[table]`
```toml
[database]
host = "localhost"

[database.pool]
max_open = 25
max_idle = 5
```

### 方式二：点号键名
```toml
[database]
host = "localhost"
pool.max_open = 25
pool.max_idle = 5
```

两者完全等价。推荐：**嵌套层级少于3层用点号，超过则用分层声明**，可读性更好。

Go 映射：
```go
type DatabaseConfig struct {
    Host string     `toml:"host"`
    Pool PoolConfig `toml:"pool"`
}

type PoolConfig struct {
    MaxOpen int `toml:"max_open"`
    MaxIdle int `toml:"max_idle"`
}
```

---

## 3.2 表格数组：`[[]]` 语法详解

这是 TOML 最独特且最常被误解的特性。

**场景**：项目需要连接多个数据库实例（主库 + 只读副本）。

```toml
[[databases]]
name = "primary"
host = "db-master.internal"
port = 5432
role = "readwrite"

[[databases]]
name = "replica"
host = "db-replica.internal"
port = 5432
role = "readonly"

[[databases]]
name = "analytics"
host = "db-analytics.internal"
port = 5432
role = "readonly"
```

Go 映射——用 **slice**：
```go
type AppConfig struct {
    Databases []DatabaseInstance `toml:"databases"`
}

type DatabaseInstance struct {
    Name string `toml:"name"`
    Host string `toml:"host"`
    Port int    `toml:"port"`
    Role string `toml:"role"`
}
```

关键理解：**`[[xxx]]` 每出现一次，就是 slice 中新增一个元素**。

## 3.3 嵌套表格数组：表格数组内部还有子表

更复杂的场景：每个数据库实例还有自己的连接池配置和标签。

```toml
[[databases]]
name = "primary"
host = "db-master.internal"
port = 5432
tags = ["production", "critical"]

  [databases.pool]
  max_open = 50
  max_idle = 10
  max_lifetime = "30m"

[[databases]]
name = "replica"
host = "db-replica.internal"
port = 5432
tags = ["production", "readonly"]

  [databases.pool]
  max_open = 20
  max_idle = 5
  max_lifetime = "15m"
```

Go 映射：
```go
type DatabaseInstance struct {
    Name string   `toml:"name"`
    Host string   `toml:"host"`
    Port int      `toml:"port"`
    Tags []string `toml:"tags"`
    Pool PoolConfig `toml:"pool"`
}

type PoolConfig struct {
    MaxOpen     int    `toml:"max_open"`
    MaxIdle     int    `toml:"max_idle"`
    MaxLifetime string `toml:"max_lifetime"`
}
```

注意 `[databases.pool]` 的缩进只是为了可读性，TOML 不关心缩进——它通过**出现在哪两个 `[[databases]]` 之间**来确定归属。

## 3.4 实战产出：扩展 AppConfig

将第1章的单数据库配置升级为完整的多实例配置：

`config/app.toml`（扩展版）：

```toml
# AppConfig - 完整服务配置

[server]
host = "0.0.0.0"
port = 8080
read_timeout = 5
write_timeout = 10

# 多数据库实例
[[databases]]
name = "primary"
host = "localhost"
port = 5432
user = "admin"
password = "secret"
dbname = "myapp"
role = "readwrite"

  [databases.pool]
  max_open = 25
  max_idle = 5

[[databases]]
name = "replica"
host = "localhost"
port = 5433
user = "reader"
password = "readonly"
dbname = "myapp"
role = "readonly"

  [databases.pool]
  max_open = 10
  max_idle = 3

# 中间件配置
[[middlewares]]
name = "cors"
enabled = true

  [middlewares.options]
  allowed_origins = ["http://localhost:3000", "https://myapp.com"]
  allowed_methods = ["GET", "POST", "PUT", "DELETE"]
  max_age = 3600

[[middlewares]]
name = "ratelimit"
enabled = true

  [middlewares.options]
  requests_per_second = 100
  burst = 20

[[middlewares]]
name = "gzip"
enabled = false

  [middlewares.options]
  min_length = 1024

[log]
level = "info"
format = "json"
output = "stdout"

[features]
enable_signup = true
enable_oauth = false
maintenance_mode = false
```

对应的 Go 结构体：

```go
package main

import (
    "fmt"
    "os"

    "github.com/BurntSushi/toml"
)

type AppConfig struct {
    Server      ServerConfig       `toml:"server"`
    Databases   []DatabaseInstance `toml:"databases"`
    Middlewares []Middleware       `toml:"middlewares"`
    Log         LogConfig          `toml:"log"`
    Features    FeatureFlags       `toml:"features"`
}

type ServerConfig struct {
    Host         string `toml:"host"`
    Port         int    `toml:"port"`
    ReadTimeout  int    `toml:"read_timeout"`
    WriteTimeout int    `toml:"write_timeout"`
}

type DatabaseInstance struct {
    Name     string     `toml:"name"`
    Host     string     `toml:"host"`
    Port     int        `toml:"port"`
    User     string     `toml:"user"`
    Password string     `toml:"password"`
    DBName   string     `toml:"dbname"`
    Role     string     `toml:"role"`
    Pool     PoolConfig `toml:"pool"`
}

type PoolConfig struct {
    MaxOpen int `toml:"max_open"`
    MaxIdle int `toml:"max_idle"`
}

type Middleware struct {
    Name    string                 `toml:"name"`
    Enabled bool                   `toml:"enabled"`
    Options map[string]interface{} `toml:"options"`
}

type LogConfig struct {
    Level  string `toml:"level"`
    Format string `toml:"format"`
    Output string `toml:"output"`
}

type FeatureFlags struct {
    EnableSignup    bool `toml:"enable_signup"`
    EnableOAuth     bool `toml:"enable_oauth"`
    MaintenanceMode bool `toml:"maintenance_mode"`
}

func main() {
    var cfg AppConfig
    _, err := toml.DecodeFile("config/app.toml", &cfg)
    if err != nil {
        fmt.Fprintf(os.Stderr, "配置加载失败: %v\n", err)
        os.Exit(1)
    }

    fmt.Printf("服务器: %s:%d\n\n", cfg.Server.Host, cfg.Server.Port)

    fmt.Println("=== 数据库实例 ===")
    for _, db := range cfg.Databases {
        fmt.Printf("  [%s] %s@%s:%d/%s (pool: %d/%d)\n",
            db.Role, db.User, db.Host, db.Port, db.DBName,
            db.Pool.MaxOpen, db.Pool.MaxIdle)
    }

    fmt.Println("\n=== 中间件 ===")
    for _, mw := range cfg.Middlewares {
        status := "OFF"
        if mw.Enabled {
            status = "ON"
        }
        fmt.Printf("  %s [%s]\n", mw.Name, status)
    }
}
```

运行结果：
```
服务器: 0.0.0.0:8080

=== 数据库实例 ===
  [readwrite] admin@localhost:5432/myapp (pool: 25/5)
  [readonly] reader@localhost:5433/myapp (pool: 10/3)

=== 中间件 ===
  cors [ON]
  ratelimit [ON]
  gzip [OFF]
```

## 3.5 `map[string]interface{}` 的妙用

注意中间件的 `Options` 字段用了 `map[string]interface{}`——因为不同中间件的参数结构不同（cors 有 `allowed_origins`，ratelimit 有 `requests_per_second`）。

这是处理**异构配置**的常见模式：
- 结构确定的部分 → 用具体 struct
- 结构不确定的部分 → 用 `map[string]interface{}`

后续可以再做类型断言或二次反序列化。

## 章末思考题

**题1：** `[[databases]]` 和 `[databases]` 的本质区别是什么？如果你把 `[[databases]]` 误写成 `[databases]`，Go 代码会报什么错？

**参考答案：**
`[databases]` 定义一个普通表（对应 struct），`[[databases]]` 定义一个表格数组（对应 slice）。如果误写为 `[databases]` 但 Go struct 中字段是 `[]DatabaseInstance`，解析不会报错但 slice 长度为 0（类型不匹配时静默忽略）。反过来，如果 TOML 中用了 `[[databases]]` 但 Go 中字段是单个 struct 而非 slice，则会报 `type mismatch` 错误。这种不对称行为是常见 bug 来源。

---

**题2：** 中间件的 Options 用了 `map[string]interface{}`。如果 TOML 中 `allowed_origins = ["a", "b"]`，在 Go 中取出来的实际类型是什么？你怎么安全地转换它？

**参考答案：**
取出来的类型是 `[]interface{}`（而非 `[]string`）。安全转换方式：
```go
origins, ok := mw.Options["allowed_origins"].([]interface{})
if ok {
    for _, o := range origins {
        str, _ := o.(string)
        fmt.Println(str)
    }
}
```
更优雅的做法：先解析到 `map[string]interface{}`，再用 `mapstructure` 等库做二次绑定到具体 struct。这也解释了为什么**能用具体 struct 时尽量用 struct**——类型断言繁琐且容易出错。

---

**题3：** 如果未来新增一种中间件，配置结构和现有的完全不同，你需要改 Go 代码吗？这体现了什么设计取舍？

**参考答案：**
不需要改 Go 代码——因为 Options 是 `map[string]interface{}`，任何新键值都能被接收。但代价是：你失去了类型安全。如果新中间件的配置写错了（如 `max_agee` 拼错），编译器不会帮你发现。这是**灵活性 vs 类型安全**的经典取舍。折中方案：对已知中间件定义具体的 Options struct，只对"插件化"中间件保留 map。
