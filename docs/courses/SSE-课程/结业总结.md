# 结业总结

## 一、核心理念提炼

**理念一：协议的本质是约束，不是限制**

SSE 刻意舍弃了全双工、舍弃了二进制、舍弃了复杂握手。这些"舍弃"换来的是：任何能处理 HTTP 的基础设施都能透明代理它，任何能读文本的人都能调试它，任何能用几行代码的服务端都能实现它。好的协议设计不是"什么都能做"，而是"在正确的约束下做到最简单"。

**理念二：技术选型看能力边界，不看使用时长**

原生 EventSource 和 fetch SSE 都可以做持久连接，也都可以单次消费。选型的依据是能力需求（要不要 POST、要不要自定义头），而不是"谁是长连接谁是短请求"。把它们当作互补工具而非替代关系，才能做出正确的架构决策。

**理念三：SSE 的"简单"只在协议层，应用层的复杂度不会消失**

协议只有四个字段（data/id/event/retry），但生产环境要处理的连接管理、重连退避、心跳保活、消息去重、断点续传、认证刷新、缓冲对抗——每一项都是实打实的工程问题。SSE 把协议的复杂度降到了零，但把应用层的复杂度交给了你。

**理念四：每一层中间件都可能破坏 SSE 的前提**

SSE 依赖一个前提："响应不被缓冲，连接不被中断"。但 Nginx 会缓冲、CDN 会缓冲、负载均衡器会超时断开、Node.js 压缩中间件会缓冲。排查 SSE 问题的核心方法就是从外到内逐层绕过，找到破坏前提的那一层。

**理念五：重连策略是分布式系统问题，不是前端问题**

当 1000 个客户端同时断线又同时重连，重连策略直接决定服务端能否扛住。固定间隔、线性退避、指数退避+抖动——选择取决于你的部署规模。小项目随便选，大规模部署必须认真对待。

## 三、进阶方向

以下方向可以进一步深化 SSE 及相关领域的能力：

**方向一：WebTransport 与 HTTP/3 流式通信**
WebTransport 是下一代浏览器实时通信 API，基于 HTTP/3（QUIC），同时支持可靠流和不可靠数据报。能解锁：更低延迟的流式通信、不受 HTTP/1.1 6 连接限制、更适合高并发场景。

**方向二：SSE 在微服务架构中的事件分发设计**
Redis Stream / Kafka 消费者组 + SSE 网关的模式，实现跨服务的事件实时推送。能解锁：微服务间的实时数据同步、大规模 SSE 网关的横向扩展能力。

**方向三：AI 流式输出的工程化**
SSE 只是传输层，上层还有 token 计量、流式 JSON 解析（SSE 事件中的 data 可能是增量 JSON 片段）、中断恢复、多模型切换等工程问题。能解锁：构建生产级 AI 对话系统的能力。

**方向四：实时数据的可靠性保障**
Exactly-once 语义在 SSE 中的实现、消息顺序保证、背压控制（客户端处理不过来时如何通知服务端降速）。能解锁：金融级/支付级的实时数据推送能力。
