# 第2章：SDD 的核心工作流

> 第1章建立了"为什么需要 Spec"的认知，本章进入工作流本身——这正是 Power Inversion 的具体落地：意图如何一步步转化为可执行的代码。

---

## 2.1 工作流的五个阶段

spec-kit 的工作流是线性的，但每一步都有明确的输入/输出和角色分工：

```
Constitution
    ↓
Specify（Spec）
    ↓
Plan
    ↓
Tasks
    ↓
Implement
```

这不是随意排序——每一层的存在都有理由，顺序不能颠倒。

---

## 2.2 第零层：Constitution（治理文档）

**这是什么**：整个项目的开发宪法。在任何功能开始之前就存在，规定不可违反的工程原则。

**典型内容**：
- 测试策略（"TDD 强制，不可跳过"）
- 架构约束（"所有服务必须独立部署"）
- 代码标准（"无类型 any，100% TypeScript strict"）
- 安全原则（"所有外部输入必须验证"）

**为什么放最前面**：Constitution 是所有后续 Spec 和 Plan 的隐性约束。如果没有它，每次写 Plan 都要重新声明这些原则，或者 AI 会做出与团队规范不符的技术决策。

**对应关系**：类似于 CLAUDE.md，但更正式、更显式、有版本号。

---

## 2.3 第一层：Specify（Spec 文档）

**输入**：一句话的功能描述（用户意图）
**输出**：结构化的 Spec 文档
**谁来做**：人类描述意图，AI 辅助展开

`/speckit.specify` 命令接收描述，基于模板生成包含以下内容的文档：

```md
## User Stories（用户故事，按优先级排列）
  - 每个故事可独立开发、测试、部署
  - 每个故事有 Acceptance Scenarios（Given/When/Then）

## Functional Requirements（功能需求）
  - FR-001: 系统 MUST...
  - FR-002: 用户 MUST 能...

## Key Entities（核心数据实体）

## Success Criteria（可量化的成功指标）

## Assumptions（边界假设）
```

**关键设计原则**：Spec 只描述"什么"，不描述"怎么做"。它是技术无关的（technology-agnostic）。

---

## 2.4 第二层：Plan（技术实现规划）

**输入**：Spec 文档 + 技术栈选择
**输出**：技术架构文档
**谁来做**：AI 生成，人类 review

`/speckit.plan` 读取 Spec，结合技术栈偏好，生成：

- 技术架构决策（及决策理由）
- 数据模型（`data-model.md`）
- API 契约（`contracts/`）
- 测试场景（从 Acceptance Scenarios 转化而来）
- Quickstart 验证指南

**这里发生的事情**：Spec 的"用户故事"被翻译成"API 端点"，"数据实体"被翻译成"数据库 Schema"，"验收场景"被翻译成"测试用例骨架"。

---

## 2.5 第三层：Tasks（任务清单）

**输入**：Plan 文档（+ 可选的 data-model、contracts）
**输出**：原子化的任务列表
**谁来做**：AI 生成

`/speckit.tasks` 读取 Plan，生成每个任务有明确：
- 做什么
- 依赖哪些前置任务
- 完成的验证标准

**为什么 Plan 不够，还需要 Tasks**：Plan 是给人看的架构文档，Tasks 是给 AI 执行的指令序列。粒度不同，格式不同。Plan 说"实现用户认证模块"，Tasks 说"先建 users 表迁移 → 再实现 JWT 生成函数 → 再写登录端点 → 最后加速率限制中间件"。

---

## 2.6 第四层：Implement（执行）

**输入**：Tasks 清单
**输出**：可运行代码
**谁来做**：AI 执行，人类验收

`/speckit.implement` 按顺序执行任务清单。每个任务完成后，对照 Acceptance Scenarios 验证。

---

## 2.7 整体工作流结构图

```
┌─────────────────────────────────────────────┐
│               CONSTITUTION                   │
│  （项目治理层：原则 / 约束 / 不可违反规则）      │
└──────────────────┬──────────────────────────┘
                   │ 约束所有后续层
┌──────────────────▼──────────────────────────┐
│                  SPEC                        │
│  输入：用户意图（自然语言）                     │
│  输出：User Stories + FR + 验收场景            │
│  关键词：What，不是 How；技术无关               │
└──────────────────┬──────────────────────────┘
                   │ AI 翻译
┌──────────────────▼──────────────────────────┐
│                  PLAN                        │
│  输入：Spec + 技术栈选择                       │
│  输出：架构 + 数据模型 + API 契约 + 测试骨架    │
│  关键词：How；技术相关；可 review              │
└──────────────────┬──────────────────────────┘
                   │ AI 拆解
┌──────────────────▼──────────────────────────┐
│                  TASKS                       │
│  输入：Plan                                  │
│  输出：原子化任务序列（有依赖关系 + 验证标准）   │
└──────────────────┬──────────────────────────┘
                   │ AI 执行
┌──────────────────▼──────────────────────────┐
│               IMPLEMENT                      │
│  输出：可运行代码，对照 Acceptance Scenarios   │
└─────────────────────────────────────────────┘
```

---

## 2.8 工作流的本质：可追溯性

整个工作流最重要的特性不是某一层的内容，而是**每一层都能追溯到上一层**：

- 代码 → 可追溯到 Task
- Task → 可追溯到 Plan 里的某个技术决策
- Plan → 可追溯到 Spec 里的某个 User Story
- Spec → 可追溯到原始意图

这意味着：**任何变更都有明确的入口**。需求变了，改 Spec，重新生成 Plan 和 Tasks。技术选型变了，改 Plan，重新生成 Tasks。不需要在代码里找"这段逻辑是为了满足哪个需求"。

这也是为什么 SDD 对需求变化有天然的抵抗力——变更不是在实现层打补丁，而是在意图层重新表达。

## 章末思考题

**Q1（结构理解）**：为什么 Spec 和 Plan 要分成两层，而不是直接写一份"既有用户故事又有技术架构"的文档？这种分层设计解决了什么问题？

> **参考答案**：分层的核心价值是**关注点分离**。Spec 是产品思维的输出，Plan 是工程思维的输出。如果混在一起，产品经理 review 时会被技术细节干扰，工程师 review 时会被用户故事模糊焦点。更重要的是：**当需求变化时，你只需要改 Spec，Plan 可以重新生成**——如果两者混在一起，每次需求变更都要在同一份文档里同时修改意图描述和技术决策，极容易造成不一致。分层让变更的影响范围最小化。

**Q2（批判型）**：Constitution → Spec → Plan → Tasks → Implement，这个流程看起来相当重，对于一个 2 小时能做完的小功能，走完全套流程值得吗？

> **参考答案**：这是 SDD 最常见的现实挑战。spec-kit 的应对策略是：各层的投入是弹性的。Constitution 只需写一次（项目级），后续所有功能复用。对于小功能，Spec 可以很简短（一个 User Story + 两个验收场景），Plan 可以跳过详细的 data-model 文档，Tasks 可以只有3-4条。真正的问题不是"走完全套值不值"，而是"**什么粒度的 Spec 是这个功能规模下的最小充分约束**"。这个判断能力本身就是 SDD 实践的核心技能。

**Q3（应用型）**：在你过去的工作流里，"澄清文档 → 技术文档 → 执行"对应了 SDD 的哪几层？如果明天要接入 spec-kit，你会在哪里引入新的工作习惯，在哪里保持不变？

> **参考答案**：澄清文档 ≈ Spec，技术文档 ≈ Plan + Tasks（已经是任务粒度）。可以保持不变的：意图层的书写方式，以及任务粒度的技术拆分习惯。需要引入的：① 在澄清文档里增加 Given/When/Then 格式的验收场景；② 在项目初始化时写一份 Constitution，把隐性的工程原则显式化；③ 用 spec-kit 的模板标准化文档格式，让 AI 工具链能稳定读取和生成这些文档。
