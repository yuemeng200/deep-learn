# 第4章：SDD vs Vibe Coding vs TDD+AI——三种范式的比较框架

> 前三章我们从意图鸿沟出发，走完了 SDD 的完整工作流。现在退后一步：SDD 是唯一的 AI Coding 范式吗？当然不是。这一章要做的是建立一套评估框架，让你在面试中能说清楚"每种模式擅长什么、不擅长什么、什么时候该用哪个"。

---

## 4.1 三种范式的一句话定义

**Vibe Coding**：持续向 AI 表达意图，通过迭代修正逼近目标。"我觉得应该这样……不对，改一下……再调调……"——核心是**实时反馈循环**。

**SDD（Spec-Driven Development）**：先写结构化的规格文档，再让 AI 在规格约束下执行。"先把想要什么写清楚，然后按规格生成"——核心是**前置约束**。

**TDD+AI**：先写测试用例（期望行为），让 AI 生成通过测试的代码。"测试定义了正确性，AI 负责实现"——核心是**行为约束**。

---

## 4.2 统一评估框架

五个维度，用来对三种范式做公平比较：

| 维度 | 含义 |
|------|------|
| **意图传递效率** | 从"脑子里想的"到"AI 理解的"，信息损耗有多大？|
| **可验证性** | 生成的代码是否可以独立验证正确性？|
| **适用场景** | 在什么类型的项目/团队中效果最好？|
| **认知负担** | 人类的心智投入集中在哪些环节？有多重？|
| **团队协作性** | 多人协作时，工作流是否可持续？|

---

## 4.3 对比矩阵

| | Vibe Coding | SDD | TDD+AI |
|---|---|---|---|
| **意图传递效率** | ⚡ 最高——实时对话，即时修正 | 🔄 中等——Spec 写完才执行，前期投入大 | 🔄 中等——测试用例本身就是意图表达，但只覆盖行为 |
| **可验证性** | ❌ 最弱——没有独立的验证锚点，靠人眼看 | ✅ 强——Acceptance Scenarios 可直接生成测试 | ✅ 最强——测试先行，代码必须通过测试才算完成 |
| **适用场景** | 原型探索、个人项目、小功能、快速验证想法 | 中大型功能、团队协作、需求变更频繁的项目 | 逻辑密集型功能、API 层、算法实现 |
| **认知负担** | 执行期重——持续在线审查和修正 | 前期重——写 Spec 和 review Plan 需要深度思考 | 中期重——写测试需要同时持有"期望行为"和"实现约束" |
| **团队协作性** | ❌ 最弱——意图存在于对话历史中，不可共享 | ✅ 最强——Spec/Plan 是版本化的文档，可 review | 🔄 中等——测试文件可共享，但意图上下文不一定清晰 |

---

## 4.4 逐维度的深度解读

### 意图传递效率：Vibe Coding 的主场

Vibe Coding 的优势是**零摩擦启动**——想到什么说什么，AI 立刻响应。对于探索性任务（"我想试试这个效果"），这是最高效的方式。

但它的效率是**局部效率**。每次启动新任务，意图从零重新表达。不存在跨任务的意图复用。

SDD 的效率是**全局效率**。Spec 写一次，Plan 可以重新生成多次。同一个 Spec 可以生成不同技术栈的 Plan。但前期的一次性成本确实高。

**面试话术**："Vibe Coding 在单次任务的迭代速度上是最快的，但它缺乏跨任务的意图复用。SDD 用前期的 Spec 投入换来了后续所有任务的可追溯性和可复用性。两者不是对立的，而是不同粒度下的最优选择。"

---

### 可验证性：SDD 和 TDD 各有侧重

SDD 的可验证性来自 Acceptance Scenarios——它们验证的是**用户行为**（"点击书签后图标变了"）。

TDD 的可验证性来自测试用例——它们验证的是**代码行为**（"调用 toggle 返回 200 且 bookmarked 为 true"）。

关键区别：**SDD 的验证锚点在用户层，TDD 的验证锚点在实现层**。SDD 的 Acceptance Scenarios 可以直接转化为 TDD 的测试用例，但反过来不行——测试用例无法告诉你"这个 API 设计是不是用户想要的"。

这也是为什么 spec-kit 把 Acceptance Scenarios 放在 Spec 层而不是 Plan 层——验证用户意图应该在技术实现之前。

---

### 适用场景：三种模式的"最强主场"

**Vibe Coding 最强场景**：快速原型。你要在 2 小时内验证一个想法是否可行，写 Spec 纯属浪费时间。直接开聊，快速迭代，得到一个能跑的东西。**探索期的最优选择。**

**SDD 最强场景**：需求变更频繁的中大型项目。因为 Spec 和 Plan 分离，需求变了只需要改 Spec，Plan 可以重新生成。如果是在实现层直接改代码，每次需求变更的成本是累加的；在 SDD 里，成本是重生的（regenerate）。

**TDD+AI 最强场景**：逻辑密集型功能。支付计算、权限判断、状态机、数据转换——这些功能的正确性可以被精确定义为输入→输出的映射，测试用例能穷举关键路径。AI 在这些场景下的价值是"生成通过测试的实现"，而测试本身保证正确性。

---

### 认知负担：不同阶段的压力分布

```
         启动期        执行期        维护期
Vibe:     低 ████████   高 ████████████  高 ████████████
SDD:      高 ████████████ 中 ████████     低 █████
TDD+AI:   中 ████████   中 ████████      低 ██████
```

Vibe Coding 的认知负担是**后置的**——启动毫不费力，但执行中要持续审查 AI 的输出，维护时要在没有文档的情况下理解"当初为什么这样做"。

SDD 的认知负担是**前置的**——写 Spec 和 review Plan 是最费脑的部分，但执行和维护阶段的压力很低，因为一切可追溯。

TDD+AI 的认知负担是**均匀分布的**——写测试需要提前思考，但边界清晰，执行时 AI 在测试的约束下生成代码，维护时测试本身就是文档。

---

### 团队协作性：SDD 的结构性优势

Vibe Coding 在多人协作中的致命问题：**意图存在于对话历史中**。A 做了某个功能，B 要改它，B 唯一的信息源是代码本身和 A 的记忆。

SDD 的文档体系天然支持团队协作：Spec 可以被产品经理 review，Plan 可以被架构师 review，Tasks 可以被任何开发人员执行。每一层都有明确的**审查者和责任人**。

TDD+AI 的协作性介于两者之间：测试文件是共享的、可版本化的，但"为什么写这些测试"的意图上下文不一定被记录。

---

## 4.5 一个关键洞察：三种模式不是互斥的

最成熟的 AI Coding 工程师不是"选一种模式用到底"，而是**在不同阶段切换不同模式**：

```
探索期 → Vibe Coding（快速验证想法）
    ↓ 确定方向后
定义期 → SDD（写 Spec，锁定意图）
    ↓ Spec 完成后
实现期 → TDD+AI（测试驱动 AI 实现）
    ↓ 测试通过后
维护期 → SDD（Spec 是变更入口）
```

---

## 4.6 面试中如何聊这个话题

面试官可能问："你觉得 Spec-Driven Development 好还是 Vibe Coding 好？"

**错误回答**：站队。说"SDD 好"或"Vibe 好"都是减分的。

**正确回答框架**：

> "这两种模式不是对立的，它们解决的是 AI Coding 工作流中不同阶段的问题。Vibe Coding 擅长探索期的快速验证，SDD 擅长需求稳定后的结构化实现。我自己的实践是：用 Vibe 做探索，确认方向后切换到 Spec-Driven 的结构化流程。关键是知道什么时候该从一种模式切换到另一种——这个判断标准是：**当你发现自己在重复修正同一个意图偏差时，就该停下来写 Spec 了**。"

## 章末思考题

**Q1（综合型）**：你在第1章的延伸讨论中说自己的工作流已经和 SDD 高度同构。现在有了这个对比框架，你的工作流在这五个维度上的短板分别是什么？

> **参考答案**：短板主要在两个维度。① 可验证性：验证方式是描述性的而非可执行的（没有 Given/When/Then），无法自动转化为测试用例。② 团队协作性：如果意图上下文存在于对话历史或个人记忆中（而不是版本化的 Spec 文档），多人协作时信息会丢失。其他三个维度（意图传递效率、适用场景、认知负担）你的工作流已经覆盖得不错。

**Q2（应用型）**：假设你明天要做一个"用户通知系统"——涉及多种通知渠道（邮件/站内信/Push）、通知模板管理、用户偏好设置。你会选择哪种范式？还是混合使用？

> **参考答案**：这是典型的"混合使用"场景。通知系统的核心逻辑（发送流程、模板渲染、偏好过滤）是逻辑密集型的，适合 TDD+AI——用测试定义"发送邮件通知时应正确应用用户偏好"。系统的整体需求（用户能配置通知偏好、管理员能管理模板）适合 SDD——写 Spec 锁定用户故事和验收场景。而通知渠道的集成细节（邮件 SDK、Push 服务配置）适合 Vibe Coding——快速试错。三种模式在这个项目里各有用武之地。

**Q3（批判型）**：对比矩阵里 SDD 在"团队协作性"上得分最高。但如果团队成员都不愿意写 Spec、不愿意 review Plan，SDD 的这个优势是不是不成立？这说明什么？

> **参考答案**：这说明**工具和方法论的能力上限不等于实际可达的效果**。SDD 的团队协作优势是结构性的，但实现它需要团队文化的配合——愿意在前期投入时间写 Spec 和 review Plan。如果团队没有这个文化，SDD 会变成形式主义的负担（写了 Spec 没人看，Plan review 变成走过场）。这也是为什么面试中说"SDD 好"不如说"SDD 在什么条件下好"——方法论的适用性取决于组织条件，而不仅仅是技术条件。
