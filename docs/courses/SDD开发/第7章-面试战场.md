# 第7章：面试战场——如何系统性地表达这套认知

> 6章的学习，最终要在一个场景里收束：面试。本章不是教你怎么背答案，而是帮你在面试中展示一种稀缺能力——"我不只是 AI Coding 的使用者，我是 AI Coding 方法论的思考者"。

---

## 7.1 面试中的核心定位

面试官问 SDD 相关问题，本质在考察的不是"你知不知道 spec-kit"，而是三个层次：

1. **你用 AI 写代码吗？**（基本盘——确认你有实际经验）
2. **你用 AI 写代码的方式有方法论吗？**（进阶——确认你不是无脑 Vibe）
3. **你能批判性地评估不同方法论吗？**（高级——确认你有独立思考能力）

你的定位应该是**第三层**——不是 SDD 的布道者，而是"理解了 SDD 的设计逻辑，也知道它的边界，能根据场景选择合适模式"的工程师。

---

## 7.2 高频面试问题与回答框架

### 问题一："你怎么用 AI 辅助开发？"

**❌ 软回答**：
> "我用 Claude Code 写代码，plan 模式，挺好用的。"

没有方法论，没有思考，只是一个工具使用者。

**✅ 硬回答**：
> "我的 AI Coding 工作流分为探索和实现两个阶段。探索期用 Vibe Coding 快速验证方向，确认方向后切换到结构化流程——先写意图文档（类似 Spec），然后拆成任务粒度的技术文档让 AI 执行。这个流程和 Spec-Driven Development 的理念高度一致：Spec 是意图层（What），技术文档是实现层（How），两层分离的好处是需求变更时只需要改意图层，实现层可以重新生成。"

**为什么这个回答有力**：30秒内展示了"我有实际经验"+"我理解背后的设计逻辑"+"我能把它和行业方法论关联起来"。

---

### 问题二："你了解 Spec-Driven Development 吗？怎么看？"

**❌ 站队回答**：
> "SDD 很好，比 Vibe Coding 靠谱多了。"

没有深度，面试官追问就会露馅。

**✅ 分析回答**：
> "SDD 的核心主张是 Power Inversion——让代码服务于规格，而不是规格服务于代码。这在 AI Coding 时代是有意义的，因为 AI 的'合理补全'机制会填补你没说清楚的空白，Spec 提供了显式的约束。但 SDD 不是万能的，它的局限在于：前期投入高（写 Spec 需要深度思考），对团队文化有要求（大家得愿意写和 review Spec），而且对于探索性任务来说 Spec 是过度工程化的。所以我倾向于混合使用：探索期 Vibe，稳定期 SDD，逻辑密集的部分 TDD+AI。关键是知道什么时候切换。"

**为什么这个回答有力**：展示了完整的理解（知道 SDD 是什么、为什么有道理）+ 批判性思考（知道边界在哪）+ 实践智慧（不是站队，而是根据场景选择）。

---

### 问题三："你觉得 AI 会取代程序员吗？"

**❌ 两极回答**：
> "不会，AI 写的代码质量不行。" 或 "会，以后只要写 Spec 就行了。"

**✅ 框架回答**：
> "AI 改变的是'编码'这个动作的成本，不是'工程'这个活动的价值。用 Harness Engineering 的框架来看：AI 能高效完成从 Spec 到代码的转化（Layer 2），但工具约束（Layer 1）、上下文一致性（Layer 3）、质量验证（Layer 4）、团队协作（Layer 5）这些层面仍然需要人类工程师来设计和维护。工程师的价值从'写代码'转移到了'设计约束框架'和'审查意图质量'。这不是被取代，而是角色的升级。"

---

### 问题四："你们团队的 AI Coding 工作流是什么样的？"

**❌ 流水账回答**：
> "我们用 Cursor，先写 .cursorrules，然后用 Agent 模式写代码。"

**✅ 结构化回答**：
> "我们用的是五层 Harness 框架。最底层是工具权限控制，确保 AI 不能做超出授权的事。第二层是 Spec 驱动——新功能先写 Spec，由 AI 生成技术 Plan，拆成 Tasks 后执行。第三层是上下文管理——通过 CLAUDE.md 这类文件确保每次 AI 对话都有一致的项目上下文。第四层是 CI/CD 验证——AI 生成的代码必须通过自动化测试和 lint。第五层是组织流程——PR review 时对照 Spec 审查，而不只是看代码。这五层共同约束了 AI 的编码行为。"

**为什么这个回答有力**：它把"我们团队怎么做的"从工具层面提升到了框架层面。面试官能感受到你不只是在描述操作流程，而是在描述一个有设计感的体系。

---

## 7.3 常见陷阱

### 陷阱一：把 SDD 当成唯一正确答案

面试官可能故意挑战："SDD 这么好，为什么不是所有团队都在用？"

**应对**：回到第4章的对比框架——SDD 在意图传递效率上不如 Vibe Coding，在前置投入上比 TDD 更重。它最适合的是需求变更频繁、多人协作的中大型项目。不是所有场景都需要 SDD，也不是所有团队都准备好了采用 SDD。

### 陷阱二：用术语堆砌代替理解

如果你说"Power Inversion""Intent Gap""Harness Engineering"但解释不清楚，面试官一眼就能看出来。

**应对**：每个术语只用一次，用在完整的论述里，而不是罗列。一个说清楚的例子比三个术语加分得多。

### 陷阱三：贬低 Vibe Coding

有些候选人会说"Vibe Coding 是初学者才用的"。这是减分项。

**应对**：Vibe Coding 在探索期是最有效的模式。你自己的工作流里也包含 Vibe Coding 阶段。展示你知道何时使用它，而不是贬低它。

---

## 7.4 把你的 Vibe Coding 经验转化为加分项

你最大的资产不是"学了 SDD"，而是"有丰富的 Vibe Coding 实战经验 + 现在有了 SDD 的理论框架来理解和优化自己的实践"。

面试中的表达策略：

> "我过去一直用 Vibe Coding 模式开发，积累了大量实战经验。在学习了 SDD 之后，我意识到自己的工作流——澄清文档 + 技术文档 + AI 执行——在结构上已经和 SDD 高度同构。SDD 给了我两样新东西：一是 Acceptance Scenarios 的可执行格式（Given/When/Then），让验证条件可以直接转化为测试用例；二是 Constitution 层，把隐性的工程原则显式化为项目治理文档。我的下一步实践方向是把这些增量整合进现有工作流，而不是推翻重来。"

这段话展示了：经验丰富、有自我反思能力、能快速吸收新方法论、务实（不教条）。

## 章末思考题

**Q1（模拟型）**：面试官说"我们团队现在纯 Vibe Coding，经常出问题，你觉得应该怎么改进？"你会怎么回答？给出你的回答大纲。

> **参考答案**：不应该说"你们应该上 SDD"。应该问清楚问题出在哪：① 如果是"AI 生成的不是想要的"→ 意图层的问题，可以引入轻量 Spec（不需要完整流程，先从 User Stories + Acceptance Scenarios 开始）；② 如果是"不同人产出风格不一致"→ 上下文管理的问题，加 CLAUDE.md；③ 如果是"线上 bug 太多"→ 验证层的问题，加 CI/CD。诊断先于处方——先搞清楚哪个 Harness 层缺失，再有针对性地补。

**Q2（自我评估型）**：如果用一句话向面试官总结你对 AI Coding 的理解，你会说什么？

> **参考答案**（参考方向）：每个人的答案应该不同，但应该包含三个要素：① 你对 AI Coding 的定位（工具/伙伴/协作框架）；② 你理解的核心挑战（意图鸿沟/质量约束/团队协作）；③ 你的实践策略（不是站队某种模式，而是根据场景选择）。
