# 第1章：为什么需要 Spec？

> 这门课的核心本质是「AI 时代人的价值在哪里」。第一章是这个问题的起点——不是给出答案，而是把问题真正暴露出来。

---

## 1.1 你已经遇到过这个问题

你用 Claude Code plan 模式开发，大概率经历过这种场景：

你描述了一个功能，AI 给出了一个计划，你确认，它开始实现。结果出来的代码在逻辑上是"对的"，但不是你想要的——它的交互方式、边界处理、数据结构，跟你脑子里的版本有出入。然后你开始修正，来回几轮，最终产出和最初意图之间存在"漂移"。

这不是 Claude 的问题，也不是你描述得不够清楚的问题。**这是一个结构性问题：意图（Intent）和实现（Implementation）之间存在天然的鸿沟。**

---

## 1.2 意图鸿沟（Intent Gap）

意图鸿沟指的是：**你脑子里的"想要什么"和 AI 实际执行的"做了什么"之间的偏差空间。**

这个鸿沟的来源有三层：

**① 自然语言的模糊性**

"做一个用户登录功能"——这句话里有多少隐含假设？
- 是 email/password，还是 OAuth？
- 失败几次后锁定？
- Token 存在哪里？有效期多长？
- 是否需要记住我？
- 移动端和 PC 端行为一样吗？

你以为你说清楚了，因为这些问题在你脑子里有答案。但你没有说出来。

**② AI 的"合理补全"机制**

AI 不会停下来说"我不知道"。它会用最"合理"的方式填补你没说清楚的部分。这种合理性来自训练数据里的常见模式——它会做一个"普通"的登录，而不是你项目里"特定"的登录。

**③ 迭代中的意图漂移**

Vibe Coding 的典型模式是：描述 → 生成 → 修正 → 再生成。每一轮修正都是在修"偏差"，但你的真实意图从未被显式表达过。修了3轮之后，代码越来越接近你想要的，但整个过程的认知负担都在你身上——你是在"用修正来代替表达"。

---

## 1.3 传统软件工程的解法及其失败

软件工程几十年来一直在想办法填这个鸿沟。解法有很多：

- **写需求文档（PRD）**：人工翻译意图，但文档和代码很快脱节
- **写用例（Use Cases）**：更结构化，但仍然是参考，不是约束
- **TDD**：用测试表达期望行为，但只覆盖了功能边界，不覆盖设计意图
- **设计评审（Design Review）**：人工对齐，成本高，不可持续

这些方法有一个共同的失败模式：**它们都接受了"代码是最终真相"这个前提**。文档是参考，代码是真相。随着时间推移，文档不更新，代码和意图的距离越来越大。

spec-kit 在文档里把这个历史问题描述为：

> "Specifications served code — they were the scaffolding we built and then discarded once the 'real work' of coding began."

规格服务于代码，代码完成了，规格就被扔掉了。

---

## 1.4 Power Inversion：SDD 的根本主张

SDD 的核心主张只有一句话：

**让代码服务于规格，而不是规格服务于代码。**

这是一个权力结构的翻转（Power Inversion）。

在这个新结构里：
- **Spec 是"源代码"**，它表达的是意图
- **代码是 Spec 的"编译产物"**，它是意图在某个语言/框架里的一次实例化

这意味着什么？

| 传统范式 | SDD 范式 |
|---------|---------|
| 代码是真相，文档是注释 | Spec 是真相，代码是输出 |
| 维护软件 = 改代码 | 维护软件 = 改 Spec |
| Bug 修复 = 改实现 | Bug 修复 = 修正意图表达 |
| 重构 = 整理代码结构 | 重构 = 重新表达清楚 |

**为什么现在才可行？**

因为 AI 的能力到达了一个阈值——自然语言的规格可以可靠地生成可运行的代码。这在 5 年前不成立，现在成立了。

spec-kit 的文档把这个时机表述为「三个收敛」：AI 能力到达阈值 × 软件复杂度持续增长 × 需求变化速度加快。**SDD 不是一种偏好，而是对这个时代特征的一种适应。**

---

## 1.5 Spec 的本质功能

理解了意图鸿沟和 Power Inversion 之后，Spec 的功能可以被精确定义：

**Spec 是意图的显式化合约。**

它做三件事：
1. **强迫意图具体化**：写 Spec 的过程，就是把你脑子里模糊的想法变成可以被检验的陈述
2. **创造一个可审查的节点**：在执行之前，人类可以 review 的不是代码，而是意图——这大幅降低了发现偏差的成本
3. **为 AI 创造约束空间**：AI 在 Spec 的约束下生成，而不是在"合理补全"的自由空间里漫游

这正是 Claude Code plan 模式在做的事——只是 plan 通常是即兴生成的，不是结构化的、版本化的规格。SDD 的升级在于：**把这个 plan 变成显式的、持久化的、可版本化的合约文档。**

## 章末思考题

**Q1（理解型）**：意图鸿沟存在于所有的人机协作中，不只是 AI Coding。你能举一个非 coding 场景里意图鸿沟导致问题的例子，并说明它和 AI Coding 里的意图鸿沟有何相似之处？

> **参考答案**：比如向设计师提需求："做一个简洁的首页"。设计师和你对"简洁"的理解可能截然不同——你想的是信息密度低，他做的是元素少但留白多。出来之后你说"不对"，但问题不在执行，在于意图从没被显式化。这和 AI Coding 的本质完全一样：自然语言携带了大量隐含假设，执行方（人或 AI）用"合理补全"来填补——结果和预期有偏差。

**Q2（批判型）**：SDD 主张"Spec 是真相，代码是输出"。但如果 Spec 写错了，岂不是会系统性地生成错误代码？这个风险比"代码写错了"更大还是更小？为什么？

> **参考答案**：这是 SDD 最核心的风险——错误前移（error propagation upstream）。Spec 错误会比代码错误更难发现，因为它发生在执行之前，没有运行时的即时反馈。但 SDD 的应对策略是：**Acceptance Scenarios（验收场景）**。好的 Spec 里包含可测试的验收条件，这些条件会在代码生成后被验证。所以本质上风险不是更大，而是不同——代码 bug 是在实现层修，Spec 错误要在意图层修，修的成本更低但需要更强的提前思考能力。这也是为什么「Spec 的质量」是 SDD 里最关键的变量（第5章的主题）。

**Q3（迁移型）**：你现在用的 Claude Code plan 模式，和 SDD 最大的区别是什么？如果要把你现有的工作流往 SDD 方向迁移，第一步应该改变什么？

> **参考答案**：Claude Code plan 模式的 plan 是**即兴的、一次性的、不持久化的**——它在对话里生成，完成后就消失了，下一次开始新任务时从零来过。SDD 的核心升级是：**把 plan 变成显式的、持久化的、版本化的 Spec 文档**。迁移的第一步，不是换工具，而是改变习惯：在每次开始任务之前，先把意图写成一个文档（哪怕粗糙），让 AI 基于这个文档来执行——而不是在对话中即兴生成计划然后立即执行。

---

## 1.6 延伸讨论：已有工程实践与 SDD 的边界在哪里？

> 本节来自课程讨论，记录一个重要的认知校正。

一个常见的误区是：以为自己的工作流和 SDD 相去甚远。但如果你过去的工程实践是这样的——

**PRD → 澄清文档（非技术意图层，详细描述需求链路）→ 技术文档（按模块拆分，每个模块有技术实现描述、边界和验证方式，粒度已到任务级别）→ AI 辅助执行**

那么这个结构与 SDD 是**高度同构的**：

| 你的工作流 | SDD（spec-kit）|
|-----------|---------------|
| 澄清文档 | Spec（用户意图层）|
| 技术文档（任务粒度）| Plan + Tasks |
| AI 辅助翻译 | `/speckit.plan` + `/speckit.tasks` |

**真正的增量差别只有两处**：

**① Acceptance Scenarios 的格式规范**

你的验证方式是描述性的，SDD 要求使用 Given/When/Then 格式。这不是有没有验证的区别，而是**AI 能否直接从验收条件生成测试用例**的区别——是工程化程度的问题，不是结构问题。

**② Constitution 层**

spec-kit 引入了一个针对整个项目的治理文档，记录不可违反的开发原则（如"测试优先"、"所有模块独立可测"）。它不针对单个功能，而是所有 Spec 和 Plan 的上层约束。你的工作流里可能有 CLAUDE.md 或类似文件在起这个作用，但不一定被显式命名和版本化。

**结论**：如果你已经有澄清文档 + 任务粒度技术文档 + AI 翻译的工作流，你已经在实践 SDD 的核心理念。spec-kit 做的是把这套流程**标准化、工具化**，并补齐 Constitution 治理层和 Acceptance Scenarios 的可执行格式。在面试中，这是一个有力的表述起点：*"我一直在实践 SDD 的核心理念，spec-kit 是它的工具化实现。"*
