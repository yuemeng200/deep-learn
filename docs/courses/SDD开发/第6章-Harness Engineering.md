# 第6章：Harness Engineering——SDD 之上的更大框架

> 前5章我们把 SDD 从理念到实践到质量标准都讲透了。现在要做的最后一步认知升级是：SDD 不是终点，它是 Harness Engineering 这个更大框架中的一层。理解这个框架，你就能在面试中说："SDD 解决的是意图层的问题，但 AI Coding 的完整约束需要更多层的协作。"

---

## 6.1 什么是 Harness Engineering

Harness 的原意是"马具"——给马套上缰绳，不是为了限制马的奔跑能力，而是为了**让马的力量在可控方向上释放**。

Harness Engineering 就是：**构建系统性的约束框架，让 AI 编码能力在可控、可验证、可追溯的轨道上运行。**

SDD 是这个框架的一部分，但不是全部。

## 6.3 逐层解读

### Layer 1：工具约束层——硬边界

**问题**：AI 能执行 shell 命令、能读写文件、能调 API——如果不限制，它可能删库、发邮件、改配置。

**Harness 手段**：
- 文件权限控制（只允许读写特定目录）
- 工具白名单（只暴露 git/测试/lint 相关命令）
- 执行超时（单个任务最长运行时间）
- 沙箱隔离（在容器里执行，不影响宿主环境）

**Claude Code 的实现**：每次 AI 要执行一个有副作用的操作（写文件、运行命令），都会弹出权限确认。这个确认机制就是 Layer 1 的 Harness。

**面试话术**："工具约束层是 Harness 的底线——它不关心 AI 写的代码质量如何，只确保 AI 不能做超出授权范围的事。这是安全层，不是质量层。"

---

### Layer 2：Spec 驱动层——意图约束

**问题**：AI 能写代码了，但写的代码是不是你想要的？

这就是前5章讲的全部内容。SDD 的 Constitution/Spec/Plan/Tasks 就是在约束"AI 写的代码应该满足什么意图"。

这一层解决的是**方向性问题**——AI 在正确的方向上努力。

---

### Layer 3：上下文管理层——一致性约束

**问题**：AI 每次启动新对话时，对项目的理解是空白的。它不知道你的团队用什么代码风格、有哪些架构约束、测试策略是什么。

**Harness 手段**：
- **CLAUDE.md**：Claude Code 的持久化指令文件，每次对话自动加载
- **.cursorrules / .clinerules**：Cursor/Cline 的等效文件
- **Constitution（spec-kit）**：SDD 流程中的治理文档

它们的共同特征：**文件存在于项目仓库中，被版本化管理，每次 AI 启动时自动读取。**

这一层解决的是**一致性问题**——不同的 AI 对话、不同的开发者，产出符合统一标准的代码。

---

### Layer 4：持续验证层——质量守门

**问题**：即使 Spec 写得好、上下文管得好，AI 生成的代码仍然可能有 bug。谁来把关？

**Harness 手段**：
- **CI/CD Pipeline**：每次提交自动运行测试、lint、构建
- **测试覆盖率门槛**：低于阈值不允许合并
- **安全扫描**：检测依赖漏洞、敏感信息泄露
- **代码质量门禁**：Sonar/ESLint 等静态分析

这一层解决的是**底线质量问题**——不管 AI 还是人写的代码，都必须通过自动化验证才能进入主分支。

**关键认知**：CI/CD 不是新的东西，但在 AI Coding 时代它的角色变了。过去 CI 是"人写的代码的最后一道保险"，现在 CI 是"AI 生成的代码的第一道验证"。**AI 生成速度远超人类，如果没有自动化验证层，技术债务的积累速度也会远超人类手动 review 能处理的范围。**

---

### Layer 5：组织流程层——人类协作

**问题**：AI 生成的代码谁来 review？多个 AI Agent 同时工作如何协调？

**Harness 手段**：
- **PR 流程**：AI 生成的代码走同样的 PR review 流程
- **分支策略**：每个 Spec 对应一个 feature branch（spec-kit 自动创建）
- **Code Review 协议**：review 者对照 Spec 和 Plan 审查，而不是只看代码
- **多 Agent 协调**：不同 AI Agent 负责不同 User Story，通过 Git 合并

这一层解决的是**协作问题**——让 AI 和人类、AI 和 AI 之间的协作可控。

---

## 6.4 SDD 在 Harness 中的定位

**SDD 是 Layer 2 + Layer 3 的一部分**。它提供了功能级的意图约束（Spec）和项目级的一致性约束（Constitution）。但它不涉及工具权限（Layer 1）、自动化验证（Layer 4）、或团队流程（Layer 5）。

这意味着：**一个只用了 SDD 的团队，只解决了 Harness 的一部分问题。** 如果没有 CI/CD（Layer 4）和 Review 流程（Layer 5），SDD 生成的代码质量仍然依赖人工审查。

反过来也成立：**一个有完善 CI/CD 和 Review 流程但没有 SDD 的团队，解决了质量守门和协作问题，但每一段 AI 生成的代码缺少意图层的约束——还是在 Vibe Coding，只是 Vibe 得更规范了。**

---

## 6.5 你的现有实践在 Harness 中的位置

| Harness 层 | 你的现状 |
|-----------|---------|
| Layer 1 工具约束 | ✅ Claude Code 的权限确认机制 |
| Layer 2 Spec 驱动 | 🟡 有澄清文档（≈Spec），缺 Given/When/Then 和 Constitution |
| Layer 3 上下文管理 | ✅ CLAUDE.md + Skills |
| Layer 4 持续验证 | ❓ 取决于项目是否有 CI/CD |
| Layer 5 组织流程 | ❓ 取决于团队是否有 PR review 流程 |

如果面试官问"你现在的 AI Coding 工作流是什么"，你可以用这个五层框架来组织回答——比说"我用 Claude Code plan 模式"要有层次得多。

## 章末思考题

**Q1（框架型）**：Devin、Cursor Agent、GitHub Copilot Workspace 这些"AI 软件工程师"产品，分别覆盖了 Harness 的哪些层？

> **参考答案**：Devin 覆盖了最全——它有自己的沙箱（Layer 1）、可以读取项目文档（Layer 3）、能执行测试和部署（Layer 4），甚至能提 PR（Layer 5）。Cursor Agent 主要覆盖 Layer 1（IDE 内执行权限）和 Layer 2（可以通过 prompt 约束意图）。Copilot Workspace 则试图覆盖 Layer 2 到 Layer 4（从 issue 生成 plan、实现、跑测试）。但没有任何一个产品完整覆盖了所有五层——这正是为什么 Harness Engineering 是一个框架而不是一个产品。团队需要组合不同工具来构建完整的 Harness。

**Q2（批判型）**：如果 Layer 4（CI/CD）足够强大，是否可以不需要 Layer 2（SDD）？反正代码通不过测试就会被拦截。

> **参考答案**：不行，因为它们约束的是不同的东西。Layer 4 约束的是**代码的正确性**（测试是否通过），Layer 2 约束的是**代码的意图**（这是不是你想要的功能）。一个 AI 可以写出测试全部通过、但完全不是你想要的代码——比如你想要一个书签功能，它写了一个完美的点赞功能，测试全绿。CI/CD 无法区分"正确但不想要"和"正确且想要"——这个判断只能在意图层（Spec）完成。

**Q3（定位型）**：你自己当前最薄弱的 Harness 层是哪个？如果要补强它，最务实的第一个动作是什么？

> **参考答案**：结合之前的讨论，最薄弱的可能是 Layer 4（如果项目没有完善的 CI/CD）或者 Layer 2（Spec 的格式规范性）。如果 Layer 4 是短板，最务实的第一个动作不是搭 CI/CD 管线，而是在本地实现一个轻量验证脚本——每次 AI 生成代码后自动跑一遍 lint + 测试。如果 Layer 2 是短板，最务实的第一个动作是在下一个功能开发时，试用 spec-kit 的 `/speckit.specify` 命令，体验一次结构化 Spec 的生成过程。
