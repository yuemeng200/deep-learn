# 第5章：Spec 的质量决定一切——什么是好的 Spec？

> 第4章比较了三种范式，得出的结论是"在不同阶段切换不同模式"。但无论选哪种模式，SDD 的成败都取决于一个变量：**Spec 本身的质量**。一个模糊的 Spec 生成的代码，不会比 Vibe Coding 好。本章以 spec-kit 的 spec-template 为解剖对象，拆解好 Spec 和坏 Spec 的差异。

---

## 5.1 Spec 的核心矛盾：模糊性 vs 精确性

写 Spec 面临一个天然矛盾：

- **太模糊**：AI 用"合理补全"填补空白，结果偏离意图（又回到了 Vibe Coding 的问题）
- **太精确**：Spec 变成了伪代码，失去了"技术无关"的特质，也失去了换技术栈重新生成的价值

好的 Spec 不是"尽可能详细"，而是**在关键决策点上精确，在实现细节上模糊**。

---

## 5.2 以 spec-kit 模板为骨架：六个关键层次

回顾第3章的 spec-template，它有六个层次。每一层都有常见的好坏之分：

### 层次一：User Stories（用户故事）

**坏写法**：
> "用户可以管理书签"

一个故事包含了太多行为（添加、删除、查看、排序）。无法独立开发、独立测试。

**好写法**：
> "用户可以在文章页面收藏/取消收藏一篇文章（P1）"
> "用户可以在专属页面查看所有收藏的文章（P2）"

拆到每个故事都是一个**可独立交付的 MVP 切片**。P1 做完了就能用，P2 是增强。

**判断标准**：如果一个 User Story 去掉后，其他 Story 是否仍然可测试？如果不是，说明拆得不够。

---

### 层次二：Acceptance Scenarios（验收场景）

**坏写法**：
> "点击书签后应该正常工作"
> "收藏功能要稳定可靠"

这是愿望，不是验收条件。"正常工作"怎么定义？"稳定可靠"怎么测量？

**好写法**：
> **Given** 已登录用户在某篇文章页面，**When** 点击书签图标（未收藏状态），**Then** 图标变为已收藏样式，文章被加入收藏列表

三个要素缺一不可：
- **Given**：前置条件（谁、在什么状态）
- **When**：具体动作（不是"使用功能"，而是"点击图标"）
- **Then**：可观察的结果（不是"正常工作"，而是"图标变了+数据加了"）

**为什么这个格式不可妥协**：因为它是整个工作流中**唯一的人类→AI 的行为契约**。模糊的验收场景会让 Plan 层和 Tasks 层的 AI 生成模糊的测试。精确的验收场景会像锚点一样，把后续每一层都固定住。

---

### 层次三：Functional Requirements（功能需求）

**坏写法**：
> "系统应该支持书签功能"
> "要有好的用户体验"

FR-001 里的"系统 MUST..."不是许愿，是**可验证的断言**。

**好写法**：
> "FR-001: 系统 MUST 允许已认证用户收藏任意文章"
> "FR-002: 系统 MUST 允许已认证用户取消收藏"

每个 FR 都是**一个测试的前提**。如果某个 FR 无法被一个测试验证，说明它要么太模糊，要么不应该出现在 FR 里（应该在 Assumptions 或 Success Criteria 里）。

---

### 层次四：Edge Cases（边界情况）

**坏写法**：
> "要处理各种异常情况"

**好写法**：
> "用户在两个标签页同时打开同一篇文章，一个标签页取消收藏后，另一个标签页的状态如何？"
> "文章被删除后，对应的书签记录如何处理？"

Edge Cases 不需要给出答案（那是 Plan 层的事），但需要**提出问题**。一个 Spec 的质量，很大程度上取决于它提出了多少"没想到"的边界情况。这是人类思维的核心价值所在——AI 很难主动提出它不知道的边界情况。

---

### 层次五：Success Criteria（成功指标）

**坏写法**：
> "功能上线后用户满意"

**好写法**：
> "SC-001: 书签切换操作响应时间 < 200ms"
> "SC-002: /bookmarks 页面在 100 条收藏内加载时间 < 1s"

成功指标必须是**可量化的**。它决定了 Plan 层的架构决策——比如 SC-001 的 < 200ms 要求，直接导致了 Plan 层选择"乐观更新"而不是"等服务器确认"。

---

### 层次六：Assumptions（边界假设）

这层经常被忽视，但它定义了 Spec 的**适用范围**。

**坏写法**：省略不写。

**好写法**：
> "用户认证系统已存在"
> "文章系统已存在"
> "移动端响应式在本功能范围内"

Assumptions 的价值是**显式声明"这个 Spec 不负责什么"**。如果没有它，AI 会在 Plan 层试图一并实现认证系统和文章系统——范围蔓延。

---

## 5.3 好/坏 Spec 的完整对比

以同一个功能为例：

**❌ 坏 Spec（片段）**：

用户可以收藏文章，也可以取消收藏。收藏的文章可以在收藏页面看到。要做得好看，体验流畅。注意异常处理。

问题：没有故事拆分、没有验收条件、没有边界定义、没有成功指标。"好看"和"流畅"无法验证。

**✅ 好 Spec（片段）**：

US1 (P1): 用户可在文章页收藏/取消收藏
  Given 已登录+未收藏状态，When 点击书签，Then 图标变已收藏+数据持久化
  Given 已登录+已收藏状态，When 点击书签，Then 图标恢复+数据删除
  Given 未登录，When 点击书签，Then 跳转登录页

US2 (P2): 用户可在专属页查看所有收藏
  Given 3篇收藏，When 访问 /bookmarks，Then 显示3篇（标题+摘要+日期）
  Given 0篇收藏，When 访问 /bookmarks，Then 显示空状态提示

Edge: 多标签页同步、文章删除后的书签处理
FR-001~005: 每条可验证
SC-001: 切换 < 200ms, SC-002: 列表 < 1s
Assumptions: 认证和文章系统已存在

**质量差异的本质**：坏 Spec 把思考的负担推给了 AI（让它猜）；好 Spec 把思考的负担留给了人类（让它执行）。

---

## 5.4 两类常见 Spec 反模式

### 反模式一：过度约束

```markdown
FR-001: 系统 MUST 使用 React 的 useState 管理书签状态
FR-002: 系统 MUST 使用 axios 发送 POST 请求到 /api/bookmarks
FR-003: 系统 MUST 使用 CSS Grid 布局收藏列表
```

这不是 Spec，是**用自然语言写的伪代码**。它违反了 Spec 的"技术无关"原则，把 Plan 层的决策提前到了 Spec 层。后果：换技术栈时 Spec 要重写，失去了"Spec 是稳定真相"的核心价值。

**检验方法**：如果 Spec 里出现了任何框架名、库名、技术术语，说明越界了。

### 反模式二：欠约束

```markdown
US1: 用户可以管理书签
Edge Cases: 需要处理各种异常
SC-001: 用户体验要好
```

这不是 Spec，是**产品经理的白板讨论**。没有可验证的验收条件，AI 会用"合理补全"填满空白——本质上退化成了 Vibe Coding，只是多走了一遍流程。

**检验方法**：如果 Acceptance Scenarios 不能直接转化为测试用例，说明约束不够。

---

## 5.5 一个实用判断：Spec 是否"够好了"

不需要完美。一个实用的判断标准——**三问检验**：

1. **可转化性**：每个 Acceptance Scenario 能否直接写成一个测试？（如果不能，太模糊）
2. **可替换性**：如果换一个完全不同的技术栈，这份 Spec 是否仍然成立？（如果不能，过度约束）
3. **可边界性**：Edge Cases 和 Assumptions 是否声明了"这个 Spec 不负责什么"？（如果没有，范围蔓延风险）

三个问题都通过，Spec 就可以进入 Plan 阶段了。

## 章末思考题

**Q1（诊断型）**：以下 Spec 片段违反了什么原则？"用户点击收藏按钮后，系统调用 fetch('/api/bookmarks', { method: 'POST', body: JSON.stringify({ articleId }) })，返回 200 后更新页面状态。"

> **参考答案**：违反了"技术无关"原则——Spec 层不应该包含具体的 API 调用细节（fetch、POST、JSON.stringify）。这些是 Plan 层的技术决策。正确的 Spec 写法是："Given 已登录用户在文章页，When 点击收藏，Then 文章被加入收藏列表且页面反映新状态。"具体怎么调 API、用什么库，留给 Plan 层决定。这样如果将来从 REST 切换到 GraphQL，Spec 不需要改。

**Q2（权衡型）**：一个团队写 Spec 花了 3 天，Plan 生成了 1 天，Tasks 生成了半天，实现 2 天。总共 6.5 天。如果直接 Vibe Coding 同样的功能，可能 3 天就搞定了（包含修正时间）。SDD 的额外 3.5 天成本在什么条件下是值得的？

> **参考答案**：当且仅当以下条件成立时值得：① 需求会变更（如果一锤定音，SDD 的文档投资没有回报）；② 多人参与（Spec 和 Plan 的 review 成本被多人复用分摊）；③ 功能有长期维护期（6个月后 Spec 的追溯价值才能体现）。如果这是一次性的、小范围的、不会变的功能，3.5 天的额外成本确实不划算。这也是为什么第4章说"按功能规模分级"——不是所有功能都值得走完整 SDD。

**Q3（实践型）**：回顾你在第1章讨论中描述的"澄清文档"，用三问检验（可转化性/可替换性/可边界性）评估一下，它离好的 Spec 还差多远？

> **参考答案**：大概率的情况是——可替换性通过（澄清文档通常不涉及技术细节）、可边界性部分通过（可能有范围说明但不够显式）、可转化性不通过（验收条件是描述性的而非 Given/When/Then）。差距主要在最后一项：把描述性的"验证方式"改写成可执行的 Given/When/Then 格式。这不是本质差距，是格式差距——补充的成本很低，但收益很高（直接解锁 AI 自动生成测试的能力）。
