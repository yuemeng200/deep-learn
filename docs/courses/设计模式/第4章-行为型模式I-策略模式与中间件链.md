# 第4章：行为型模式 I——策略模式与中间件链

## 回扣本质

前三章我们建立了项目的骨架和创建/结构关系。本章进入行为型模式——**对象之间如何协作完成一件事**。策略模式和中间件链解决的是同一个根本问题：**同一个动作有多种做法，怎么让做法可以随时替换，而不改调用方代码**。这正是"低成本修改和扩展"在运行时行为层面的直接体现。

---

## 一、策略模式：把"怎么做"变成可插拔的零件

### 问题场景

LinkFlow 要记录短链跳转统计。但产品经理说了："初期先同步写数据库就行，后面流量大了要换成异步队列。"

如果不用策略模式：

```go
func (s *LinkService) Redirect(code string) (*domain.Link, error) {
    link, err := s.store.FindByCode(code)
    if err != nil {
        return nil, err
    }

    // 统计逻辑——以后要换成异步队列怎么办？
    if s.asyncMode {
        s.queue.Push(ClickEvent{Code: code, Time: time.Now()})
    } else {
        s.store.IncrClick(code)
    }

    return link, nil
}
```

每加一种统计方式，就多一个 if 分支。核心业务逻辑被策略选择污染了。

### 心智模型

策略模式的核心：**定义一族算法，把每种算法封装成独立对象，让它们可以互相替换**。调用方只知道"有一个策略能处理统计"，不知道具体是同步还是异步。

```
┌──────────────┐     调用     ┌────────────────────┐
│ LinkService  │─────────────▶│ ClickRecorder 接口  │
└──────────────┘              └─────────┬──────────┘
                                        │
                    ┌───────────────────┬┴───────────────────┐
                    │                   │                     │
          ┌─────────▼──┐    ┌──────────▼───┐    ┌──────────▼────┐
          │ SyncRecorder│    │ AsyncRecorder │    │ NoopRecorder  │
          │ (直接写库)  │    │ (推入队列)    │    │ (测试用空实现) │
          └────────────┘    └──────────────┘    └───────────────┘
```

### 实现

```go
package stats

import (
    "linkflow/domain"
    "time"
)

// ClickEvent 是一次点击事件
type ClickEvent struct {
    Code      string
    Timestamp time.Time
    IP        string
    UserAgent string
}

// Recorder 是策略接口——怎么记录点击
type Recorder interface {
    Record(event ClickEvent) error
}
```

#### 策略一：同步写库

```go
package stats

import "linkflow/store"

type SyncRecorder struct {
    store store.Store
}

func NewSyncRecorder(s store.Store) *SyncRecorder {
    return &SyncRecorder{store: s}
}

func (r *SyncRecorder) Record(event ClickEvent) error {
    return r.store.IncrClick(event.Code)
}
```

#### 策略二：异步队列

```go
package stats

import (
    "encoding/json"
    "log"
)

type AsyncRecorder struct {
    ch chan ClickEvent
}

func NewAsyncRecorder(bufferSize int) *AsyncRecorder {
    r := &AsyncRecorder{
        ch: make(chan ClickEvent, bufferSize),
    }
    go r.consume()
    return r
}

func (r *AsyncRecorder) Record(event ClickEvent) error {
    select {
    case r.ch <- event:
        return nil
    default:
        log.Println("click buffer full, dropping event")
        return nil
    }
}

func (r *AsyncRecorder) consume() {
    for event := range r.ch {
        data, _ := json.Marshal(event)
        log.Printf("async process: %s", data)
        // 实际项目：写入 Kafka / Redis Stream / 批量入库
    }
}
```

#### 策略三：空实现（测试用）

```go
package stats

type NoopRecorder struct{}

func (r *NoopRecorder) Record(event ClickEvent) error {
    return nil
}
```

### 在 LinkService 中使用

```go
type LinkService struct {
    store    store.Store
    recorder stats.Recorder  // 策略接口
    // ...
}

func WithRecorder(r stats.Recorder) Option {
    return func(s *LinkService) {
        s.recorder = r
    }
}

func (s *LinkService) Redirect(code string, ip, ua string) (*domain.Link, error) {
    link, err := s.store.FindByCode(code)
    if err != nil {
        return nil, err
    }

    // 策略调用——不管背后是同步还是异步
    _ = s.recorder.Record(stats.ClickEvent{
        Code:      code,
        Timestamp: time.Now(),
        IP:        ip,
        UserAgent: ua,
    })

    return link, nil
}
```

### 组装时选择策略

```go
// main.go
var recorder stats.Recorder
if cfg.StatsMode == "async" {
    recorder = stats.NewAsyncRecorder(10000)
} else {
    recorder = stats.NewSyncRecorder(s)
}

svc := service.NewLinkService(s,
    service.WithRecorder(recorder),
)
```

策略的选择在 main.go（组装层），业务代码完全不知道。

## 二、中间件链（Chain of Responsibility）

### 问题场景

HTTP 请求进来后，你需要依次做：记录日志 → 鉴权 → 限流 → 真正的业务处理。这些横切关注点如果写在 handler 里：

```go
func (h *LinkHandler) Create(w http.ResponseWriter, r *http.Request) {
    // 日志
    log.Printf("%s %s", r.Method, r.URL.Path)
    // 鉴权
    token := r.Header.Get("Authorization")
    if !isValid(token) {
        http.Error(w, "unauthorized", 401)
        return
    }
    // 限流
    if !h.limiter.Allow() {
        http.Error(w, "rate limited", 429)
        return
    }
    // 真正的业务逻辑...终于到了
}
```

每个 handler 都要重复这些代码。中间件链解决这个问题。

### 心智模型

中间件链是**责任链模式**的 HTTP 变体。每个中间件像洋葱的一层：请求从外到内穿过每一层，响应从内到外穿出来。每一层可以决定"放行"或"拦截"。

```
请求 ──▶ [日志] ──▶ [鉴权] ──▶ [限流] ──▶ [Handler]
响应 ◀── [日志] ◀── [鉴权] ◀── [限流] ◀── [Handler]
```

### Go 标准库的中间件签名

```go
// Middleware 是一个函数：接收一个 handler，返回一个增强过的 handler
type Middleware func(http.Handler) http.Handler
```

这个签名是 Go HTTP 生态的事实标准。

### 实现三个中间件

#### 日志中间件

```go
package middleware

import (
    "log"
    "net/http"
    "time"
)

func Logging(next http.Handler) http.Handler {
    return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        start := time.Now()
        next.ServeHTTP(w, r)  // 调用下一层
        log.Printf("%s %s %v", r.Method, r.URL.Path, time.Since(start))
    })
}
```

#### 鉴权中间件

```go
package middleware

import "net/http"

func Auth(validToken string) Middleware {
    return func(next http.Handler) http.Handler {
        return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
            token := r.Header.Get("Authorization")
            if token != "Bearer "+validToken {
                http.Error(w, "unauthorized", http.StatusUnauthorized)
                return  // 拦截，不调用 next
            }
            next.ServeHTTP(w, r)  // 放行
        })
    }
}
```

#### 限流中间件

```go
package middleware

import (
    "net/http"
    "sync"
    "time"
)

func RateLimit(maxPerSecond int) Middleware {
    var (
        mu      sync.Mutex
        tokens  = maxPerSecond
        lastRef = time.Now()
    )

    return func(next http.Handler) http.Handler {
        return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
            mu.Lock()
            now := time.Now()
            elapsed := now.Sub(lastRef)
            // 简单令牌桶：每秒补充
            if elapsed >= time.Second {
                tokens = maxPerSecond
                lastRef = now
            }
            if tokens <= 0 {
                mu.Unlock()
                http.Error(w, "rate limited", http.StatusTooManyRequests)
                return
            }
            tokens--
            mu.Unlock()

            next.ServeHTTP(w, r)
        })
    }
}
```

### 链式组合

```go
package middleware

import "net/http"

type Middleware func(http.Handler) http.Handler

// Chain 把多个中间件组合成一个
func Chain(middlewares ...Middleware) Middleware {
    return func(final http.Handler) http.Handler {
        // 从后往前包裹，这样执行时是从前往后
        for i := len(middlewares) - 1; i >= 0; i-- {
            final = middlewares[i](final)
        }
        return final
    }
}
```

### 在 LinkFlow 中使用

```go
// main.go
func main() {
    cfg := config.Get()
    // ... 创建 svc, h ...

    // 组合中间件链——顺序决定执行顺序
    chain := middleware.Chain(
        middleware.Logging,
        middleware.Auth(cfg.AuthToken),
        middleware.RateLimit(100),
    )

    mux := http.NewServeMux()
    mux.Handle("/links", chain(http.HandlerFunc(h.Create)))

    // 跳转接口不需要鉴权，用不同的链
    publicChain := middleware.Chain(
        middleware.Logging,
        middleware.RateLimit(1000),
    )
    mux.Handle("/", publicChain(http.HandlerFunc(h.Redirect)))

    log.Fatal(http.ListenAndServe(":"+cfg.Port, mux))
}
```

**关键洞察**：不同路由可以用不同的中间件组合。中间件是独立的零件，`Chain` 是组装器。增加新的横切关注点？写一个函数，插入链中，不改任何现有代码。

## 三、策略 vs 中间件：它们的关系

| 维度 | 策略模式 | 中间件链 |
|------|---------|---------|
| 解决的问题 | "做同一件事有多种算法" | "一件事要经过多个步骤处理" |
| 运行时有几个 | 选一个 | 全部按顺序执行 |
| 典型场景 | 统计方式、短码生成算法 | HTTP 请求处理管道 |
| 共同点 | 都通过接口/函数签名解耦，都支持运行时切换 |

## 章末思考题

**Q1：** 如果你需要一个"先尝试异步，队列满了回退到同步"的混合策略，你会怎么实现？它还是策略模式吗？

> **参考答案**：创建一个 `FallbackRecorder`，它组合了 `AsyncRecorder` 和 `SyncRecorder`。在 `Record` 方法中先尝试异步，如果返回特定错误（队列满）则调用同步。它仍然满足 `Recorder` 接口，对 `LinkService` 来说就是"又一个策略"——这是策略模式与**装饰器**模式的结合。一个策略的内部可以组合其他策略，只要对外暴露的接口不变。

**Q2：** 中间件的执行顺序很重要。如果把限流放在日志前面，会有什么问题？如果把鉴权放在限流后面呢？

> **参考答案**：限流在日志前面：被限流的请求不会留下日志，你无法知道有多少请求被拒绝了，排查问题时丢失关键信息。鉴权在限流后面：未认证的请求会消耗限流额度，攻击者可以用大量无效请求把正常用户的额度耗尽（一种 DoS 攻击方式）。最佳顺序通常是：日志（观测一切）→ 鉴权（拒绝无效身份）→ 限流（保护下游资源）。

**Q3（挑战）：** Go 的 `http.Handler` 中间件模式有一个隐含限制：中间件之间传递数据只能通过 `context.Context`。这会带来什么问题？你见过或能想到什么替代方案？

> **参考答案**：问题：① context 的值是 `interface{}`，没有类型安全，取值时需要类型断言；② key 冲突风险——不同中间件可能用相同的 key；③ 调试困难——你看不到 context 里塞了什么。替代方案：① 用自定义的 typed key（`type ctxKey struct{}`）避免冲突；② 封装 helper 函数（`func GetUserFromCtx(ctx) *User`）提供类型安全的存取；③ 框架级方案如 gin 的 `c.Set/c.Get` 用一个 map 显式传递；④ 更激进的：不用 context，把中间件上下文放到一个显式传递的 struct 里（但这就不兼容标准库了）。Go 选择了最简单的方案，代价是类型安全。
