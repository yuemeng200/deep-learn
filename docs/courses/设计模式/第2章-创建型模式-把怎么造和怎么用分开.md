# 第2章：创建型模式——把"怎么造"和"怎么用"分开

## 回扣本质

上一章我们建立了"接口即契约、组合替代继承"的认知，搭建了 LinkFlow 骨架。本章进入设计模式的第一个分类——**创建型**，解决的核心问题是：**对象怎么创建的，不应该让使用方操心**。这正是"创建 → 组装 → 运转"三步中的第一步——把"变化"封装起来，这里变化的是"创建过程"。

---

## 一、问题场景：LinkFlow 的初始化越来越复杂了

随着项目演进，`main.go` 里的组装代码开始膨胀：

```go
// 这些配置从哪来？谁来保证只有一份？
cfg := loadConfig("config.yaml")

// 数据库连接——应该全局唯一
db, _ := sql.Open("mysql", cfg.DSN)

// 存储层——根据配置选内存还是 MySQL？
var s store.Store
if cfg.StoreType == "memory" {
    s = store.NewMemoryStore()
} else if cfg.StoreType == "mysql" {
    s = store.NewMySQLStore(db)
}

// 服务层——参数越来越多
svc := service.NewLinkService(s, cfg.DefaultExpiry, cfg.CodeLength, logger)
```

三个痛点浮现了：
1. **全局唯一资源**（Config、DB 连接）怎么保证只创建一次？
2. **根据条件创建不同实现**的 if-else 散落在 main 里，加新存储类型就要改 main
3. **构造参数爆炸**，`NewLinkService` 的参数列表越来越长

三个创建型模式分别解决这三个问题。

---

## 二、Singleton：保证全局唯一

### 心智模型

Singleton 的本质不是"全局变量"，而是**对"有且只有一个"这个约束的代码化表达**。数据库连接池、配置对象、日志器——这些东西创建多份不仅浪费，还可能引发状态不一致。

### Go 的地道做法：`sync.Once`

Java 里的 Singleton 需要 double-checked locking、volatile 等花活。Go 一行搞定：

```go
package config

import (
    "os"
    "sync"
    "gopkg.in/yaml.v3"
)

type Config struct {
    Port         string `yaml:"port"`
    StoreType    string `yaml:"store_type"`
    DSN          string `yaml:"dsn"`
    DefaultExpiry int   `yaml:"default_expiry"`
    CodeLength   int    `yaml:"code_length"`
}

var (
    instance *Config
    once     sync.Once
)

func Get() *Config {
    once.Do(func() {
        instance = &Config{}
        data, err := os.ReadFile("config.yaml")
        if err != nil {
            panic("failed to read config: " + err.Error())
        }
        if err := yaml.Unmarshal(data, instance); err != nil {
            panic("failed to parse config: " + err.Error())
        }
    })
    return instance
}
```

**关键点**：
- `sync.Once` 保证 `Do` 里的函数只执行一次，即使多个 goroutine 并发调用 `Get()`
- 不需要 `init()` 函数——延迟到第一次使用时才初始化（lazy initialization）
- 整个包对外只暴露 `Get()` 函数，没有 `New`，语义上就在告诉你"这个东西只有一份"

### 在 LinkFlow 中的应用

```go
// main.go
func main() {
    cfg := config.Get()  // 全局唯一配置
    // ...后续使用 cfg.Port, cfg.StoreType 等
}
```

### 什么时候不该用 Singleton？

当你发现测试时想替换它，Singleton 就成了障碍。所以 Go 社区的共识是：**Singleton 管资源，但通过参数传递给使用方**。不要在业务代码里直接调 `config.Get()`，而是在 `main.go` 调一次，然后作为参数注入。

## 三、Factory：根据条件创建不同实现

### 心智模型

Factory 的核心是：**使用方说"我要什么"，Factory 负责"怎么造"**。使用方不需要知道有哪些具体类型，不需要导入它们的包。

### 简单工厂：一个函数搞定

```go
package store

import "fmt"

// NewStore 是工厂函数——调用者只需传配置，不需要知道具体类型
func NewStore(storeType string, dsn string) (Store, error) {
    switch storeType {
    case "memory":
        return NewMemoryStore(), nil
    case "mysql":
        return NewMySQLStore(dsn)
    default:
        return nil, fmt.Errorf("unknown store type: %s", storeType)
    }
}
```

### 在 LinkFlow 中的应用

```go
// main.go —— 清爽了
func main() {
    cfg := config.Get()

    s, err := store.NewStore(cfg.StoreType, cfg.DSN)
    if err != nil {
        log.Fatal(err)
    }

    svc := service.NewLinkService(s)
    // ...
}
```

原来散落在 main 里的 if-else 被封装进了 `store` 包。**新增一种存储后端？只需要加一个 case，main.go 不用动。**

### 注册式工厂（进阶）

如果你连 switch-case 都不想改，可以用注册模式：

```go
package store

var registry = map[string]func(dsn string) (Store, error){}

// Register 让每个实现自己注册自己
func Register(name string, factory func(dsn string) (Store, error)) {
    registry[name] = factory
}

func NewStore(storeType string, dsn string) (Store, error) {
    factory, ok := registry[storeType]
    if !ok {
        return nil, fmt.Errorf("unknown store type: %s", storeType)
    }
    return factory(dsn)
}
```

```go
// store/mysql.go
package store

func init() {
    Register("mysql", func(dsn string) (Store, error) {
        return NewMySQLStore(dsn)
    })
}
```

这样新增存储实现，只需在新文件的 `init()` 里注册，**工厂函数本身永远不用改**。这就是"对扩展开放，对修改关闭"的开闭原则。

## 四、Functional Options：Go 最地道的构造方式

### 问题：参数爆炸

```go
// 第一版
func NewLinkService(store store.Store) *LinkService

// 需求增长...
func NewLinkService(store store.Store, expiry int, codeLen int, logger *log.Logger) *LinkService

// 继续增长...加 10 个参数？
```

Java 用 Builder 模式解决。Go 有更优雅的方案。

### 心智模型

Functional Options 的核心思想：**用一组"修改函数"来配置对象，每个函数只管一件事**。

```go
package service

import "log"

// Option 是一个"修改 LinkService 配置"的函数
type Option func(*LinkService)

// 每个 With* 函数返回一个 Option
func WithExpiry(seconds int) Option {
    return func(s *LinkService) {
        s.defaultExpiry = seconds
    }
}

func WithCodeLength(length int) Option {
    return func(s *LinkService) {
        s.codeLength = length
    }
}

func WithLogger(logger *log.Logger) Option {
    return func(s *LinkService) {
        s.logger = logger
    }
}

type LinkService struct {
    store         store.Store
    defaultExpiry int
    codeLength    int
    logger        *log.Logger
}

func NewLinkService(s store.Store, opts ...Option) *LinkService {
    // 先设默认值
    svc := &LinkService{
        store:         s,
        defaultExpiry: 3600,
        codeLength:    6,
        logger:        log.Default(),
    }
    // 再用 Options 覆盖
    for _, opt := range opts {
        opt(svc)
    }
    return svc
}
```

### 在 LinkFlow 中的应用

```go
// main.go
func main() {
    cfg := config.Get()
    s, _ := store.NewStore(cfg.StoreType, cfg.DSN)

    // 清晰、可读、可选、可扩展
    svc := service.NewLinkService(s,
        service.WithExpiry(cfg.DefaultExpiry),
        service.WithCodeLength(cfg.CodeLength),
    )

    h := handler.NewLinkHandler(svc)
    // ...
}
```

### 为什么比 Config Struct 更好？

你可能会问："传一个 Config 结构体不也行吗？"

| 对比 | Config Struct | Functional Options |
|------|--------------|-------------------|
| 零值问题 | `Config{Expiry: 0}` 是"要设0"还是"忘了设"？ | 默认值在构造函数里，Option 只覆盖你显式传的 |
| 可扩展性 | 加字段要改 Config 定义 | 加一个 `WithXxx` 函数，完全向后兼容 |
| 文档性 | 所有字段平铺，哪些必填哪些可选不明显 | 必填参数是普通参数，可选的才用 Option |

这就是为什么 Go 标准库和几乎所有主流库（gRPC、zap、cobra）都采用这个模式。

## 五、本章完整的 LinkFlow 初始化流程

把三个模式串起来：

```go
package main

import (
    "log"
    "net/http"
    "linkflow/config"
    "linkflow/handler"
    "linkflow/service"
    "linkflow/store"
)

func main() {
    // 1. Singleton：全局唯一配置
    cfg := config.Get()

    // 2. Factory：根据配置创建存储实现
    s, err := store.NewStore(cfg.StoreType, cfg.DSN)
    if err != nil {
        log.Fatal(err)
    }

    // 3. Functional Options：灵活构造服务
    svc := service.NewLinkService(s,
        service.WithExpiry(cfg.DefaultExpiry),
        service.WithCodeLength(cfg.CodeLength),
    )

    h := handler.NewLinkHandler(svc)

    mux := http.NewServeMux()
    mux.HandleFunc("/links", h.Create)
    mux.HandleFunc("/", h.Redirect)

    log.Printf("LinkFlow running on :%s\n", cfg.Port)
    log.Fatal(http.ListenAndServe(":"+cfg.Port, mux))
}
```

对比第1章末尾的 main.go，结构更清晰，职责更分明，扩展更容易。

## 章末思考题

**Q1：** `sync.Once` 和 `init()` 函数都能实现"只执行一次"。它们的核心区别是什么？在什么场景下你会选择 `sync.Once` 而不是 `init()`？

> **参考答案**：`init()` 在包被导入时自动执行，无法控制时机，也无法传参或处理错误（只能 panic）。`sync.Once` 是延迟执行——直到第一次调用时才触发，你可以选择在合适的时机初始化，还能优雅处理错误。当初始化依赖运行时条件（如配置文件路径、环境变量、命令行参数）时，`sync.Once` 远优于 `init()`。另外 `init()` 会让包之间产生隐式的依赖顺序，调试困难。

**Q2：** 现在产品经理说："要支持 Redis 存储。"用了工厂模式后，你需要做哪些步骤？哪些现有文件完全不用动？

> **参考答案**：步骤：① 新建 `store/redis.go`，实现 `Store` 接口；② 在注册式工厂方案中，在 `init()` 里调用 `Register("redis", ...)`；③ 配置文件里 `store_type` 改为 `"redis"`。**完全不用动的文件**：`main.go`、`service/link.go`、`handler/link.go`、`store/store.go`（接口定义和工厂函数）。这就是工厂 + 接口带来的威力——新增实现是"添加代码"而不是"修改代码"。

**Q3（挑战）：** Functional Options 模式中，如果某个 Option 依赖另一个 Option 的结果（比如 `WithCache` 需要知道 `WithExpiry` 设的值），你会怎么处理？这暴露了 Functional Options 的什么局限性？

> **参考答案**：Functional Options 的执行顺序就是传入顺序，后面的 Option 可以读取前面 Option 已经设置的字段值。但这引入了**顺序依赖**——调用者必须知道"先传 WithExpiry 再传 WithCache"，否则 Cache 读到的是默认值。这暴露了 Functional Options 的局限：它适合**互相独立的配置项**，一旦 Option 之间有依赖关系，要么在文档里明确说明顺序，要么改用两阶段构造（先 New 出来，再调 Build），要么让有依赖的 Option 内部自己去读最终值（在所有 Option 执行完之后再做一次 resolve）。
