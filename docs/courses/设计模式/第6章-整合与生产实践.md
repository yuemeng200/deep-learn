# 第6章：整合与生产实践

## 回扣本质

前五章我们逐步引入了接口思维、创建型模式、结构型模式和行为型模式。本章要做两件事：**把所有模块串成一个完整的生产级服务**，并补入两个生产环境必不可少的模式——Circuit Breaker（熔断器）和 Graceful Shutdown（优雅退出）。这两个模式的共同点是：**让系统在异常条件下依然可控**，这正是"低成本修改和扩展"的终极形态——不仅正常路径可扩展，异常路径也有设计。

## 二、Circuit Breaker：下游挂了不拖垮自己

### 问题场景

WebhookSender 要向外部服务发 HTTP 请求。如果外部服务挂了：
- 每次请求都要等超时（5秒）才能返回
- 大量 goroutine 卡在等待中
- 最终 LinkFlow 自己也被拖垮

### 心智模型

熔断器像家里的电闸——电流异常时自动切断，避免烧毁电路。过一段时间后试探性地合上，如果恢复了就正常通电。

三个状态：

```
            连续失败达到阈值              超时后试探
┌─────────┐──────────────────▶┌────────┐──────────────▶┌───────────┐
│  Closed │                   │  Open  │               │ Half-Open │
│ (正常)  │◀──────────────────│ (熔断) │◀──────────────│  (试探)   │
└─────────┘   试探成功，恢复   └────────┘   试探失败     └───────────┘
```

- **Closed**：正常状态，请求正常通过，记录失败次数
- **Open**：熔断状态，直接拒绝请求，不调用下游（快速失败）
- **Half-Open**：试探状态，允许少量请求通过，成功则恢复 Closed，失败则回到 Open

### 实现

```go
package breaker

import (
    "errors"
    "sync"
    "time"
)

var ErrCircuitOpen = errors.New("circuit breaker is open")

type State int

const (
    Closed   State = iota
    Open
    HalfOpen
)

type CircuitBreaker struct {
    mu             sync.Mutex
    state          State
    failureCount   int
    successCount   int
    maxFailures    int       // 连续失败多少次触发熔断
    timeout        time.Duration  // Open 状态持续多久后尝试 Half-Open
    lastFailure    time.Time
    halfOpenMax    int       // Half-Open 时允许几个请求通过
}

func New(maxFailures int, timeout time.Duration) *CircuitBreaker {
    return &CircuitBreaker{
        state:       Closed,
        maxFailures: maxFailures,
        timeout:     timeout,
        halfOpenMax: 1,
    }
}

// Execute 包裹一个可能失败的操作
func (cb *CircuitBreaker) Execute(fn func() error) error {
    cb.mu.Lock()

    switch cb.state {
    case Open:
        // 检查是否超时，可以进入 Half-Open
        if time.Since(cb.lastFailure) > cb.timeout {
            cb.state = HalfOpen
            cb.successCount = 0
            cb.mu.Unlock()
            return cb.doExecute(fn)
        }
        cb.mu.Unlock()
        return ErrCircuitOpen  // 快速失败

    case HalfOpen:
        cb.mu.Unlock()
        return cb.doExecute(fn)

    default: // Closed
        cb.mu.Unlock()
        return cb.doExecute(fn)
    }
}

func (cb *CircuitBreaker) doExecute(fn func() error) error {
    err := fn()

    cb.mu.Lock()
    defer cb.mu.Unlock()

    if err != nil {
        cb.failureCount++
        cb.lastFailure = time.Now()

        if cb.state == HalfOpen {
            cb.state = Open  // 试探失败，重新熔断
        } else if cb.failureCount >= cb.maxFailures {
            cb.state = Open  // 达到阈值，触发熔断
        }
        return err
    }

    // 成功
    if cb.state == HalfOpen {
        cb.successCount++
        if cb.successCount >= cb.halfOpenMax {
            cb.state = Closed  // 试探成功，恢复正常
            cb.failureCount = 0
        }
    } else {
        cb.failureCount = 0  // Closed 状态下成功一次就重置计数
    }
    return nil
}

// State 返回当前状态（用于监控）
func (cb *CircuitBreaker) GetState() State {
    cb.mu.Lock()
    defer cb.mu.Unlock()
    return cb.state
}
```

### 在 WebhookSender 中使用

```go
type WebhookSender struct {
    url     string
    client  *http.Client
    cb      *breaker.CircuitBreaker
}

func NewWebhookSender(url string) *WebhookSender {
    return &WebhookSender{
        url:    url,
        client: &http.Client{Timeout: 5 * time.Second},
        cb:     breaker.New(5, 30*time.Second), // 连续5次失败则熔断30秒
    }
}

func (w *WebhookSender) Handle(e event.Event) {
    err := w.cb.Execute(func() error {
        body, _ := json.Marshal(e)
        resp, err := w.client.Post(w.url, "application/json", bytes.NewReader(body))
        if err != nil {
            return err
        }
        resp.Body.Close()
        if resp.StatusCode >= 500 {
            return fmt.Errorf("webhook returned %d", resp.StatusCode)
        }
        return nil
    })

    if errors.Is(err, breaker.ErrCircuitOpen) {
        log.Println("webhook circuit open, skipping")
    } else if err != nil {
        log.Printf("webhook error: %v", err)
    }
}
```

**关键洞察**：CircuitBreaker 是一个通用的**装饰器**——它不关心被包裹的操作是什么（HTTP 调用、数据库查询、RPC），只关心"成功还是失败"。这让它可以复用在任何外部调用上。

## 三、Graceful Shutdown：优雅退出

### 问题场景

服务收到 kill 信号（部署新版本、K8s 滚动更新）时：
- 正在处理的请求会被直接中断——用户看到 502
- 异步事件处理器的 buffer 里还有未处理的事件——数据丢失
- 数据库连接没有正确关闭——连接泄漏

### 心智模型

优雅退出就是：**不再接收新请求，等现有工作做完，然后依次关闭资源**。像餐厅打烊——不再让新客人进门，但已经坐下的客人吃完再走。

### 实现

```go
package main

import (
    "context"
    "log"
    "net/http"
    "os"
    "os/signal"
    "syscall"
    "time"
)

func main() {
    cfg := config.Get()
    // ... 创建所有组件 ...

    server := &http.Server{
        Addr:    ":" + cfg.Port,
        Handler: mux,
    }

    // 在一个 goroutine 中启动服务器
    go func() {
        log.Printf("LinkFlow running on :%s", cfg.Port)
        if err := server.ListenAndServe(); err != http.ErrServerClosed {
            log.Fatalf("server error: %v", err)
        }
    }()

    // 等待终止信号
    quit := make(chan os.Signal, 1)
    signal.Notify(quit, syscall.SIGINT, syscall.SIGTERM)
    <-quit

    log.Println("shutting down...")

    // 给正在处理的请求最多 10 秒完成
    ctx, cancel := context.WithTimeout(context.Background(), 10*time.Second)
    defer cancel()

    // 1. 停止接收新请求，等待已有请求完成
    if err := server.Shutdown(ctx); err != nil {
        log.Printf("server shutdown error: %v", err)
    }

    // 2. 关闭事件总线（等待 buffer 中的事件处理完）
    bus.Shutdown()

    // 3. 关闭数据库连接
    if closer, ok := s.(interface{ Close() error }); ok {
        closer.Close()
    }

    log.Println("goodbye")
}
```

### 给 EventBus 加上 Shutdown 能力

```go
func (b *Bus) Shutdown() {
    // 如果有 worker pool，等待所有 worker 完成
    // 如果用了 buffer channel，drain 它
    b.mu.Lock()
    b.handlers = make(map[Type][]Handler) // 清空订阅，不再分发
    b.mu.Unlock()
}
```

### 给 AsyncRecorder 加上关闭能力

```go
func (r *AsyncRecorder) Close() {
    close(r.ch) // 关闭 channel，consume goroutine 会自然退出
}
```

### Closer 接口模式

多个组件都需要关闭，可以用接口统一管理：

```go
type Closer interface {
    Close() error
}

// 在 main 中收集所有需要关闭的组件
var closers []Closer

// 关闭时按相反顺序关闭（后创建的先关闭）
for i := len(closers) - 1; i >= 0; i-- {
    if err := closers[i].Close(); err != nil {
        log.Printf("close error: %v", err)
    }
}
```

## 四、最终版 main.go：完整组装

```go
package main

import (
    "context"
    "log"
    "net/http"
    "os"
    "os/signal"
    "syscall"
    "time"

    "linkflow/config"
    "linkflow/event"
    "linkflow/handler"
    "linkflow/handlers"
    "linkflow/middleware"
    "linkflow/service"
    "linkflow/store"
)

func main() {
    // ==================== 配置 ====================
    cfg := config.Get() // Singleton

    // ==================== 存储 ====================
    s, err := store.NewStore(cfg.StoreType, cfg.DSN) // Factory
    if err != nil {
        log.Fatal(err)
    }

    // ==================== 事件系统 ====================
    bus := event.NewBus() // Observer

    // 注册事件处理器
    bus.Subscribe(event.LinkClicked, handlers.LogHandler)
    bus.Subscribe(event.LinkCreated, handlers.LogHandler)

    if cfg.WebhookURL != "" {
        webhook := handlers.NewWebhookSender(cfg.WebhookURL) // 内含 Circuit Breaker
        bus.Subscribe(event.LinkClicked, webhook.Handle)
    }

    hotRank := handlers.NewHotRank()
    bus.Subscribe(event.LinkClicked, hotRank.Handle)

    // ==================== 业务服务 ====================
    svc := service.NewLinkService(s, // 依赖注入 + Functional Options
        service.WithEventBus(bus),
        service.WithExpiry(cfg.DefaultExpiry),
        service.WithCodeLength(cfg.CodeLength),
    )

    // ==================== HTTP 层 ====================
    h := handler.NewLinkHandler(svc)

    // 中间件链 (Chain of Responsibility)
    authChain := middleware.Chain(
        middleware.Logging,
        middleware.Auth(cfg.AuthToken),
        middleware.RateLimit(100),
    )
    publicChain := middleware.Chain(
        middleware.Logging,
        middleware.RateLimit(1000),
    )

    mux := http.NewServeMux()
    mux.Handle("/links", authChain(http.HandlerFunc(h.Create)))
    mux.Handle("/", publicChain(http.HandlerFunc(h.Redirect)))

    server := &http.Server{
        Addr:    ":" + cfg.Port,
        Handler: mux,
    }

    // ==================== 启动 ====================
    go func() {
        log.Printf("LinkFlow running on :%s", cfg.Port)
        if err := server.ListenAndServe(); err != http.ErrServerClosed {
            log.Fatalf("server error: %v", err)
        }
    }()

    // ==================== 优雅退出 ====================
    quit := make(chan os.Signal, 1)
    signal.Notify(quit, syscall.SIGINT, syscall.SIGTERM)
    <-quit

    log.Println("shutting down gracefully...")

    ctx, cancel := context.WithTimeout(context.Background(), 10*time.Second)
    defer cancel()

    server.Shutdown(ctx)
    bus.Shutdown()
    if closer, ok := s.(interface{ Close() error }); ok {
        closer.Close()
    }

    log.Println("goodbye")
}
```

## 五、回顾：每个模式解决了什么问题

| 模式 | 解决的问题 | 在 LinkFlow 中的体现 |
|------|-----------|-------------------|
| Singleton (sync.Once) | 全局唯一资源的创建 | Config |
| Factory | 根据配置创建不同实现 | Store 创建 |
| Functional Options | 构造参数灵活可扩展 | LinkService 初始化 |
| Repository + DI | 业务逻辑与存储解耦 | Store 接口 + 构造注入 |
| Strategy | 同一行为多种实现可切换 | 统计 Recorder |
| Chain of Responsibility | 请求经过多步可组合处理 | HTTP 中间件 |
| Observer / Event Bus | 一事件多响应解耦 | 点击后触发多个下游 |
| Circuit Breaker | 防止下游故障传播 | Webhook 外部调用 |
| Graceful Shutdown | 进程退出时有序清理 | 信号处理 + 超时控制 |

## 六、设计模式的使用原则

从 LinkFlow 的演进中提炼几条原则：

### 1. 模式是解决问题的，不是炫技的
只在遇到真实痛点时引入模式。第1章的版本没有 Factory、没有 EventBus，照样能跑。模式是**随着复杂度增长而引入的**，不是一开始就堆上去的。

### 2. 接口是 Go 模式的统一地基
几乎所有模式在 Go 中都通过接口实现：Strategy 是接口、Repository 是接口、Observer 的 Handler 是函数签名（隐式接口）。掌握接口思维 = 掌握了 Go 模式的 80%。

### 3. main.go 是组装车间
所有的"选择"（用哪个存储、用哪个策略、注册哪些事件处理器）都发生在 main.go。业务代码只面向接口编程，不做选择。这让测试、替换、扩展都变得简单。

### 4. 不要过度设计
如果一个组件只有一种实现且可预见的未来不会变——直接用具体类型就行，不需要抽接口。**测试需要 mock** 是引入接口最常见也最正当的理由。

## 章末思考题

**Q1：** 如果 LinkFlow 要部署多个实例（水平扩展），现在的架构中哪些组件会出问题？你会怎么改造？

> **参考答案**：有问题的组件：① `MemoryStore`——每个实例的数据不共享，用户在实例 A 创建的短链在实例 B 找不到；② `HotRank`——每个实例只统计自己收到的请求，排名不准；③ `AsyncRecorder` 的内存 buffer——实例重启就丢失。改造方案：① Store 换成共享存储（MySQL/Redis），这就是为什么我们用了 Factory——只改配置不改代码；② HotRank 改用 Redis ZSET 做共享排名；③ 异步统计用外部消息队列（Kafka/Redis Stream）。核心架构不需要大改——因为每个组件都面向接口，替换实现即可。

**Q2：** Circuit Breaker 的阈值（5次失败、30秒超时）怎么确定？设太敏感和设太迟钝各有什么后果？

> **参考答案**：太敏感（如 2 次失败就熔断）：网络偶尔抖一下就熔断，正常服务被误杀，可用性反而下降。太迟钝（如 100 次失败才熔断）：下游已经挂了还在不断重试，资源浪费、延迟堆积。确定方法：① 观察正常情况下的错误率基线，阈值设在基线之上；② 超时时间和下游的恢复时间匹配；③ 生产环境通常配合监控动态调整，而不是写死。Netflix Hystrix 的经验值：10秒内50%错误率触发熔断，5秒后试探。

**Q3（挑战）：** 回顾整个项目，如果让你从零重新设计，你会在哪些地方做不同的决定？有没有某个模式是"引入过早"或"可以更简单"的？

> **参考答案**：这是一个开放性问题，合理的反思包括：① EventBus 对于当前规模可能过早——如果只有 2-3 个下游处理器，直接在 Service 里调用也很清晰，等到 5 个以上再引入 Bus；② Functional Options 在只有 2-3 个配置时，一个简单的 Config struct 也够用；③ Circuit Breaker 如果 Webhook 不是核心功能，可以先用简单的超时 + 重试替代。**模式的价值和项目复杂度成正比**——本课程为了教学把它们全部引入了同一个项目，但实际工作中应该根据当前的复杂度阶段性引入。提前引入模式的成本是"代码比问题本身更复杂"，这比没有模式更糟糕。
