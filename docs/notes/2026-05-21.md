# 2026-05-21 · vercel-ai-sdk, streaming-ui, rsc, tool-calling, agent

## Q1：Vercel AI SDK 的核心定位和五大能力分别是什么？

AI SDK 是 AI 能力的前端/Node.js 胶水层，不是 Agent 框架。五大能力：

1. **统一 LLM 接口**：provider-agnostic API，`model` 参数换一行就能切换 OpenAI/Anthropic/Google
2. **流式 UI**：内置 Data Stream Protocol + `useChat` 状态管理，支持文本流和 RSC 组件流
3. **结构化输出**：`generateObject` + zod schema，LLM 输出直接得到类型安全的对象
4. **Tool calling**：定义工具 + `maxSteps` 自动循环，LLM 决定调用什么、SDK 执行并把结果喂回
5. **Agent 编排**：不提供框架，提供原语——多次 `generateText` 手动串联，灵活但无自动编排

适合做产品级 AI 功能集成（80% 的轻量场景），不适合复杂自主 Agent 研究。

## Q2：AI SDK 的前后端协作模式是怎样的？前端拿到的是什么格式？

实际架构是 `客户端 → 你的后端 → LLM Provider`。AI SDK 前后端都覆盖：后端用 `streamText` + `toDataStreamResponse()` 生成标准流式响应，前端用 `useChat({ api: '/api/chat' })` 消费。

前端拿到的是 AI SDK 自定义的 **Data Stream Protocol**，每行格式为 `类型前缀:JSON值`：`0` = 文本 chunk，`2` = tool call 开始，`9` = tool call 结果，`8` = 自定义业务数据，`e` = usage 元信息，`d` = 流结束。`useChat` 内部解析协议 → 拼接文本 → 更新 messages 状态 → 触发重渲染。

前后端必须配套用才顺畅——如果后端不是 Node.js/Next.js，只剩前端 `useChat` 消费自定义流接口，需要后端手动适配这个协议格式。

## Q3：AI SDK 的 streamUI 是什么能力？原理是什么？

streamUI 让 LLM **选择**展示哪个预制 UI 组件（不是让 AI 生成组件代码），然后借 RSC 流式推到前端。流程：用户发消息 → LLM 决定调用哪个工具并传参 → AI SDK 执行你预先写好的 `generate` 函数 → 函数 `yield` 骨架屏、`return` 最终组件 → RSC 协议推给客户端自动替换。

Generator 函数（`function*`）对应 RSC 流中的两次推送：第一次推送骨架屏 payload，第二次推送最终组件 payload。核心区别于传统方式：不再由前端判断意图决定渲染什么，而是**由模型决定展示什么 UI 组件**。

限制条件：必须用 Next.js + React Server Components（依赖 RSC 的流式传输能力），本质是 Server Action 返回可流式的 JSX。

## Q4：RSC（React Server Components）的工作原理是什么？和 SSR 有什么区别？

RSC 把"组件渲染"搬到服务端，用自定义流式协议把**序列化的组件树**（RSC Payload）推给客户端。传输的不是 HTML 也不是 JSON，而是 `["$","div",null,{"className":"...","children":"..."}]` 这种结构。客户端有 React 运行时解析后直接 patch 进现有组件树。

和 SSR 的核心区别：

| 维度 | SSR | RSC |
|------|-----|-----|
| 产出 | 完整 HTML 字符串 | 序列化组件树（可增量） |
| 到达客户端后 | hydrate 整个页面 | patch 进现有树，保留客户端状态 |
| 后续更新 | 只首屏用一次，之后纯客户端 SPA | 可反复从服务端拉新组件片段局部替换 |

开发体验差别不大（都是 async 函数直接 fetch 数据），关键差异在传输和更新机制。样式不随 RSC payload 传输，走正常 CSS 加载链路（Tailwind 类名、CSS Modules 等客户端已加载好）。

> 💡 **Tips**：RSC 目前只有 Next.js App Router 完整支持。服务端组件不能有 `useState`/`onClick` 等交互逻辑，需要交互的部分必须标记 `'use client'`。

## Q5：AI SDK 的 Tool Calling 和 Agent 编排能力边界在哪？

Tool calling 本质就是一个最简 Agent 循环：LLM 选工具 → SDK 执行 → 结果喂回 → LLM 再决策。`maxSteps` 控制最大轮数。AI SDK 帮你封装了"工具调用循环"（否则需要手写 while 循环 + 手动路由 + 手动拼 messages）。

和正经 Agent 框架（LangChain/CrewAI/AutoGen）的区别：无内置记忆系统、不支持多 Agent 自动协作、无显式规划机制、无错误恢复策略、无防护栏。多 Agent 需要手动用多次 `generateText` 串联；Agent 路由通过工具调用实现"转接"（Swarm 模式）。

**哲学**：不提供框架，提供原语；不做自动编排，让你手动组合。好处是灵活可控无学习成本；坏处是复杂场景（Agent 互相对话、长期记忆、几十轮任务）需要大量胶水代码，此时应考虑换用专门的 Agent 框架。

## Q6：LangGraph 和 n8n 有什么区别？

二者都是"节点+边"的有向图工作流模式，但定位完全不同。n8n 是通用自动化集成平台，偏运营/低代码用户，核心场景是连接 SaaS API，作为"API 之间的胶水"使用。LangGraph 是 AI Agent 开发框架，偏开发者（写 Python），核心场景是 LLM 多轮推理、Tool Use、状态机编排，作为"LLM 推理的骨架"使用。LangGraph 内置 checkpoint、memory、human-in-the-loop 等状态管理能力，而 n8n 状态管理较轻量，主要做数据流转。

> 💡 **Tips**：DeerFlow（ByteDance 开源）底层用的就是 LangGraph + LangChain 作为 Agent 运行时。

## Q7：DeerFlow 用了 LangGraph 的哪些核心功能？

共 7 个核心功能点：

- `create_agent`（预构建 ReAct Agent）：一行代码构建标准推理-行动-观察循环图，入口在 `agents/lead_agent/agent.py`
- `AgentState` + 自定义 State：`ThreadState` 继承 `AgentState`，扩展沙箱、artifacts、todos 等字段
- Reducer 模式：`Annotated[list[str], merge_artifacts]` 实现多节点并发写状态时的去重合并
- Middleware 管道：20 层洋葱模型中间件链，在 LLM 调用前后注入行为
- Tool 节点：`@tool` 装饰器注册工具，通过 `get_available_tools()` 统一加载（内置 + MCP + ACP）
- 子 Agent 编排：`task_tool` 创建独立 Agent 实例（general-purpose / bash），双线程池并行执行，子 Agent 禁用 task 工具防止递归
- `get_stream_writer` / `get_config`：LangGraph 的流式输出和运行时配置读取

DeerFlow **没有**用底层 `StateGraph` 手动构建图，复杂度通过中间件链和子 Agent 系统消化。

> 💡 **Tips**：`create_react_agent` 实际来自 `langgraph.prebuilt` 模块，DeerFlow 最新版中 import 路径是 `from langchain.agents import create_agent`（LangGraph 已将此 API 合并到 langchain 包）。

## Q8：LangGraph 中间件的接口规范和执行时机是什么？

框架规定中间件继承 `AgentMiddleware`，实现两个钩子：`before_agent(state, runtime)` 和 `after_agent(state, runtime)`。`before_agent` 在 LLM 调用前执行，用于注入上下文、获取资源；`after_agent` 在 LLM 调用后执行，用于提取信息、释放资源。返回值 `dict` 会通过 Reducer 合并到 state，`None` 不修改。执行模型是洋葱模型：中间件按列表顺序 1→20 执行 `before_agent`，然后 LLM 调用，再逆序 20→1 执行 `after_agent`。中间件不改变图结构，而是通过修改 state 影响 Agent 行为。

典型分工：`ThreadDataMiddleware` 只在 `before_agent` 创建工作目录；`MemoryMiddleware` 只在 `after_agent` 把对话加入记忆队列；`DynamicContextMiddleware` 只在 `before_agent` 注入日期和记忆。

## Q9：LangChain 本身最核心的功能是什么？

统一抽象层——把 LLM 生态碎片化的接口统一成一套标准 API。核心模块包括：Model I/O（统一 `invoke()` 调不同 LLM）、Messages（统一 `HumanMessage/AIMessage/ToolMessage` 格式）、Tools（统一 `@tool` 工具定义和调用协议）、Output Parsers（字符串 → 结构化输出）、RAG（文档加载→分片→向量化→检索）。LangChain 提供"零件"（模型接口、工具、消息格式），LangGraph 在其上提供"组装方式"（状态图编排、循环、分支、持久化）。

> 💡 **Tips**：RAG 全称是 Retrieval-Augmented Generation（检索增强生成），用于让 LLM 访问私有数据。
