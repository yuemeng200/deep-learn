# 第1章：视频即时间的函数——心智模型、前世今生与版图

> **回扣本质**：这门课的「魂」是——**视频是时间的纯函数**。本章的任务就是把这个心智模型从零搭起来，并给你一张完整的「视频生产版图」。后续三章，本质都是在往这张图里填细节：第2章填「如何描述每一帧」，第3章填「帧如何变成文件」，第4章填「如何批量生产 + 选型」。

---

## 1.1 源头问题：视频为什么这么难被「编程」？

先抛一个场景，你立刻就能感受到痛点：

> 公司有 **1000 个商品**，要给每个商品做一个 15 秒的介绍视频（商品名逐字打出、价格弹簧弹出、产品图旋转、结尾 logo）。

如果用 **After Effects / Premiere**：你打开 AE，手工搭一个，然后……然后呢？改 1000 次？AE 的确有模板和脚本（ExtendScript），但那是个**脆弱的补丁层**，跑不在服务器上、不能 `git diff`、不能接数据库。这条路基本是死的。

为什么这么难？因为视频本质是**「时间维度上的像素流」**，而传统编程工具里，「时间」从来不是一等公民——它只是 `Date.now()` 这种墙钟时间。你能算一个数、画一个 div，但你说不清「在第 137 帧时，左上角那个文字的透明度应该是 0.73」。

这就是 Remotion 要击穿的根本问题：**给「时间」一个一等公民的位置，让视频可以被精确地、确定地用代码描述。**

GUI 时间线工具（AE/Premiere/FCP）的真正局限不是「不够强」，而是**黑盒**——它的产出是一个 `.aep` 二进制文件，无法版本化、无法数据驱动、无法复现、无法自动化。它适合**一个精心打磨的作品**，不适合**程序化、规模化的生产**。

## 1.2 核心重构：视频是时间的纯函数

这是整门课最重要的一句话，理解它，后面一切都顺：

> **正如 React 把 UI 渲染成 `f(state)`，Remotion 把每一帧渲染成 `f(frame)`。**

在 React 里，你从不直接操作 DOM，你只声明「给定这个 state，UI 长这样」。Remotion 完全一样——你从不直接「播放动画」，你只声明「给定这一帧，画面长这样」：

```tsx
import { AbsoluteFill, useCurrentFrame } from 'remotion';

export const MyVideo = () => {
  const frame = useCurrentFrame();          // ← 唯一的时间输入
  const opacity = Math.min(frame / 30, 1);  // ← opacity 是 frame 的纯函数

  return (
    <AbsoluteFill style={{ backgroundColor: 'white',
      justifyContent: 'center', alignItems: 'center' }}>
      <h1 style={{ opacity, fontSize: 120 }}>Hello, Remotion</h1>
    </AbsoluteFill>
  );
};
```

注意这里**没有任何动画 API**——没有 `.play()`、没有 timeline、没有 keyframe。但你跑起来，文字会从透明渐变到完全显示。

**为什么？因为「动画」不是一个独立的概念。** 当 `frame` 从 0 连续步进到 150，组件对每一帧的「静态描述」在时间上连接起来，动画就**自然涌现**了。用微积分的语言说：**动画是「帧的纯函数」在时间维度上的导数。**

这个认知极其关键，记牢它：
- Remotion **根本不做动画**，它做的是「对每一帧的渲染」。
- `useCurrentFrame()` 是组件里**唯一**的时间输入。
- **确定性由此而生**：相同的 `frame` + 相同的数据 → 永远是相同的像素。没有随机、没有墙钟、没有竞态。

> 💡 **轻量验证（思维实验）**：假如 `useCurrentFrame()` 不是纯函数——比如它内部混入了 `Math.random()` 或 `Date.now()`——会发生什么？
> 答案：确定性崩溃。同一帧渲染两次结果可能不同，视频无法复现，无法 git 版本化，渲染时帧与帧之间会出现闪烁。**这就是为什么 Remotion 用尽一切手段（包括后面会讲的 `delayRender`、逐帧截图而非实时录制）来保卫确定性。** 确定性不是它的一个 feature，是它的地基。

## 1.3 前世今生：Remotion 从哪来

- **谁**：**Jonny Burger**，瑞士开发者、资深 React 工程师。
- **起点动机**：他在做视频时厌倦了 AE 的手工活，问了一个朴素却锋利的问题——**「为什么不能用 React 写视频？」** 关键洞察是把 `frame` 当作 React 的「状态变量」：一旦时间变成 props/state，视频就成了 UI 在时间维度的延伸，整个 React 生态（组件、hooks、TS、props 流）可以原样搬过来。
- **时间线**：
  - **2021 年**：公开发布 **v1**，确立「frame 纯函数」模型与 `<Composition>` 抽象。
  - **2021 年末**：推出 **Remotion Lambda**（云端渲染）——这是**商业化的关键一步**，让视频能跑在 AWS Lambda 上规模化渲染。
  - **v2 / v3**：生态扩张——`<Player>`（Web 内嵌实时播放器）、各种 codec/媒体包、`@remotion/renderer` 编程式 API。
  - **v4（2023+）**：成熟期，稳定至今（当前 v4.x）。
  - **现在（2026）**：正在**重构渲染管线**，用 **WebCodecs** 逐步替代 FFmpeg（第3章核心）。
- **为什么能成**：踩中两股浪——「视频生产软件化」+「创作者经济/短视频爆发」；同时技术上吃准了 React 已是事实标准这个红利。

**商业模式**（先埋个种子，第4章细讲）：**框架本身免费**，但有一条「Company License」——超过 3 人的营利公司使用需购买许可证；云端渲染（Lambda/Cloud）是付费服务。这点和纯开源竞品（如 HyperFrames 的 Apache 2.0）有本质区别，会影响你的选型与成本结构。

## 1.5 横向对比：为什么「时间的函数」是更优抽象？

| 方案 | 本质 | 致命短板 |
|---|---|---|
| **FFmpeg 脚本** | 对**已有素材**做变换（剪辑/转码/拼接/水印） | 无法**生成**程序化画面（如「价格弹簧弹出」）。它是「后期」，不是「创作」。 |
| **Canvas + MediaRecorder** | 在 Canvas 上画动画并**实时录制** | **实时、非确定**：帧率不稳、无法指定某帧时刻，3 分钟视频必须录满 3 分钟（第3章详述）。 |
| **AE 表达式（Expressions）** | 在 GUI 里用 JS 驱动个别属性 | 是 GUI 工具的「补丁」，非一等公民：不能 `git diff`、不能组件化复用、不能服务器批量。 |
| **WebGL 直接渲染 + 截图** | 最底层，自己造一切轮子 | 等于从零写一个 Remotion，放弃了 React 生态。 |
| **Remotion（时间的函数）** | 把视频提升为 **React 一等组件** | （需要学习成本、渲染较慢——这是它**主动选择**确定性带来的代价） |

Remotion 的高明之处：它没有发明新 DSL，而是**复用了你已有的全部心智资产**（React/TS/CSS/SVG…），同时用「frame 纯函数」这一个抽象，同时拿到了**组件化、类型安全、数据驱动、确定性、可自动化**。代价是渲染速度（第3章会拆解）——但这是它为确定性**主动支付的**，不是缺陷。

## 1.6 动手：第一个 Composition

**① 入口 `src/index.ts`**
```tsx
import { registerRoot } from 'remotion';
import { RemotionRoot } from './Root';
registerRoot(RemotionRoot);   // 把 Root 注册给 Remotion 运行时
```

**② Root —— 定义「有哪些视频」`src/Root.tsx`**
```tsx
import { Composition } from 'remotion';
import { MyVideo } from './MyVideo';

export const RemotionRoot = () => (
  <Composition
    id="MyVideo"           // 唯一标识（渲染/Lambda 时用它指定）
    component={MyVideo}    // 描述「每帧长什么样」的组件
    durationInFrames={150} // 总帧数 = 5 秒 × 30fps
    fps={30}               // 帧率
    width={1920}           // ← 这三个定义了视频的「时空容器」
    height={1080}
  />
);
```

**③ 组件 —— 描述「每帧」`src/MyVideo.tsx`**（即 1.2 那段）

理解 `Composition` 的关键：**它定义的是「容器」（时间空间），而 `component` 定义的是「内容」（每帧的纯函数）。** `durationInFrames × fps` 给出时长，`width/height` 给出空间。`fps=30` 的含义是：运行时会**以 1/30 秒为步长**，把 frame 从 0 推到 149，对每个 frame 渲染一次你的组件——这就是「逐帧」的全部含义。

初始化与预览：
```bash
npx create-video@latest my-first-video   # 脚手架（会问你选哪个模板）
cd my-first-video
npm run dev                               # 启动 Remotion Studio，浏览器实时预览
```

Studio 左侧是一个**时间轴**——拖动它，本质就是手动设置 `frame`，组件对每个 frame 重新渲染。**你在 Studio 里「拖时间轴」看到的，和最终渲染出来的视频，是同一个纯函数的两次调用——所以所见即所得，确定性保证。**

## 章末思考题

**题 1（理解层）**：Remotion 的组件里**没有任何动画 API**（没有 play、没有 timeline），却能产生动画。请解释这是为什么，并说明这个「没有」为何反而是核心设计的体现。

> **参考答案**：因为动画不是独立概念，而是「帧的纯函数」在时间维度上自然涌现的结果。组件只对「当前 frame」做静态描述；当运行时把 frame 从 0 步进到 N，每帧的静态描述连起来就成了动画。用微积分类比：动画是帧函数对时间的「导数」。之所以**没有**动画 API，正是因为 Remotion 把动画降维成了「对每帧的纯函数渲染」——你不需要额外的动画概念，`frame` 这一个输入就足够。这种「少即是多」正是它确定性的来源：没有隐式状态机、没有时间事件、没有竞态。

**题 2（对比/应用层）**：回到「1000 个商品各做 15 秒视频」的需求。用 **AE**、**FFmpeg**、**Remotion** 分别会卡在哪一步？为什么 Remotion 是这个场景的天然解？

> **参考答案**：
> - **AE**：卡在「无法批量」。手工做 1 个可以，1000 个不可能；即使模板+ExtendScript，脚本脆弱、跑不在服务器、不能并发。它的产出是黑盒 `.aep`，无法流水线化。
> - **FFmpeg**：卡在「只能变换、不能生成」。它能拼接已有素材、加水印、转码，但**表达不出**「商品名逐字打出 + 价格弹簧弹出」这种**程序化视觉**——它没有「在 frame N 时属性是多少」的表达力。
> - **Remotion**：组件接收 `props`（商品名/价格/图），`calculateMetadata` 根据数据算时长，外层一个循环或队列调用 `renderMedia`，1000 个视频就是 1000 次函数调用。这是「让视频像软件」哲学的直接兑现——视频成了可调用、可参数化的函数。这也是第4章（数据驱动 + Lambda 批量）要彻底打通的能力。

**题 3（深度/边界层，预告第3章）**：Remotion 假设「frame 由外部精确控制、每帧可被单独截图」。设想未来浏览器原生支持了**确定性逐帧编码**（如 WebCodecs 的 `VideoEncoder` 配合可控步进）。**Remotion 现在仍然采用「无头 Chrome 逐张截图 + FFmpeg」的方式，这是出于什么权衡？这套「截图方案」未来会被淘汰吗？**

> **参考答案**：
> - **现在为什么这么做**：因为「用真实浏览器渲染每一帧」是当前**最确定、最通用**的方案。浏览器里能渲染的一切——异步字体加载、React 状态、CSS 动画、Canvas/WebGL——都能被截到；并且每帧可以用 `delayRender()` 精确「等待资源就绪」再截。这换来了 100% 的确定性和表现力。
> - **会不会被淘汰**：要分清两个环节——**「画面生成」** vs **「编码」**。WebCodecs 替代的是**编码环节**（取代 FFmpeg 把帧压成 mp4），它**不替代**画面生成——帧仍然要由浏览器渲染出来。所以「用浏览器渲染每一帧」的范式不会变，变的只是「渲染好的帧送给谁编码」。
> - **真正可能动摇范式的**，是「能否在浏览器**进程内**同时完成确定性渲染 + 编码并直接输出文件」（省掉截图的进程间往返）——这正是 Remotion 用 WebCodecs 重构管线的方向。所以不是「截图方案被实时录制取代」，而是「截图 + 外部 FFmpeg」演进为「截图 + 浏览器内 WebCodecs 编码」。第3章会把这个演进彻底讲透。
