# Dive

对开源项目做证据驱动的中文拆解。目标不是复述 README，而是判断它实际解决什么问题、方案是否成立、技术价值和使用风险是什么。

## 步骤

1. 明确研究目标。用户没有指定时，默认回答“这个项目是什么、怎么实现、是否值得关注”。
2. 收集事实证据：
   - 仓库元信息：描述、语言、license、star/fork、release、最近活跃。
   - README 和官方文档：只当作项目自述，不直接当作事实。
   - 目录结构和关键源码：验证实际组成、入口、输入输出、扩展点。
   - Issues、Discussions、Releases：验证真实用户痛点、维护状态和限制。
3. 做本质还原：用两句话说明它实际做什么、目标用户是谁、在技术链路中的位置。
4. 做架构分析：描述关键模块、核心抽象、数据/调用链路，以及方案匹配度。
5. 做价值判断：区分真实创新、体验改进、包装话术和重复造轮子；指出失败场景。
6. `Evidence-gated` 扩展分析：
   - 用户关心选型或市场位置时，做 2-4 个竞品对比。
   - 用户关心参与或学习时，做技术投资回报和参与路线图。
   - 信息无法验证时标注“未获取到”，不要猜。
7. 按 `docs/dives/` 约定保存：
   - 文件：`docs/dives/{项目名}-research-{日期}.md`
   - 更新：`docs/dives/index.md` 的“当前拆解”列表追加链接。

## 输出要求

- 报告包含 frontmatter：`title`、`date`、`summary`。
- 结论前置，证据可追溯。
- 中文输出，技术术语保留英文原文。
- 数字给出具体值；不要写“很多”“较快”这类模糊判断。
- README 声明必须用代码、文档、issue 或 release 交叉验证。

## 报告结构

```markdown
---
title: {项目名} 深度研究报告
date: YYYY-MM-DD
summary: [一句话概括本次研究的核心主题]
---

# {项目名} 深度研究报告

## 结论先行

## 一、项目概览

## 二、它实际解决什么问题

## 三、怎么解决的

## 四、本质与创新

## 五、使用建议

## 六、竞品对比（按需）

## 七、参与价值（按需）

## 证据来源
```
